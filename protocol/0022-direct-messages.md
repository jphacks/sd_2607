# 0022: 個別通信（DM）プロファイル

状態: 提案・未採用 — `apps/messenger`（Hanashi）の相互運用デモが使う値の記録。[0003 §9.3](0003-open-questions.md) で延期された個別通信を決定するものではない。§1〜§5 は既存の合意事項（署名・メッシュ形式・配送期限）を変更しない。

## 1. 目的と範囲

Mosimo のメッシュは、どのアプリが発信した署名済みイベントでも、署名・宛先 EID・配送期限が正しければ保存して中継する（[mndt §9](mndt.md)、`MeshEngine.insert`）。この性質を使い、投稿以外の用途のアプリが同じメッシュを共有できることを、1対1のメッセージで示す。

- 対象: テキストのみの 1対1 メッセージ、配達通知、表示名。
- 対象外: グループ、メディア、既読通知、メタデータ秘匿、鍵の失効・ローテーション、オンライン配送。

## 2. イベント

いずれも通常の Nostr イベント（[0012 §4.2](0012-bindings.md) の CBOR で bundle に入る）。発信者は Mosimo の Nostr 鍵で署名し、`mosimo.oriom.dev:delivery-expires-at` を必須タグとして付ける（既定 24 時間）。atproto commit は付けない。

| 用途 | kind | タグ | content |
|---|---|---|---|
| メッセージ | 4 | `["p", <宛先 pubkey>]`, `["t", "mosimo.oriom.dev"]` | [NIP-04](https://github.com/nostr-protocol/nips/blob/master/04.md) 暗号文 |
| 配達通知 | 4 | 上記 ＋ `["e", <受け取ったメッセージの event id>]` | 空文字列の NIP-04 暗号文 |
| 表示名 | 0 | `["t", "mosimo.oriom.dev"]` | `{"name": "<最大40文字>"}` |

- 暗号化は NIP-04（ECDH の x 座標を鍵とする AES-256-CBC、`base64(暗号文)?iv=base64(iv)`）。相手の x-only 公開鍵は偶数 y として持ち上げる。
- 受信側は `p` が 1 つだけで自分を指す kind 4 のみを読む。`e` があれば配達通知、なければメッセージとする。
- 本文は UTF-8 で 2,000 バイト以下（`MeshPolicy` の bundle 上限内に収めるための実装上限）。
- 表示名は起動時と変更時に発信する。同じ pubkey の表示名は `created_at` が新しいものを採る。

## 3. 配送状態

送信側は次の状態を表示する。いずれも観測であり、保証ではない。

| 状態 | 条件 |
|---|---|
| 送信中 | 端末に保存済み。どの隣接ノードにも渡っていない |
| 中継 | 隣接ノードが bundle に `ack` を返した、または inventory に含めた（ホップ単位） |
| 配達 | 宛先から該当 event id の配達通知を受け取った（端末間） |
| 期限切れ | 配達通知がないまま配送期限を過ぎた |

配達通知も発信者ごとの発信頻度制限（1分あたり12件）に数える。

## 4. 既存ノードでの扱い

- 中継ノードは kind を問わず保存・中継する。投稿 UI は kind 1 のみを表示する。
- PDS は kind 1・5 のみを受け付けるため、それ以外の kind は PDS へ搬出せず、PDS 受入待ちによる追い出し保護もしない。一般の Nostr リレーへは従来どおり搬出しうる（暗号文と `p` タグが公開される）。
- Hanashi 自身はリレーへ接続しない（メッシュのみ）。

## 5. 既知の限界

- NIP-04 は誰と誰が通信しているか（`pubkey`・`p`）を隠さず、Nostr でも非推奨である。秘匿が必要なら NIP-17（gift wrap ＋ NIP-44）へ移行する。
- 宛先は配送期限内にメッシュ上で接触できなければ受け取れない。再送はしない。
- 表示名は自己申告で、本人確認ではない。

## 6. 未決定事項

- **同一端末の複数アプリ**: 各アプリが独立したメッシュノードとして同じ GATT Service UUID を広告する。LAN（`_mosimo._tcp`）では同一端末内のアプリ同士も相互に中継できることを実機で確認したが、BLE での共存は未検証。将来は端末あたり 1 ノードとし、他アプリがプロセス間通信で利用する形などを検討する。
- 個別通信を正式に採用する場合の kind・暗号方式・宛先 EID（[mndt](mndt.md) の単一宛先 EID）の選択。
