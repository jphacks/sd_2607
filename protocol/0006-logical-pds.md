# 0006: 論理 PDS と分散公開

状態: draft-00（構成方針合意。内部通信と適合試験は未定）

## 1. 公開モデル

端末を著者の単一 writer とし、収集・復元サーバー群が署名済みリポジトリを復元・複製する。既存 Relay に対しては、一つの論理 PDS として公開する。元の commit・CID・`rev` を維持し、サーバーが著者として再署名しない。

複数の運用グループが、それぞれ論理 PDS を提供できる。DID は一つのグループの公開 HTTPS endpoint を正規 PDS として指定する。全世界で一つの公開ドメインを必須にはしない。アプリ・運用者が既定グループを事前設定し、初回 PLC 操作からその公開 endpoint を指定する。これにより初回起動がオフラインでも公開先を含む初期操作を署名できる。代理登録ノードは指定先を改変しない。

DID での指定、グループによる受け入れ、リポジトリの公開完了は区別する。endpoint の指定だけで受け入れや公開を保証しない。受け入れの具体的な制限・確認方法、既定グループが停止している場合の扱いは未決定である。公開先変更は端末の PLC 管理鍵による署名を必要とする。

物理 PDS と論理 PDS グループは多対多の関係とし、同一の物理 PDS が複数グループに所属できる。署名済みブロックの保存を共用しても、各論理 endpoint の公開対象・stream・`seq`・再送履歴・account 状態は区別する。

## 2. 参加権限

情報の収集・検証・ミラーは誰でも独立して行える。正規公開系への参加には各グループの承認・認証を必要とする。データを保持しているだけで公開 endpoint の応答・採番・切替等の権限を得ることはない。

承認済みの物理 PDS にも著者の投稿署名鍵・PLC 管理鍵を渡さない。参加・離脱・権限失効とグループ間の独立した認証の具体方式は未決定である。

### 2.1 発信者の受け入れ

初期仕様の基本方式として、発信者の事前登録なしに署名済みデータから受け入れを開始できるようにする。初期 PLC 操作・鍵対応宣言・署名済み投稿等を検証し、DID の正規公開先が自グループであることを確認したうえで、資源上限・濫用対策・運用方針の範囲で復元・公開する。

DID に自グループを指定されただけで無制限の保存義務は生じない。拒否・保留・容量超過と公開完了の確認方法は未決定である。発信者の受け入れは物理 PDS の運用参加承認とは別であり、発信者は公開系の運用権限を得ない。

### 2.2 グループ間のコミット共有

DID の正規公開先が他の同一プロトコル対応の論理 PDS グループであり、その正規公開先がまだ知らない commit を収集した場合、当該グループへ commit や取得元 Nostr リレー情報を共有する。正規公開先が世界中の Nostr リレーを自力で監視できることだけに依存しない。

共有する元の著者署名・Nostr event ID・commit CID・`rev` を変更しない。commit 単体にレコード本文や復元に必要な情報が含まれるとは限らないため、必要な交換データ・ブロックの取得にもつながる仕組みを設ける。取得元リレーの URL やイベント参照は探索ヒントであり、そのリレーの可用性・保持・真正性の保証ではない。中継時に元 Nostr イベントのタグへ追記してはならない。

共有を受けたグループは元データを独立に検証し、自グループの方針で受け入れる。共有元グループが受信先 DID の正規公開元になることや、通知だけでリポジトリ状態の検証・公開が完了することは意味しない。

共有の基本方式は、小さな通知を送り、受信側が必要なデータだけ取得する方式とする。既知の commit であれば取得を省略できる。通知の候補情報は著者 DID・commit CID・対応する Nostr event ID・取得先だが、必須項目と正確な形式は未決定である。通知の受信、元データの検証、リポジトリ状態の検証・公開完了を区別する。

正規公開先が停止中の場合は、共有元が制限付きで再試行する。通知を受けただけで別グループへ転送し続けず、原則として DID の正規公開先への共有に限定して循環を抑える。DID の移行時の具体処理、再試行回数・期間・間隔は未決定である。

相手が既知かを確認する方法、対応グループの発見、DID 更新・解決失敗時の保留、通知・取得・応答の形式、送信者認証、取得データの保持と可用性、大量通知の抑止は未決定である。通知中の CID・`rev` や URL の自己申告だけを根拠に受理を完了しない。DID や取得元 URL も不信な入力として扱い、外部アクセスには SSRF・増幅攻撃・資源枯渇への対策が必要となる。

### 2.3 物理 PDS による Nostr リレー提供

物理 PDS 自身も Nostr リレーとして機能する。クライアントが接続できる場合は標準 Nostr イベントを直接投稿し、保持されているイベントの取得・購読も直接行える。本プロトコルの独自タグや古い投稿時刻だけを理由に拒否しない受け入れ方針を提供し、クライアントの優先的な利用先とする。

グループ間通知の取得先として、共有元物理 PDS の Nostr リレーも案内できる。Nostr での受理・保存と、論理 PDS の正規公開先としての状態検証・公開完了は別である。詳細は [Nostr リレープロファイル](0007-nostr-relay-profile.md) を参照する。

### 2.4 MST の再構築

メッシュ・Nostr の入力は、端末署名済み commit・レコード・path・変更操作を元に PDS 内で MST を再構築して検証する。MST ノードを同梱する独自配送形式は設けない。各更新の配送データには適用元 commit CID を含め、Nostr 署名で保護する。初回は適用元なしを明示し、以後は端末が直前に確定した commit を参照する。標準 commit の形式は変更しない。PDS は検証済みの適用元状態に変更を適用し、新しい commit の `data` と root を照合する。適用元の状態や必要な過去の変更が欠落している場合は状態検証を保留する。

欠落コミットを探して補完するプロトコルは [延期課題](0003-open-questions.md#9-延期した課題今回の設計対象外) とし、今回は定義しない。発見済みデータのグループ間共有は維持する。再構築後の標準 atproto API・firehose では、既存仕様に必要な MST・CAR を PDS が生成・提供する。

## 3. 外部動作の要件

内部の DB、複製方式、合意アルゴリズム、リーダー選出方式は固定せず、以下の外部動作を要求する方針とする。

- 同じ論理 endpoint の `seq` を、障害切替後に別の意味で再利用しない。
- 保持する再送範囲では、カーソルから欠落なく再開できる。
- 再送できない範囲は欠落を隠さず、標準の再同期経路で回復できるようにする。
- 提供する署名済みリポジトリと公開する更新情報を整合させる。
- 整合性を保てない複製先へ無条件に切り替えない。

これは特定の内部方式での実現可能性や、常に無停止で切り替えられることを検証したものではない。stream と API の整合性の具体的な保証範囲、再送 window、障害状態・復旧手順と適合試験は今後定義する。

各物理 PDS が無調整に採番した stream を負荷分散するだけでは要件を満たさない。異なる公開 endpoint 間の `seq` を共通カーソルとして流用しない。

## 4. 内部実装と相互運用の境界

特定の DB や分散基盤を本プロトコルへの参加条件として要求しない。一方、内部方式が自由であることは、任意の異なる実装がそのまま同じグループで協調できるという保証ではない。

異なる実装同士が同一グループで協調するための、メンバー認証・ブロック交換・イベントログ複製等の共通通信仕様を規定するかは未決定である。

## 5. 残る依存点

共通公開名の DNS・TLS・ドメイン管理権限、stream の制御系は依存点として残る。複数運用者によるデータ複製だけで単一障害点が解消したとは扱わない。

論理 PDS 全体が利用不能になった際、別グループへ移す場合は DID の PDS endpoint 更新が関係する。PLC 管理鍵を端末だけが保持するため、端末不在時の任意の公開先変更を保証しない。具体的な復旧方針は未決定である。
