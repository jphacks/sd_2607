# 0003: 未決事項と仕様化の順序

状態: draft-00

本書は未解決事項の一覧であり、選択肢を採用済みとして扱うものではない。設計対話は一度に一つの判断を確認し、結果を関連文書へ反映する。

## 1. ID と署名

- 採用済み `did:plc` の初期操作の配送形式。初期操作のローカル検証、オンラインノードによる代理登録、登録・解決確認の具体規則。
- 初回 DID Document の導出元となる PLC 初期操作の PDS endpoint、管理鍵の回復構成、登録再試行・負荷制限・更新・失効確認。`rotationKeys` には端末の PLC 管理用公開鍵を用いる。
- 採用済みの相互署名付き鍵対応宣言の符号化・配送・更新・失効、DID を含めるか。鍵生成・保管、独立生成と用途別導出の選択。初期仕様で端末が生成する3用途の鍵は、別々の鍵のまま曲線を `secp256k1` に統一することが合意済み（Nostr は BIP-340 Schnorr、atproto・PLC は ECDSA）。PLC 管理鍵も投稿署名鍵から分離して端末だけに保持する。機関の身元証明用鍵・サービス鍵の曲線はこの決定の対象外。
- 同一 DID の単一 writer、再インストール、鍵侵害・失効。OS バックアップ復元等による状態の巻き戻りへの対応は §9.5 に延期する。

## 2. 投稿・交換データ

- 正式名称・識別子・Lexicon NSID・版管理。
- レコード、commit、Nostr タグの正確な対応と検証順序。初期仕様は Nostr → atproto の復元・公開を対象とし、atproto → Nostr の逆変換は対象外。atproto レコード内の Nostr 署名保持は要求しない。
- 本文重複を避けつつ元の署名対象バイト列を復元する方法。
- CBOR の決定的符号化、CID、数値・時刻・文字列・未知拡張の取り扱い。
- 発信地点・影響範囲のスキーマ、精度、符号化、距離計算法。WGS 84 の緯度・経度（度）、円の半径はメートルとし、高度を範囲判定に使わない。初期仕様は円と地域コードに限定し、多角形は対象外。
- 採用済み Geohash の精度・セル数上限、正規化、空の領域一覧の扱い、索引用タグの選定。複数領域は和集合とすることが合意済み。行政区域コードは初期仕様の地域コードに採用しない。境界データ不要・オフラインでの領域判定・小さな組み込み実装を重視する。
- サイズ・ネスト・要素数・本文長等の資源上限。

## 3. リポジトリの同期

- PDS が操作・レコードから MST を再構築する方式を採用済み。本プロトコルの入力に MST ノードや包含証明を同梱する形式は定義しない。
- 適用元 commit CID を Nostr 署名対象の配送情報として含める方式は採用済み。初回は適用元なしを明示し、以後は端末が直前に確定した commit を指定する。検証済みの適用元状態から再構築し、新しい commit の root と照合する。具体形式、初回状態の検証規則、順序逆転時の保留・再評価、再構築上限、検証待ち状態を定義する。欠落コミットを探索・取得するプロトコルは §9 に延期する。
- 古い状態や fork の検出と解決。ただし、OS バックアップ復元等による状態の巻き戻りへの対応は §9.5 の延期対象とする。
- 配送同値によるイベントの省略と、個々のリポジトリ復元の両立。

## 4. 削除・訂正

- 投稿イベントと削除要求、atproto の削除操作の対応形式。削除は MST のレコードを除いた新しい commit を生成する操作であり、過去の commit の消去ではない。複数削除のバッチ化と注釈に対応する Label の撤回は未決定。
- 削除要求と対象イベントの同一著者検証、先行到着時の保留。
- 削除要求の保持期間、再投入抑制、未接続期間との関係。
- 通常投稿と訂正・補足・追認は1件につき1レコード追加・1 commit・1 Nostr 投稿とし、誰でも自身のレコードとして注釈できる。参照、連鎖、複数注釈、元著者と他者の主張の表示を定義する。
- 本人署名付き注釈レコードを正本とし、グループ等の Labeler が自身の DID を `src` としてサービス鍵で標準 Label を集約発行する方式は採用済み。具体的な運用単位・値・採用基準・`#atproto_label`・Labeler endpoint・配信、元注釈との対応・集約・撤回・冗長化を定義する。レコード追加だけで標準 Label 配信が成立するとは扱わない。
- 基本 Label は注釈の存在を示し、元の発信者の確認済み身元・署名を信頼判断に利用できる方針は合意済み。自治体等の身元はアプリ既定・利用者選択のルート公開鍵から名称と公開鍵への多段署名チェーンで証明し、論理的な拡張ブロックとして含める。投稿用鍵・証明権限・再委任権限を区別し、下位で権限範囲を拡大しない制約は採用済み。末端証明は組織名・DID・atproto 署名公開鍵を結び付け、Nostr 鍵は相互署名付き鍵対応宣言を介して結び付ける方式も採用済み。証明には有効期間を設け、署名・権限検証、期間確認、失効情報の確認時点、情報不足の状態を区別する方針も採用済み。証明書形式・組織／名称／用途の範囲と包含判定・権限の符号化・検証に用いる DID の状態・経路長／サイズ・有効期間の長さ／時刻表現・失効情報の形式／鮮度・時計ずれ・鍵更新時の再発行と過去投稿の扱いを定義する。Label から元注釈・署名・証明へたどる API／索引、信頼の重み・適用範囲・相反する指摘の扱いも未決定。
- 配送同値グループの代表イベントが削除された場合の扱い。

## 5. メッシュ配送

- アプリ間相互接続の発見方法と BLE・Wi-Fi 等のリンク仕様。
- OS のバックグラウンド制限と実装可能な接触・転送モデル。
- BPv7 の endpoint、bundle 構成、フラグ、登録・未登録コードの検証。
- 接触時の inventory・要求・転送形式と資源制限。
- 時計ずれの具体的な判定、寿命、hop、再バンドル、重複排除記録の寿命。配送期限の実施はベストエフォートとし、時刻不明でもローカル上限内での中継を許容することは合意済み。
- 情報の有効期間と配送期限は分離する。通常投稿の署名付き配送期限は必須。情報の有効期間の必須・任意、既定期間、制御データの扱い、満了後の表示・保存、他の層の保持方針との関係は未決定。
- 地域内優先・範囲外抑制・ゲートウェイ搬出の具体規則。
- 優先度の段階数・既定値・スケジューリング、Sybil、DoS、断片化・再組み立て。著者指定はヒントとし受信側が実効優先度を決め、資源上限を解除しない方針は合意済み。

## 6. オンライン公開と冗長化

- 物理 PDS が Nostr リレーを兼ね、直接投稿・取得・購読の優先先となる方針は採用済み。能力・制限公開には NIP-11 と本プロトコル向け追加情報を採用する。本文と訂正は `kind: 1`、削除要求は `kind: 5` とし、制御データは別イベントに分離する。検索用プロトコル識別は `t` タグを採用済み。識別値・種別ごとの適用・バージョン表現、制御イベントの kind・追加索引・追加 NIP・能力公開の具体スキーマ・リレー互換性・保存方針を定義する。独自タグや古い投稿時刻だけで拒否しないが、具体的な資源・時刻・削除の規則は未決定。
- アプリ同梱候補・キャッシュ・AppView 一覧・Nostr 経由の候補発見を併用する。独自拡張のない著名な一般リレーも同梱できる。信頼済みの複数発行者の一覧を自動更新の基本とし、未知候補は区別して制限付きで探索する。具体的なリスト、Nostr 発見方式、発行者認証・候補更新／失効、接続数・探索枠・再試行上限を定義する。
- PDS 公開名の管理、既定グループの受け入れ条件・確認、停止時の処理。初回登録からアプリ・運用者が事前設定したグループの endpoint を指定する方式は採用済み。複数の論理 PDS グループを許容し、DID は一つのグループを指定する。
- 一つの論理 PDS を既存 Relay 向けに公開し、背後の収集・復元サーバーを分散する構成は採用済み。物理 PDS は複数グループへ同時所属できる。収集・ミラーは自由、正規公開系への参加はグループが承認・認証する。承認・認証の具体方式、離脱・権限失効、複数サーバーの発見・複製・保存・論理 endpoint ごとの stream 統合と切替機構は未決定。
- [PDS・Relay 調査](0005-pds-relay-research.md) で正規ホスト照合・`rev` 重複処理・stream cursor の制約を確認済み。対象 Relay の実デプロイ版・設定と runtime 相互運用、共通ホスト背後の stream 継続性・DNS/TLS/管理権限の障害耐性は未検証。
- 内部の DB・合意方式は固定しない。外部の整合性・再送・復旧要件を具体化し、適合試験を定義する。異なる物理 PDS 実装同士の内部共通通信仕様の要否は未決定。
- 他の対応グループ宛ての未共有 commit は小さな通知＋必要時取得で正規公開先へ共有する。対応先発見、既知状態の確認、通知・取得・応答の具体形式、認証、取得データの保持、DID 更新時の対応、SSRF 対策、大量通知・再試行の制限は未決定。
- 発信者の事前登録不要の受け入れは採用済み。拒否・保留・公開完了の通知と具体的な資源上限は未決定。
- AppView と Nostr の二経路取得時の同一投稿判定。

## 7. 原情報取り込み

- 既定の取り込みサーバーと信頼リストの更新・失効。
- 情報源別の原情報 ID、版、訂正・取消、原文ハッシュ。
- 決定的変換の版管理、時刻・多言語・表記揺れ。
- 配送同値キーと検証・代表選択の具体形式。
- CAP・EDXL・気象庁 XML の対応範囲と変換時の情報損失。
- BSAF の収集とメッシュ投入の区別、出典・地域コードの扱い。

## 8. 仕様完成の条件

- 一次仕様への規範参照と固定リビジョン。
- 署名・変換・MST 復元・削除・配送同値のテストベクトル。
- 未知拡張、欠落、順序逆転、時計ずれ、偽装の異常系。
- 複数実装間の Nostr → atproto 復元、Nostr とメッシュ交換データの往復変換、相互通信の検証。atproto → Nostr の逆変換は初期仕様の適合条件に含めない。
- サイズ計測と資源上限の妥当性確認。

現時点では実装、テストベクトル、相互運用試験はない。

## 9. 延期した課題（今回の設計対象外）

### 9.1 欠落コミットの探索・取得

PDS の MST 再構築に必要な過去の commit・レコード・変更操作が欠けている場合、その欠落を特定し、保有者を探して取得するプロトコルが必要になる可能性がある。今回は検証保留という状態だけを扱い、探索・修復プロトコルの設計は進めない。

将来の検討事項は、欠落の識別・履歴参照、取得先の発見、要求・応答、取得物の認証、削除との整合性、保持期間、ループ・増幅・資源制限である。発見済み commit を正規 PDS へ通知し、通知から必要なデータを取得する合意済みのグループ間共有とは区別する。標準 atproto 同期の要件を変更するものではない。

### 9.2 双方向変換における署名の維持

Nostr／atproto の相互変換で各形式の元の署名・ID を維持する問題（対話中の「相互署名の問題」）を将来課題として記録する。今回は Nostr → atproto の復元・公開だけを対象とし、atproto データから元の Nostr イベントを逆生成する機能と、そのための Nostr 署名保持は要求しない。

将来の候補には、Nostr を先に署名して復元情報を atproto レコードへ含める方式、署名対象外の配送拡張、別イベント／付随データの保持がある。いずれも未採用。参照・署名生成順序の循環、一般リレーによる拡張の除去、標準リポジトリエクスポートでの復元可能性、追加データの独立検証・可用性が検討課題となる。

これは、atproto 用公開鍵と Nostr 公開鍵の対応を両鍵で相互署名する「鍵対応宣言」とは別の問題であり、鍵対応宣言の採用は維持する。

### 9.3 個別通信・限定公開と投稿の暗号化

初期仕様は公開情報の共有に限定する。宛先を限定した個別通信、グループ限定公開、投稿本文・構造化データの暗号化は今回の設計対象外とし、将来拡張へ延期する。今回は暗号化イベントの形式・鍵配布・アクセス制御を定義しない。

将来の検討事項は、受信者認証、鍵配布・更新・失効、非接続期間中の鍵管理、宛先・接触関係の漏えい、公開リポジトリとの関係、再配布と削除の限界である。TLS 等の通信路保護は投稿自体の秘匿とは別であり、この延期で通信路保護を不要にするものではない。

### 9.4 メディア本体の配送

画像・動画・音声等のメディア本体の配送は将来拡張へ延期する。初期仕様はテキスト、構造化情報、およびそれらの検証・復元に必要な署名済み commit・レコード・交換データ等を対象とする。後者がバイト列で符号化されることは、メディア配送機能の提供を意味しない。

本文にメディアへの URL を記載することは可能だが、リンク先のオフライン取得・保持・配送は保証せず、自動取得も要求しない。CAP・EDXL・気象庁 XML 等から本文・構造化情報への変換は延期対象ではない。

メディア用の分割・再送・再組み立て、形式・容量制限、検証、保存・削除、取得のプライバシー等は将来検討する。この延期は BPv7 自体の標準機能の有無を変更するものではなく、基本交換データの最大サイズや下位リンクの転送方式は別途定義する。

### 9.5 端末状態の巻き戻りへの対応

OS バックアップ復元等により、端末内の鍵・リポジトリ・発信状態が過去へ巻き戻った場合の対応は将来課題へ延期する。今回は巻き戻りの検出、旧 DID での発信再開条件、履歴の回復・分岐解消を設計しない。復元時に新しい鍵・DID を発行する案も採用済みとはしない。

通常動作で発信端末を単一 writer とする既存方針は維持するが、バックアップ復元後の安全な発信継続や履歴の非分岐を保証するものではない。この延期は、PDS が古い commit を受信しただけで検証済みの現在状態を無条件に巻き戻さないという既存方針を変更しない。
