# 0002: 公的情報の取り込みと信頼

状態: draft-00（方針合意、データ形式は未決定）

形式別のデータ構造・処理の流れと BSAF 互換性は [0013](0013-public-information.md) に整理する。本書は信頼と配送同値性の方針を扱う。

## 1. 信頼モデル

インターネットからメッシュへ取得情報を無条件に投入しない。情報源を特定でき、規定の変換によって誰が持ち込んでも元情報の同値性を判定できる取り込み方式を設ける。

初期運用では、受信者が既定の複数の取り込みサーバーを信頼する。既定では1者の有効な署名で受理可能とし、複数者の一致は追加の確認とする。受信者は信頼対象を選択でき、より厳格な方針を採用できる余地を残す。

信頼済みの1者が侵害されると誤情報を受理し得る。信頼リストの発行・更新・失効方式と各サーバーの運用主体は未決定である。

公的情報の更新・取消によって旧版の拡散を止める認可は、一般の取り込み受理とは分ける。各ユーザーが事前に保持するルート公開鍵への署名チェーンと、対象の発信元に対応する権限範囲を必要とする。取り込みサーバーを単に信頼する設定だけでは、この認可を代用しない。詳細は [0009 §5.1](0009-identity-attestations.md#51-公的情報の更新取消の認可合意済み) に従う。

中継者を変換者として信頼する必要はない。誰でも、信頼する変換者の署名を維持して情報を持ち運べる。

## 2. 将来の発表機関署名

将来は発表機関自身が署名・発信する形を目指す。機関鍵の認証は事前に信頼するルートへの署名チェーンを使う。具体的な証明書形式・委任範囲の符号化、既存の取り込み情報との関係は未決定。

実装時の推奨は、機関自身が秘密鍵を生成・管理し、公式経路で公開鍵を告知することである。第三者が秘密鍵を配布することを必須とはしない。

## 3. 配送同値性

署名付きイベント自身の ID と、同じ元情報の配送を抑制するための配送同値キーを分離する。

- 異なる投入者の Nostr event ID と署名は別物として保持する。
- atproto の commit とリポジトリ状態も、投入者ごとに異なり得る。
- 検証済みの元情報が同値なら、配送上は例外的に同じグループとして扱い、冗長な配送を抑制する。
- 異なるイベントを合成して、元の著者署名があるかのように扱ってはならない。
- 通常の個人投稿は、本文が同じという理由だけではこの例外を適用しない。

配送同値キーの候補となる要素は、正規化規則の版、情報源 ID、原情報 ID・版、正規化内容のハッシュである。これは設計候補であり、ハッシュ対象のバイト列やフィールドはまだ確定していない。

訂正・取消・内容の相違を同じ対象として潰してはならない。内容が違う場合、原情報 ID が同じだけでは統合しない。代表イベントの選択、追加署名の取得、代表イベントへの削除要求、保持・追放は今後定義する。

## 4. 検証と重複抑制

例外的な重複排除は、信頼する情報源・変換者に基づき、データの検証後に適用する。自己申告のキーや未検証の inventory 広告だけで配送済みとしてはならない。

原情報の内容が同値であることは、異なる投入者の署名済み commit・適用元 commit CID・レコード・repository path まで不要になることを意味しない。メッシュ上の本文配送の重複抑制と、各リポジトリの完全な同期の両立方法は未決定である。

再バンドルによる寿命や配送枠の無制限なリセットを許容しないための規則も必要である。

### 4.1 更新による置換と旧版の拡散停止（合意済み）

更新後の内容は、取り込み側が本文・領域・期間・適用条件を含む単独で読める新規投稿として生成・署名する。差分だけを配送して受信側に旧投稿の取得を要求する方式にはしない。更新後の内容を確定できない場合は、旧版を推測で混ぜて完全な最新版を作ったことにしない。

形式ごとに定める明示的な更新・取消の対象と、0009 §5.1の認可を確認した端末は、対象の旧情報を新たな配送候補から外し、広告・転送開始を停止する。到着順・本文一致・自己申告の新しい時刻だけで置換を決めない。対象未取得の場合も認可済みの参照を記録し、旧版が後から到着したときの再拡散を防ぐ。記録の保持期限・資源上限・失効や相反する更新を受けた場合の再評価は別途定める。

CAPの `Update`／`Cancel` では、明示的に参照された原電文から生成された投稿群を対象とする。同じ旧原電文の言語・対象別投稿を含めて旧版とし、新電文だけに基づいて新しい情報単位を発行する。新電文にない旧内容を勝手に引き継がない。任意の投稿が自己申告した出典の文字列一致だけで、別の投稿まで公式の置換対象にしない。対象投稿の原情報への対応も確認して適用する。

EDXL-DEの容器の取消は、対象容器に対して認可された通知を独立投稿として配送し、その容器由来の投稿だけの新たな広告・転送開始を止める。同じ内包CAPを別の容器や直接の公式配信から取り込んだ別投稿までは停止せず、警報自体の取消とは表示しない。対象容器を単に参照する取消通知自身も止めない。詳細は [0016 §7.1](0016-edxl-de.md#71-容器由来の投稿の取消合意済み) に従う。

EDXL-DEの `Update` は、新容器の内容だけで単独可読な投稿群を再発行し、更新権限と由来の対応を確認できた場合に、明示的に参照された旧容器由来の投稿群の新規拡散を止める。旧容器だけにあった内容の欠落は、内包警報自体の取消を意味しない。別容器・直接配信由来の別投稿は止めず、CAP自身の更新・取消は別に適用する。詳細は [0016 §7.2](0016-edxl-de.md#72-新容器の内容による再発行合意済み) に従う。

この停止は配送上の扱いであり、旧投稿・署名・atprotoの履歴の削除や改変ではない。更新・取消の新投稿自体は独立した配送対象とし、旧対象と一緒に停止しない。未知拡張の部分実装や未接触端末まで即時に停止する保証、送信済みデータの回収は提供しない。通常の配送期限・hop・ローカル資源上限は引き続き必要である。一般の原情報同値性による重複抑制とも区別する。

## 5. 原情報の真正性：確認状況と候補

2026-10-17 に [気象庁防災情報 XML の公式情報提供ページ](https://xml.kishou.go.jp/) を確認した。同ページには PULL 型の取得方法の案内がある。今回確認したページでは、電文ごとの署名と検証用公開鍵の案内は確認できていない。全配信経路で署名が存在しないと断定したものではない。

通常の HTTPS は取得時のサーバー認証と通信保護を提供するが、レスポンス本文を後からオフラインの第三者に検証させる発表機関の署名とは異なる。原文ハッシュ、URL、取得者の署名だけで、発表機関自身による認証が成立するとは扱わない。

今後検討する方式:

- 接続可能な受信者が公式情報を取得して照合する。
- 取り込みサーバーが取得先・原文ハッシュ・取得時刻と変換結果に署名する。
- 独立した複数サーバーによる取得結果の一致を追加の確認とする。
- TLS 取得証明等を調査する。ただし初期仕様への採用は未合意であり、証明者・検証者の信頼仮定と通信量を確認する。

原XMLは取り込み側で保存し、メッシュには本文と形式別に規定した構造化項目を配送する。投稿に原文参照と必要に応じたハッシュを付けるが、原XML全量の配送は必須にせず、完全復元は保証しない。詳細は [0013 §5.1](0013-public-information.md#51-原文の保存とメッシュへの変換合意済み) に従う。取得の証言と変換の証言を結び付ける形式、原文の具体的な保存場所・保持期間・ハッシュのバイト境界は未決定である。
