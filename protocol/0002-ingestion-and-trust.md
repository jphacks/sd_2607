# 0002: 公的情報の取り込みと信頼

状態: draft-00（方針合意、データ形式は未決定）

形式別のデータ構造・処理の流れと BSAF 互換性は [0013](0013-public-information.md) に整理する。本書は信頼と配送同値性の方針を扱う。

## 1. 信頼モデル

インターネットからメッシュへ取得情報を無条件に投入しない。情報源を特定でき、規定の変換によって誰が持ち込んでも元情報の同値性を判定できる取り込み方式を設ける。

初期運用では、受信者が既定の複数の取り込みサーバーを信頼する。既定では1者の有効な署名で受理可能とし、複数者の一致は追加の確認とする。受信者は信頼対象を選択でき、より厳格な方針を採用できる余地を残す。

信頼済みの1者が侵害されると誤情報を受理し得る。信頼リストの発行・更新・失効方式と各サーバーの運用主体は未決定である。

中継者を変換者として信頼する必要はない。誰でも、信頼する変換者の署名を維持して情報を持ち運べる。

## 2. 将来の発表機関署名

将来は発表機関自身が署名・発信する形を目指す。機関の公開鍵を何に基づいて認証するか、既存の取り込み情報との関係をどう扱うかは未決定。

実装時の推奨は、機関自身が秘密鍵を生成・管理し、公式経路で公開鍵を告知することである。第三者が秘密鍵を配布することを必須とはしない。

## 3. 配送同値性

署名付きイベント自身の ID と、同じ元情報の配送を抑制するための配送同値キーを分離する。

- 異なる投入者の Nostr event ID と署名は別物として保持する。
- atproto の commit とリポジトリ状態も、投入者ごとに異なり得る。
- 検証済みの元情報が同値なら、配送上は例外的に同じグループとして扱い、冗長な配送を抑制する。
- 異なるイベントを合成して、元の著者署名があるかのように扱ってはならない。
- 通常の個人投稿は、本文が同じという理由だけではこの例外を適用しない。

配送同値キーの候補となる要素は、正規化規則の版、情報源 ID、原情報 ID・版、正規化内容のハッシュである。これは設計候補であり、ハッシュ対象のバイト列やフィールドはまだ確定していない。

訂正・取消・内容の相違を同じ対象として潰してはならない。内容が違う場合、原情報 ID が同じだけでは統合しない。代表イベントの選択、追加署名の取得、代表イベントへの削除要求、保持・追放は今後定義する。

## 4. 検証と重複抑制

例外的な重複排除は、信頼する情報源・変換者に基づき、データの検証後に適用する。自己申告のキーや未検証の inventory 広告だけで配送済みとしてはならない。

原情報の内容が同値であることは、異なる投入者の署名済み commit・適用元 commit CID・レコード・repository path まで不要になることを意味しない。メッシュ上の本文配送の重複抑制と、各リポジトリの完全な同期の両立方法は未決定である。

再バンドルによる寿命や配送枠の無制限なリセットを許容しないための規則も必要である。

## 5. 原情報の真正性：確認状況と候補

2026-10-17 に [気象庁防災情報 XML の公式情報提供ページ](https://xml.kishou.go.jp/) を確認した。同ページには PULL 型の取得方法の案内がある。今回確認したページでは、電文ごとの署名と検証用公開鍵の案内は確認できていない。全配信経路で署名が存在しないと断定したものではない。

通常の HTTPS は取得時のサーバー認証と通信保護を提供するが、レスポンス本文を後からオフラインの第三者に検証させる発表機関の署名とは異なる。原文ハッシュ、URL、取得者の署名だけで、発表機関自身による認証が成立するとは扱わない。

今後検討する方式:

- 接続可能な受信者が公式情報を取得して照合する。
- 取り込みサーバーが取得先・原文ハッシュ・取得時刻と変換結果に署名する。
- 独立した複数サーバーによる取得結果の一致を追加の確認とする。
- TLS 取得証明等を調査する。ただし初期仕様への採用は未合意であり、証明者・検証者の信頼仮定と通信量を確認する。

取得の証言と変換の証言を結び付ける形式、原文の保存・配送範囲は未決定である。
