# 0015: CAP 1.2 著者拡張と投稿への変換

状態: draft-00 — 合意済みの独立拡張・情報単位別の投稿化を具体化した仕様草案。型名は管理ドメインの割り当て委任に基づく。以下のフィールドと変換規則は実装案であり、§10 の未決事項を含む。正式な Lexicon JSON の公開・実装は本書の対象ではない。

## 1. 適用範囲

OASIS CAP 1.2（2010-07-01）の XML 名前空間 `urn:oasis:names:tc:emergency:cap:1.2` を対象とする。CAP の原情報の意味を保持する著者拡張と、人が読める基本投稿・共通拡張への対応を定義する。CAP XML の完全復元や、すべての国・組織の CAP プロファイルへの対応は保証しない。

[0013](0013-public-information.md) の取り込み・公開方針、[0011](0011-extensions.md) の任意拡張モデルに従う。1件の変換投稿は1レコード・1 commit・1 Nostrイベントとし、原XML全量は取り込み側で保存する。中継端末にCAP XMLの解析を要求しない。

## 2. 識別と他の拡張との独立性

CAP 1.2 拡張の `$type` は `dev.oriom.mosimo.defs#cap12` とする。この型だけで CAP の形式・版を識別でき、`source`・EDXL拡張・オンラインのスキーマ取得を解釈の前提にしない。CAPの版と変換規則の改訂は別であり、非互換な拡張変更には新しい `$type` を用いる。

- `cap12`: 原電文・選択した情報単位・更新取消参照・CAP固有の語彙を担当する。
- `source`: 取得URL・取得時刻・変換規則・外側の配布容器の追跡を担当する。CAP発表者の認証結果ではない。
- `area`: 共通の二次元の領域判定と配送順位に利用できる影響範囲を担当する。
- `validity`: 共通の内容有効期間を担当する。

CAP内の領域・時刻と共通拡張は同じ役割ではない。CAP拡張は原形式の条件を残し、共通拡張はCAP非対応端末にも利用できる表現を提供する。共通拡張の利用可否にかかわらず、CAP拡張自身の対象・期間・語彙を勝手に書き換えない。

## 3. データ型

以下は TypeScript 風の説明用表記である。`integer` は atproto データモデルの整数とする。XMLの数値・日時の原表記を保持する項目は文字列であり、floatを使わない。これは共通の `Timestamp`・座標・距離の整数型を変更するものではない。

```ts
type CapReference = {
  sender: string;
  identifier: string;
  sent: string; // CAP原文のオフセット付き日時。共通Timestampではない
};

type CapValue = { valueName: string; value: string };

type CapArea = {
  areaDesc: string;
  polygons?: string[]; // WGS 84の座標列。原文字列を保持
  circles?: string[];  // "緯度,経度 半径km" の原文字列
  geocodes?: CapValue[];
  altitude?: string;   // 原単位のfeet。整数ミリメートルへ読み替えない
  ceiling?: string;
};

type CapResource = {
  resourceDesc: string;
  mimeType: string;
  size?: string;       // 原形式の整数の文字列表記
  uri?: string;
  digest?: string;     // CAPのresource digest。原文ハッシュではない
};

type CapInfo = {
  index: integer;      // 元CAPの全infoを文書順に数えたゼロ始まり位置
  language?: string;
  categories: string[];
  event: string;
  responseTypes?: string[];
  urgency: string;
  severity: string;
  certainty: string;
  audience?: string;
  eventCodes?: CapValue[];
  effective?: string;
  onset?: string;
  expires?: string;
  senderName?: string;
  headline?: string;
  description?: string;
  instruction?: string;
  web?: string;
  contact?: string;
  parameters?: CapValue[];
  resources?: CapResource[];
  areas?: CapArea[];
};

type CapExtension = {
  $type: "dev.oriom.mosimo.defs#cap12";
  message: CapReference;
  status: string;
  msgType: string;
  scope: string;
  references: CapReference[];
  source?: string;     // CAP alert/source。共通source拡張ではない
  restriction?: string;
  addresses?: string; // CAPの引用符付きリストを含む原文字列
  codes?: string[];
  note?: string;
  incidents?: string; // CAPの引用符付きリストを含む原文字列
  info?: CapInfo;
};
```

`message` の三項目は原CAPの `sender`・`identifier`・`sent`、`references` はCAPの参照を三項目ごとに分解した配列とする。`info.index` は元文書内の選択位置であり、別電文の同一性や配送同値性のキーとして単独使用しない。

CAPのテキストはXMLパーサーが返す文字列を保持し、元のタグ・文字参照の綴り・属性順まで復元するものではない。省略された任意項目は省略し、存在する空文字列と混同しない。複数回出現する項目は文書内の出現順を保つ配列とし、`valueName` をキーにした辞書へ潰さない。既知型の未知フィールドも保持する。

`language` が省略または空の場合、CAP対応クライアントはCAPの既定値 `en-US` として解釈する。元の省略・空文字列は書き換えず保持し、言語未指定を受信端末の言語や日本語と推測しない。

原文の `category`・`responseType`・`eventCode`・`parameter`・`resource`・`area` は、それぞれ複数形の配列へ対応する。`polygon`・`circle`・`geocode` も同様である。`derefUri` の添付本体とXML署名本体はこの拡張へ格納しない。CAPのresource `digest` はCAP 1.2で定めるSHA-1の値であり、独自にSHA-256と解釈したり発表機関の認証に使ったりしない。原XMLの別のハッシュとは区別する。

## 4. 語彙と公開取り込み

文字列はCAPの値と大文字小文字を保持し、基本プロトコル共通の列挙値へ読み替えない。主な値は次のとおり。

| 項目 | CAP 1.2の値 |
|---|---|
| `status` | `Actual`、`Exercise`、`System`、`Test`、`Draft` |
| `msgType` | `Alert`、`Update`、`Cancel`、`Ack`、`Error` |
| `scope` | `Public`、`Restricted`、`Private` |
| `urgency` | `Immediate`、`Expected`、`Future`、`Past`、`Unknown` |
| `severity` | `Extreme`、`Severe`、`Moderate`、`Minor`、`Unknown` |
| `certainty` | `Observed`、`Likely`、`Possible`、`Unlikely`、`Unknown` |

`Very Likely` の互換処理はCAPの意味解釈に従うが、署名対象の文字列を `Likely` へ書き換えない。未知・空の値を最上位の強度や `Actual` として扱わない。

実災害向けの自動投入は、信頼設定と提供元の公開再配布条件を確認したうえで、既定では `Actual`・`Public` の `Alert`／`Update`／`Cancel` を対象とする案とする。`Ack`／`Error` はメッシュ転送の受理応答ではない。訓練・試験は明示的に有効化した別の運用で扱い、実災害情報と混同しない。限定内容を `scope: Public` に変えて投入しない。

EDXL等の外側の容器の制限も取り込み時に評価する。容器の制限をCAP拡張へ複製しなくても、その制限を無視してよいことにはならない。未知の配布制約や専用パラメーターが公開可否・安全な解釈に影響する場合、推測で公開投入しない。

## 5. 投稿単位と本文

通常は選択した `info` 一つを `info` に格納する。選択した情報単位の主要な指示・対象・期間が単独で分かる基本本文を生成する。元電文の他の言語・対象の情報を、選択した情報単位の指示として混ぜない。

本文は、発表／更新／取消の区別、発表元、標題（なければ `event`）、対象地域・対象者、`description`・`instruction`、重要な期間・高度条件等を伝える。`responseType` だけから具体的な避難先等を創作せず、本文を一律に切り詰めて指示や適用条件を落とさない。変換者による転載であることを示す。定型文・改行・重複文の省略等を含む完全に決定的な本文生成規則は未確定である。

同一言語の対象が重なる `info` は、CAPの規則により後続が先行情報を拡張することがある。その解釈結果と必要な文脈の格納方法は §10 の未決事項であり、この1要素の型だけで全ケースを独立投稿化できるとは宣言しない。原情報の意味を独立して表せない場合は、機械的に切り出して投入せず取り込み側で保留する案とする。中継端末が原CAPを取得して不足文脈を補うことは要求しない。

`info` がない取消では `info` を省略し、`msgType: Cancel` と `references` を持つ通知投稿を1件生成する。取得済みの対象だけへ参照を絞らず、未取得の対象も保持する。`info` のない通常警報について、架空の領域・指示・強度を補って投稿化しない。

## 6. 共通拡張への対応

### 6.1 時刻と validity

| 入力 | 出力・意味 |
|---|---|
| `message.sent` | 原発表時刻。投稿の `createdAt` ではない |
| `info.effective` | UTCに変換して `validity.startsAt` の候補とする |
| `effective` が省略 | CAPの規則で `sent` を有効開始として用いる |
| `info.expires` | UTCに変換して `validity.endsAt` の候補とする |
| `expires` が省略 | 終了不明。固定の期限を捏造しない |
| `info.onset` | 現象の開始。`startsAt`・投稿時刻に置き換えない |

存在する空値・解釈不能な値を、省略に対する既定値で無条件に埋めない。共通型へ変換できない端点は不明として扱い、正確な期間として利用しない。原表記はCAP拡張に残す。共通 `validity` の境界の包含等の未決事項は0011に従う。

`deliveryExpiresAt` は投稿作成時に運用者が別に確定する。`expires` から常にコピーする規則にはしない。特に取消通知には、取り消す警報の古い有効終了を配送期限として流用しない。未来に有効になる情報も、配送自体を開始時刻まで待たせる必要はない。

### 6.2 領域と area

選択した情報単位の全 `area` と、その各要素の和集合を対象として扱う。CAPの円の中心はWGS 84、半径はkmであり、共通表現では座標を100万分の1度、半径をミリメートルへ変換する。円の半径0を勝手に拡大して警報対象を捏造しない。座標の丸めと円の距離モデルは別途固定する。

多角形・解決済み地域コードは [0004 §5.1](0004-geography.md#51-原情報全体を覆う近似合意済み) の全体を覆うGeohash近似を利用できる。元領域全体を扱えなければ共通 `area` を省略する。`areaDesc` だけから位置を推測せず、`geocode` の `valueName` が示すコード体系を無視しない。

共通 `area` は二次元の配送判断用であり、CAPの `altitude`・`ceiling` を消去する根拠ではない。高度条件は原形式側と本文に残し、近似領域内であることだけで完全な適用条件を満たすとは表示しない。共通 `area` の近似区分・上限等は0011・0004の未決事項に従う。

## 7. 更新・取消の関係

CAPの原情報参照は `sender`・`identifier`・`sent` の組で扱う。時刻を照合する場合は表記ではなく時点を比較し、受信した署名対象文字列は書き換えない。電文IDだけの一致や、同じ事案を示す `incidents` だけで更新対象・同一電文とは扱わない。

`Update`／`Cancel` は元電文を参照する新しい通知として保持する。更新は差分ではなく更新後の内容だけで読める投稿として生成し、既存の署名付き投稿を編集しない。新電文にない旧内容を推測で引き継がない。`AllClear` という応答種別、警報期間の終了、誤発表の取消、NIP-09による投稿削除は別の意味である。元電文の参照をatURI・Nostr event IDとして流用しない。投稿間の注釈参照へ関連付ける索引の具体形式は別途定める。

### 7.1 原電文単位の置換（合意済み）

`Update`／`Cancel` の `references` が明示する原電文から生成された投稿群を置換対象とする。対象は旧原電文の各言語・各情報単位の投稿を含み、旧電文にしかない内容を更新後の投稿へ自動的に引き継がない。明示的な更新関係のない後着電文を最新版として上書き採用しない。

更新・取消の認可には、各ユーザーが事前に保持するルート公開鍵への署名チェーンを用いる。チェーンで証明された発信元・用途・対象範囲と、CAPの原発信元・対象関係を対応付ける。投稿のNostr署名だけ、CAPの `sender` の自己申告だけ、または取り込みサーバーへの一般的な信頼だけでは認可しない。認可と署名鍵への対応は [0009 §5.1](0009-identity-attestations.md#51-公的情報の更新取消の認可合意済み) に従う。

認可済みの置換を確認した端末は、旧対象を `INVENTORY` の配送候補から外し、新たな転送を開始しない。対象が未取得でも置換関係を記録し、後着した旧版の再拡散を抑える。CAPの自己申告の参照だけで無関係な投稿を停止せず、対象投稿の出典との対応を確認する。記録の保持・容量と相反する更新の処理は未決定である。

認可を確認できない場合は、更新の主張と未確認状態を保持し、旧情報の拡散停止は保留する。CAP非対応端末や更新未受信の端末に即時停止を保証しない。旧投稿の履歴を削除する規則でもない。更新・取消通知自体は通常の上限内で配送を続け、旧警報の古い期限を新通知へ流用しない。

この置換は後続のCAP電文によるものであり、一つの電文内の同一言語の `info` を後勝ちで上書きする規則ではない。§5 の重複 `info` の単独解釈の課題は引き続き未決定である。

## 8. 配送と部分実装

| 対応範囲 | 利用可能な処理 |
|---|---|
| 基本投稿のみ | 本文表示、署名・配送期限・サイズ・資源上限に従う保持転送 |
| 共通 area／validity | 原形式を知らずに地域別の配送順位や有効期間の表示を調整 |
| cap12 | CAPの語彙・対象参照・指示・適用条件を利用した専用の表示や処理 |

CAP対応端末は、信頼する情報に対し緊急性・強度・確実性を配送順位の追加要因にできる。ただし、これらを共通の単一優先度へ機械的に変換したり、未信頼の `Extreme` 等に無制限の帯域・保存枠を与えたりしない。既定の数値重みは定めない。

`validity` の終了と配送期限満了は区別する。終了済みという理由だけで取消通知等を一律廃棄しない。CAP非対応端末は未知拡張から `severity` 等のフィールド名だけを拾って動作せず、署名対象の拡張をそのまま保持する。受信だけを根拠とするサイレン作動等の副作用は要求せず、専用動作は利用者・運用者の信頼と権限設定に従う。

## 9. Nostr・CBORへの配置例

この拡張も1オブジェクト＝1自己完結タグとし、独自のNostr kindや個別の圧縮方式を追加しない。

```text
タグ名: mosimo.oriom.dev:ext:dev.oriom.mosimo.defs#cap12
タグ値: $type以外の全フィールドのatproto CBORを通常Base64・paddingなしで符号化
```

メッシュでは0012の共通規則でタグ値を生バイト列にする。`message`・`info` の文字列を中継時に正規化しない。イベント全体の32 KiB上限にCAP拡張も含む。

次はCAP拡張だけの説明例であり、変換投稿全体には本文・時刻・配送期限等が別にある。架空の公開情報を用いる。

```json
{
  "$type": "dev.oriom.mosimo.defs#cap12",
  "message": {
    "sender": "alerts@example.org",
    "identifier": "alert-001",
    "sent": "2026-10-17T12:00:00+09:00"
  },
  "status": "Actual",
  "msgType": "Alert",
  "scope": "Public",
  "references": [],
  "info": {
    "index": 0,
    "language": "ja",
    "categories": ["Safety"],
    "event": "避難情報",
    "urgency": "Immediate",
    "severity": "Severe",
    "certainty": "Observed",
    "effective": "2026-10-17T12:00:00+09:00",
    "expires": "2026-10-17T15:00:00+09:00",
    "senderName": "例市",
    "headline": "例地区の避難情報",
    "instruction": "例地区では指定避難所へ避難してください。",
    "areas": [{ "areaDesc": "例地区", "circles": ["35.0,139.0 2.5"] }]
  }
}
```

## 10. 残る意味上の判断

- 同一言語・対象重複の複数 `info` の拡張関係を、各投稿の単独解釈を維持してどう表すか。
- 情報単位一つでも32 KiBに収まらない場合の扱い。署名後の削除や指示の黙示的な切捨ては認めない。
- 本文の決定的生成、CAP固有の値が空の場合や組織別プロファイルの扱い、変換規則の識別と公開。
- 領域の丸め・近似区分・セル上限、有効期間の境界、参照から投稿への索引、配送同値キー。
