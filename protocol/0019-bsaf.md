# 0019: BSAF v1互換拡張と投稿の相互運用

状態: draft-00 — BSAF互換性を独立拡張として定義する方針に基づく仕様草案。タグ保持・フィルタ・出典・公開形式の境界を定める。再配信対象の選定、自動投入・公開、訂正削除の連携と正式Lexicon実装には未決事項を含む。

## 1. 適用範囲と互換性

Bluesky Structured Alert Feed（BSAF）の `bsaf:v1` を対象とする。採用資料は [B1] の固定リビジョンとし、`main` の将来の変更を自動採用しない。BSAFは防災専用ではなく、スポーツ・ニュース等を含む汎用のBot投稿規約である。

本書の互換性を次の三つに分ける。

| 経路 | 入出力 | 保持する責務 |
|---|---|---|
| 既存投稿の収集 | `app.bsky.feed.post` → 対応AppView | 原レコードを保持し、表示・検索・フィルタの索引を付ける。新投稿やメッシュ投入は不要 |
| 本プロトコルへの取り込み | BSAF投稿 → `dev.oriom.mosimo.post` + `bsafV1` | 取り込み者が新規投稿へ署名。元投稿の出典・タグ・言語を保持し、Nostr・BPv7へ配送できる |
| BSAF形式での公開 | 本プロトコルの投稿 + `bsafV1` → 別の `app.bsky.feed.post` | 公開権限を持つアカウントがBSAFタグ・言語・出典付きの別レコードを公開する |

独自Lexiconの投稿へ本拡張を付けただけでは、既存のBluesky/BSAFクライアントがそのレコードを収集・表示することは保証しない。既存クライアント向けの公開には、そのクライアントが扱う `app.bsky.feed.post` が必要である。一方、BSAFの既存投稿に本プロトコル固有の配送期限・署名・拡張を要求しない。

1件の本プロトコルの投稿は1レコード・1 commit・1 Nostrイベントである。BSAF向けの別レコード公開は、同じ署名付き投稿の形式変換や全面的なatproto→Nostr逆変換ではない。自動の再配信・公開の有効化は、本書の型の追加とは別の運用判断とする。

## 2. 識別と独立性

`$type` は `dev.oriom.mosimo.defs#bsafV1` とする。BSAFのコアタグと追加タグを、元の文字列配列として保持する。CAP・気象庁XML・`source`・`area` 等の拡張や、オンラインでのBot定義取得を、タグ保持と基本表示の前提にしない。

- `bsafV1`: BSAFタグ、言語、必要に応じた原BSAF投稿への参照を担当する。
- `source`: 取得URL・取得時刻・変換者・変換規則等の追跡を担当する。本拡張の `source:` タグとは別である。
- `area`: 解釈を確定できる地理的範囲だけを共通配送へ提供する。
- `validity`: 確定できる内容の有効期間であり、BSAFのイベント時刻から自動生成しない。
- CAP・気象庁等の形式拡張: 独立して取得・解釈できた原情報だけを担当する。BSAFの本文・タグから未掲載の原XML項目を復元したことにはしない。

BSAF型の追加は基本プロトコル・メッシュ符号化の版を変更しない。非対応端末は本文を読み、未知拡張を保持して通常の配送を行える。

## 3. データ型

以下はTypeScript風の説明用表記である。フィールドの具体化案であり、正式Lexicon JSONではない。

```ts
type BsafOriginalPost = {
  uri: string;       // DIDをauthorityとするat://.../app.bsky.feed.post/<rkey>
  cid: string;       // 取得した原レコードのCID
  createdAt: string; // 原レコードのcreatedAt。原文字列を保持
};

type BsafBotDefinitionReference = {
  url: string;
  retrievedAt?: Timestamp;
  sha256?: bytes;    // 取得したJSON文書の生バイト列に対するSHA-256、32 bytes
};

type BsafV1Extension = {
  $type: "dev.oriom.mosimo.defs#bsafV1";
  tags: string[];
  langs: string[];
  original?: BsafOriginalPost;
  botDefinition?: BsafBotDefinitionReference;
};
```

### 3.1 タグと言語

`tags` は `app.bsky.feed.post.tags` と同じ並び・文字列を保持する。`bsaf:v1` と5種類のコアタグに加え、未知の追加タグも含む。型内にパース結果の `type`・`value`・`time`・`target`・`source` を重複格納しない。

`langs` はBSAF本文の言語配列である。取り込みでは原投稿の `langs` を保持し、翻訳や再配信者の言語に置換しない。新規作成では本文の言語を指定する。本プロトコルのトップレベルに `tags`・`langs` を増やさない。

本プロファイルの新規作成・相互運用対象では、`bsaf:v1` 1件と、空でない各コア値を一つずつ持つ。追加タグを含めても、出力先のレコード仕様の上限を超えない。矛盾する複数の同名コアタグ、未知版・必要項目の欠落を、後勝ちや推測によって一組へ補修しない。AppViewはそのような原投稿も本文表示用に保持できるが、解釈可能なBSAF v1への変換成功とは扱わない。

タグは最初の `:` だけで名前と残りの値に分ける。例えば `time:2026-10-18T03:04:05Z` の値は `2026-10-18T03:04:05Z` 全体である。日時内の `:`、名称の改行、空白や記号で配列を再分割しない。大文字小文字・先頭ゼロ・日時の綴りを勝手に正規化しない。画面・ログ・通知先向けのエスケープや1行表示用の整形は派生表示で行い、元の値は変えない。

### 3.2 原投稿への参照

BSAF投稿を取り込んだ場合は `original` を含める。著者はDIDをauthorityとする `uri` から得られるため、別の `authorDid` を重複格納しない。ハンドル表記のURIを取得した場合、取り込み時にDIDを確定して原レコードの場所と対応付ける。URIの場所が同じでもCIDが違えば別の内容として扱う。

原BSAF投稿を経由せず作成した場合は `original` を省略する。架空のBluesky投稿・CIDや、将来公開する予定のURIを入れない。この場合、BSAF上の発信者に対応するのは本プロトコルの投稿著者であり、機関の認証は別の問題である。

参照とCIDは原著者の署名そのものではなく、参照を含む投稿へのNostr署名も取り込み者の署名である。AppViewからの取得だけで原リポジトリ署名・包含を確認したと表示しない。原著者DIDの主張、取得内容、認証済みの帰属を区別し、通常中継に原Botの署名証明の同梱を要求しない。

### 3.3 Bot定義の参照

`botDefinition` は、そのBSAFメタデータを解釈するBot定義への任意の参照である。取り込みの場合は原Botの定義、新規作成の場合は発信者が管理する定義に対応させる。別Botの定義を流用して、そのBotとして発信したことにはしない。

`retrievedAt` と `sha256` は取り込み側が実際に取得した版を追跡するための任意項目であり、Bot定義自身の `updated_at` や署名ではない。ハッシュは取得バイト列全体に対する値とし、JSONキーの並べ替え等をしてから計算した値と混同しない。Bot定義の全JSONを投稿ごとに同梱しない。

取得済みの定義・ラベルはキャッシュまたはアプリ同梱で利用できる。オフライン時の表示・中継のために `self_url` の取得を必須にしない。URLだけで機関の認証や取得先の安全性を認めず、取得する実装はリダイレクト・サイズ・取得頻度・接続先等をローカル方針で制限する。

## 4. BSAFコアタグの対応

| 原タグ | 解釈・用途 | 自動変換しないもの |
|---|---|---|
| `bsaf:v1` | BSAF規約版の識別 | 本プロトコルの基本版・Nostrのkind |
| `type:` | Botが定義する情報種別 | タグの存在だけによる公的警報の認定 |
| `value:` | Botが定義する規模・程度の離散値 | 数値比較、配送優先権、CAPのseverityや観測／予測震度への一律変換 |
| `time:` | 元のソースイベントのUTC時刻 | 原Botの投稿時刻、取り込み時刻、有効期間、配送期限 |
| `target:` | Bot定義の対象コード。地理以外の対象もある | Geohash、行政区域、GPS位置、厳密な影響範囲 |
| `source:` | 原情報源の識別文字列 | 発信BotのDID、機関署名、更新取消の権限 |

本プロトコルから新規にBSAFメタデータを作る場合は、そのBotの公開定義に従い、同じソースを扱う既存Botの `value`・`target` を尊重する [B1]。`5+` を `震度5強`、`jp-kanto` を独自の別名へ置換しない。表示ラベルと機械値は別にする。

`source:jma` だけから `value:5+` が予測震度か観測震度かを確定しない。気象庁のマグニチュード表示規則やPLUM法の時刻解釈をBSAFタグへ無条件に適用しない。複数の地域投稿を同じ広域 `target` に対応させる場合、その値は検索・表示上の広域分類であって、各投稿が広域全体の詳細を持つ意味ではない。

## 5. 経路ごとの処理

### 5.1 既存BSAF投稿のAppView収集

原 `app.bsky.feed.post`、DID、atURI、CID、取得経路・取得時刻を保持し、BSAFの版とタグを派生索引へ対応付ける。原レコードを独自Lexiconへ書き換えない。Bot定義の `bot.did` と原投稿著者との対応を確認できる範囲で、そのBot用のフィルタUIを作る。ハンドルの一致だけで恒久的な同一著者としない。

`type`・`value`・`target` の選択肢はBotごとに扱い、同じ文字列が全Botで同じ意味とは限らない。未登録Bot、未知の値、不完全なタグ、Bot定義が取得できない場合に本文を黙って捨てず、未解釈の値と出典を表示できるようにする。値が一意に解釈できない場合は、構造化フィルタや重複折りたたみの適用を保留する。

### 5.2 BSAFから本プロトコルへの取り込み（経路案）

公開再配布条件と運用者が選んだ対象Bot・情報種別を満たす投稿を取り込み者が取得し、新しい基本投稿を生成する。BSAFタグがある全投稿を無条件にメッシュ投入する既定動作にはしない。既存のAppView収集だけの設定から自動的に再配信を有効化しない。対象選定と自動投入の採否は §11 の判断として残す。これは各取り込み側の運用方針であり、中央のBot登録や、第三者が拡張を作るための承認を要求するものではない。

- 原レコードは取り込み側に保持する。
- `bsafV1.tags`・`langs` は原値、`original` は原URI・CID・原 `createdAt` とする。
- 基本本文は元の文章と出典表示を保持し、原投稿著者・参照・再配信であることを人が読める形で添える。原Botや機関として署名したとの表示はしない。
- 新投稿の `createdAt` は変換投稿の作成時刻、`deliveryExpiresAt` は取り込み時に運用方針により確定する。古いイベントを再取得しただけで配送期間を繰り返し延ばさない。
- `source` を併用する場合、原投稿参照と矛盾する著者・取得内容へ置換しない。
- 取り込み者の鍵でレコードとcommit・Nostrイベントを生成し、通常のCBOR・BPv7経路へ流す。

BSAFだけを根拠に、元のCAP・JMA XMLや機関による認可を復元した拡張を捏造しない。Botが作った要約の原情報にない詳細を補わない。原投稿の添付・返信・引用・ラベル等が意味に重要な場合、本拡張のタグと本文だけで十分と扱わず、明示的な対応または取り込み保留とする。画像・動画の本体は配送しない。32 KiBに収めるため重要な本文・BSAFのコア値・原投稿参照を黙って削らない。

### 5.3 本プロトコルでの新規作成

投稿者は単独で読める基本本文へ出典を明記し、BSAFのタグ・言語を本拡張に保持できる。原イベント時刻が不明なら投稿時刻を `time:` として補わず、そのままBSAF v1互換と宣言しない。`original` は含めない。

CAP・JMA等の独立した拡張と併用できるが、BSAFの値をそこから導出する規則・Bot定義を必要とする。全国最大震度を地域別の値として使う、予測値を観測値として使う、未知の対象に架空の `target` を割り当てるといった単純変換はしない。本文で省略を明示したJMAの地域要約をBSAFに公開する場合も、その要約を全地域の完全な原電文と表示しない。

### 5.4 BSAF形式での別途公開（経路案）

公開権限のある著者または中継Botが、別の `app.bsky.feed.post` を作成する。`tags`・`langs` は互換な値を使い、本文末尾の `（出典：...）`、BSAF Bot定義の公開等のBSAF側の要件を満たす。取り込み者が公開する場合はその取り込み者のアカウントの投稿であり、元Botのアカウント・署名・CIDを再利用しない。自分のBotとしての公開定義と原Botの定義を区別する。

Blueskyの本文上限に収まらない場合は、重要な条件・指示・出典を失わない別途の要約規則が必要である。文字数だけで末尾を切り捨てたり、独自Lexiconをそのまま投稿できるとみなしたりしない。元本文を編集するときはfacetsのバイト位置を流用しない。添付・返信関係・Labels・facets等の完全復元は保証しない。

別途公開されたレコードは新しいURI・CIDと履歴を持ち、本プロトコルの元投稿とは別に管理する。公開先へ本プロトコルのNostr署名がそのまま引き継がれるとは扱わない。既存Botが自動フォロー・登録されている場合でも、別の中継Botが既存利用者に自動的に購読されるとは保証しない。

### 5.5 循環再配信の抑制

取り込み側は `(original.uri, original.cid)` と生成済みの本プロトコル投稿の対応を記録し、同じ原投稿の再取得だけで新しい転載を繰り返さない。BSAFへの公開側も、元の本プロトコル投稿と公開済みURI・CIDの対応を記録し、再試行で別投稿を増殖させない。記録保持・失敗後の再試行の詳細は未決定である。

自分の公開アカウント・公開済みレコードを再取り込み対象から除き、**取り込み済みBSAF投稿を別BSAF投稿へ自動再公開する経路は初版では有効化しない案**とする。任意の第三者がコピーした投稿まで完全に追跡して止める保証はなく、本文一致だけで別の原投稿を破棄しない。BSAFの予備タグへ未定義の必須ループ制御タグを勝手に挿入しない。

## 6. フィルタ・重複表示と配送

BSAFの `type + value + time + target` が異なるBot間で一致した場合の折りたたみは表示用の規則である。元の著者・URI・CID・出典・各本文を残し、利用者が展開して確認できるようにする。原Botが同じで変換者だけ異なる転載を、「別のBotからの独立した報告」として件数を水増ししない。

この組は原電文ID・ハッシュ・真正性を含まないため、Nostrイベントの重複排除、配送同値、内容の訂正取消、原投稿削除のキーへ流用しない。同じ広域タグを持つ別地域の詳細も折りたたまれ得るため、折りたたみを情報の破棄や完全な意味同値の判定としない。

フィルタは閲覧者の関心に合わせるためのものであり、公的な優先権ではない。`value:7`・`warning` 等の自己申告で保存枠・帯域・即時通知の権限を得ない。BSAFに非対応でも、通常のNostr署名・期限・資源上限に従って中継できる。

## 7. 地域・時刻・信頼

`target` を共通 `area` へ変換するのは、Bot定義と別途のコード体系・境界対応を解決でき、意味が地理的範囲に一致する場合だけとする。`jp-kanto` から都県の範囲や境界を文字列の見た目で創作しない。元領域全体を覆う近似は0004に従い、不明なら `area` を省略して対象文字列を残す。スポーツチーム等の対象から地理領域を生成しない。

`time:` は原イベント時刻、`original.createdAt` は原Botの作成時刻、基本投稿の `createdAt` は変換投稿の作成時刻である。いずれも配送期限とは異なり、BSAF v1自体に共通の有効終了・メッシュ配送期限があるとは扱わない。

`source:`・Bot定義・原投稿参照だけでは、公式機関の認証や他投稿を置換する権限を得ない。BSAFに載った取消らしい文章を見て、同じ `type/time/target` の全投稿の拡散を止めない。公的な置換には0009の事前ルート・権限・原情報への対応を別途必要とする。

## 8. 訂正・削除

同じatURIで別CIDの内容を取得しても、既存の署名付き転載は書き換えず、訂正の新投稿・参照を別途扱う。取得順やCIDの辞書順だけで最新版・置換関係を確定しない。BSAF v1のコアタグ自体に一般的な更新・取消参照の形式はないため、その形式があると仮定しない。

原投稿が取得できないことを、削除・機関の取消・危険の解消の証拠としない。原Botによる削除と、再配信者の本プロトコル投稿のNIP-09削除・atproto削除は別の操作である。元Botの削除を根拠に再配信者の鍵で元Botの署名を作ることはできない。自動追随の通知形式・認可・保存期限・対象範囲は未決定であり、単なるURLの取得失敗から削除要求を発行しない。

## 9. データの運搬と例

Nostrのタグ名は `mosimo.oriom.dev:ext:dev.oriom.mosimo.defs#bsafV1` とし、`$type` 以外の全フィールドをatproto CBOR／通常Base64・paddingなしで運ぶ。メッシュでは0012の共通変換に従って値を生バイト列にする。BSAFの `type:` 等を、意味の異なるNostr標準タグや検索目的だけの別名タグへ重複投影しない。

以下は、原BSAF投稿を経由せず本プロトコルで新規作成する際の拡張の例である。本文には地震情報と「（出典：気象庁）」等の出典を別途含める。例示の値は実際の災害通知ではない。

```json
{
  "$type": "dev.oriom.mosimo.defs#bsafV1",
  "tags": [
    "bsaf:v1",
    "type:earthquake",
    "value:5+",
    "time:2026-10-18T03:00:00Z",
    "target:jp-kanto",
    "source:jma"
  ],
  "langs": ["ja"]
}
```

取り込みではこの型に `original` を追加し、基本本文に原投稿の帰属を付ける。タグ・言語と原投稿の参照だけを運ぶもので、元の `app.bsky.feed.post` 全体や元リポジトリの署名を完全に復元できるとはしない。32 KiB上限は本文・本拡張・commit等を含むイベント全体に適用する。

### 9.1 外部レコードの上限

参照した公式 `app.bsky.feed.post` Lexicon [A1] は、本文が最大300 graphemes・3,000 bytes、`langs` が最大3要素、`tags` が最大8要素、各タグが最大64 graphemes・640 bytesである。BSAF文書の「合計640バイト」という説明とは区別し、公式レコードの各項目の制約を本プロトコル全体の上限と混同しない。BSAF向けの新規出力では、互換性のためタグ総量も640 UTF-8 bytes以内とする保守的なプロファイル案とする。

原投稿がこの保守的総量を超えることだけで、公式Lexicon違反と断定しない。受信した原タグを削ってBSAF互換へ補修せず、そのままの保持・非互換の表示と、互換な新規公開の可否を分ける。採用する外部Lexiconの固定版と変更追随は §11 に残す。

## 10. 部分実装

- 基本対応端末は、本文と通常の配送期限を扱い、未知拡張を保持する。
- BSAF対応端末は、本拡張のタグ・言語を読み、取得済みBot定義で表示・フィルタできる。原Botの帰属を確認できない転載は、確認済みBot本人の投稿とは区別する。
- 対応AppViewは既存BSAFレコードと本拡張付き投稿を併置し、同じ原URI・CIDの転載は関係を表示できる。ただし、主張だけで原投稿と内容同一・認証済みと断定しない。
- BSAF公開ブリッジは別の権限と出力規則を持つ任意の機能であり、すべての中継端末へ実装を要求しない。

## 11. 残る判断

- BSAF→本プロトコルの再配信対象。登録済みの防災Bot・対象種別への明示的な有効化を基本とする案と、より広い自動探索の採否。
- BSAF向け別途公開の自動化、長い本文の安全な要約、Bot定義・出典表示、元投稿との対応記録の保持。
- CAP・JMA等からBSAFの `type/value/time/target/source` を生成するソース別マッピングと、既存Bot定義の固定版。
- Bot定義の発見・更新・失効・配布とオフラインキャッシュ。定義更新を過去の署名付きタグの変更としない。
- 原投稿の更新削除への追随、ループ抑制記録の保持・再試行・停止条件。
- 外部Lexiconの固定版、本拡張の正式Lexicon、配列・文字列・Bot定義取得の資源上限。
