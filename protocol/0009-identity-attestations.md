# 0009: 署名チェーンによる発信者の身元証明

状態: draft-00（信頼モデル・拡張配送・委任権限の制限は合意済み。証明書形式・範囲の符号化・失効等は未決定）

## 1. 目的

自治体等の名称と公開鍵の対応を、信頼するルート公開鍵からの署名チェーンで確認する。単なる表示名や自己申告の DID 一覧だけを身元証明とはしない。確認した身元は、元の注釈発信者への信頼判断に利用する。

## 2. 信頼の起点

アプリは既定のルート公開鍵を同梱できる。利用者が信頼するルート公開鍵を選択することもできる。全実装が世界共通の単一ルートを必須にする方式ではない。検証側に配布するのは公開鍵であり、ルート秘密鍵をアプリへ配布するものではない。

受信した証明チェーンの末端や同梱ルートを、それだけで新しい信頼の起点として自動採用しない。検証経路は、あらかじめアプリ・利用者が信頼すると決めたルートへ到達する必要がある。ルートの初期配布・追加・更新・削除・失効の具体方式と UI は未決定である。

## 3. 多段の署名チェーン

ルート鍵の保持者が、自治体名と公開鍵の対応を署名して証明する。中間の証明者を介した多段の署名チェーンも扱えるようにする。

```text
信頼するルート公開鍵
  → 中間の証明者への署名付き証明
  → 自治体等の名称と公開鍵への署名付き証明
  → その鍵に対応する元の署名済み投稿・注釈
```

各段の署名、証明のつながり、証明対象の鍵と投稿・注釈の署名鍵の対応を検証する必要がある。

末端の発信端末への証明は、組織名・発信者 DID・atproto リポジトリ署名公開鍵を結び付ける。Nostr 用公開鍵は同じ証明へ重複して載せることを要求せず、合意済みの相互署名付き鍵対応宣言を通じて結び付ける。Nostr 投稿を扱う際は、証明対象の atproto 鍵と宣言内の鍵が一致し、両方の鍵による宣言の署名と、対象 Nostr イベントの署名が正しいことを確認する。

証明対象の DID と、検証に用いた DID 情報の署名公開鍵との対応も確認する。初期 PLC 操作・更新履歴・キャッシュのどの状態に基づく検証か、現在の鍵や失効状態まで確認できたかは区別する。atproto 署名鍵を変更した場合は証明の再発行等が必要となり、その手順と過去投稿への扱いは今後定義する。

この末端証明の形式方針は、ルート・中間の証明者や組織管理用の鍵まで発信端末の DID・投稿用鍵と同一の構成に限定するものではない。

### 3.1 証明権限と再委任の制限

身元を証明された投稿用の鍵、他の鍵の身元を証明できる鍵、その証明権限を再委任できる鍵を区別する。投稿者としての身元証明を受けただけで、他者を証明する権限や再委任権限を得るとは扱わない。

中間の証明者には、証明できる名称・組織・用途等の範囲と再委任の可否を制限できるようにする。下位への証明・委任で、上位から与えられた権限の範囲を拡大してはならない。署名が数学的に検証できるだけで証明経路を有効とせず、各段で権限・範囲の適合も検証する。

例えば、管内の自治体を証明できる鍵から、自組織の発信端末だけを証明できる鍵へ委任し、その発信端末には証明・再委任権限を与えない構成を表現できるようにする。この例は国・都道府県・市町村という階層を全世界に強制するものではない。

多段対応は無制限の探索・ネストを意味しない。組織・名称・用途の識別と範囲の包含判定、権限の符号化、経路長、循環、複数経路、証明書の識別・版管理等の具体規則は今後定義する。署名フォーマット・証明書スキーマ・アルゴリズムはまだ選定していない。

## 4. 拡張ブロックとしての配送

身元証明を提示する場合、署名チェーンを本プロトコルの論理的な拡張ブロックとして含める。この「ブロック」は BPv7 extension block のみに格納することを意味しない。メッシュ・Nostr・atproto の対応するデータ表現で証明を利用できる具体的な配置・符号化を今後定義する。

未知の拡張を保持・中継する既存方針に従う。身元証明に未対応、証明がない、または検証に必要な情報が不足していても、通常の著者署名による本文の検証・表示とは区別する。身元を未確認のまま、自治体の検証済み公式発信と表示しない。

チェーンの検証には各証明自身の署名を用いる。配送者・集約サービスの署名だけで、証明対象の機関や本人の署名が成立したとは扱わない。証明チェーンと対象投稿の結び付け、改変・差し替え・リプレイ対策、未知拡張としての保存規則との対応は具体化が必要である。

## 5. Label と信頼判断

標準 Label の `src` は集約サービスの DID とし、自治体本人の DID に偽装しない。Label の根拠である元の注釈、その著者署名、身元証明チェーンを確認できるようにする。確認済み自治体の誤情報指摘を強い判断材料として扱えるが、署名チェーンは投稿内容の真実性や一律の確率を保証しない。

ルートを信頼する設定、リレー候補一覧の発行者への信頼、取り込みサーバーへの信頼、Labeler への信頼はそれぞれ役割が異なる。同じ鍵・運用者を採用した場合でも、一つの役割への信頼から他の全権限を自動的に導かない。

## 6. オフライン時と未決事項

証明チェーンと信頼の起点があればオフラインで署名を検証できる構成を目指す。ただし現在の未失効や鍵の安全性まで常に確認できるわけではない。失効情報、期限、時計ずれ、証明鍵・投稿鍵の更新、過去投稿の検証、侵害後の取り扱いを定義する必要がある。

初期の身元確認を固定 DID 一覧だけで管理する案の代わりに、本書のルート公開鍵と署名チェーンを採用する。特定の既存 PKI／証明書形式を採用したものではなく、現時点で証明発行・検証の実装や相互運用試験は行っていない。
