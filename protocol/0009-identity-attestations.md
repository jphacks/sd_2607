# 0009: 署名チェーンによる発信者の身元証明

状態: draft-01（信頼モデルは合意済み。BSAF importer向けの証明書・binding・失効・検証手順は [0020: experimental wire-v1](0020-wire-v1.md) に確定。アプリアカウント証明の論理構造を追加。一般の公的発信・更新取消・アプリアカウント証明の権限形式は引き続き未決定）

## 1. 目的

自治体等の名称と公開鍵の対応を、信頼するルート公開鍵からの署名チェーンで確認する。単なる表示名や自己申告の DID 一覧だけを身元証明とはしない。確認した身元は、元の注釈発信者への信頼判断と、公的情報の更新・取消による旧版拡散停止の認可判断に利用する。

## 2. 信頼の起点

各ユーザーのクライアントは、公的情報の発信元を確認するための信頼するルート公開鍵を平時に保持しておく。アプリによる既定鍵の同梱や、利用者による事前の選択・設定で用意できる。全実装が世界共通の単一ルートを必須にする方式ではない。検証側に配布するのは公開鍵であり、ルート秘密鍵をアプリへ配布するものではない。

ルート鍵は用途別に用意できる。自治体の身元、取り込み・変換配信者の身元と権限、アプリ内のアカウントと鍵の対応など、何を証明する起点として信頼するかを設定する。アプリ開発者が既定値を用意でき、利用者も選択・設定できる。一つの用途で採用したルートから、他の用途の権限を自動的に導かない。

受信した証明チェーンの末端や同梱ルートを、それだけで新しい信頼の起点として自動採用しない。検証経路は、あらかじめアプリ・利用者が信頼すると決めたルートへ到達する必要がある。ルートの初期配布・追加・更新・削除の具体方式とUIは未決定である。0020では事前設定rootに対するCRL snapshotとroot key失効のstickyな扱いを定義するが、侵害rootからの安全な回復・新root導入は帯域外の明示的な信頼操作を必要とする。

## 3. 多段の署名チェーン

ルート鍵の保持者が、自治体名と公開鍵の対応を署名して証明する。中間の証明者を介した多段の署名チェーンも扱えるようにする。

```text
信頼するルート公開鍵
  → 中間の証明者への署名付き証明
  → 自治体等の名称と公開鍵への署名付き証明
  → その鍵に対応する元の署名済み投稿・注釈
```

各段の署名、証明のつながり、証明対象の鍵と投稿・注釈の署名鍵の対応を検証する必要がある。

末端の発信端末への証明は、組織名・発信者 DID・atproto リポジトリ署名公開鍵を結び付ける。Nostr 用公開鍵は同じ証明へ重複して載せることを要求せず、合意済みの相互署名付き鍵対応宣言を通じて結び付ける。Nostr 投稿を扱う際は、証明対象の DID・atproto 鍵が宣言内の DID・鍵とそれぞれ一致し、両方の鍵による宣言の署名と、対象 Nostr イベントの署名が正しいことを確認する。

証明対象の DID と、検証に用いた DID 情報の署名公開鍵との対応も確認する。初期 PLC 操作・更新履歴・キャッシュのどの状態に基づく検証か、現在の鍵や失効状態まで確認できたかは区別する。atproto 署名鍵を変更した場合は証明の再発行等が必要となり、その手順と過去投稿への扱いは今後定義する。

この末端証明の形式方針は、ルート・中間の証明者や組織管理用の鍵まで発信端末の DID・投稿用鍵と同一の構成に限定するものではない。

### 3.1 証明権限と再委任の制限

身元を証明された投稿用の鍵、他の鍵の身元を証明できる鍵、その証明権限を再委任できる鍵を区別する。投稿者としての身元証明を受けただけで、他者を証明する権限や再委任権限を得るとは扱わない。

中間の証明者には、証明できる名称・組織・用途等の範囲と再委任の可否を制限できるようにする。下位への証明・委任で、上位から与えられた権限の範囲を拡大してはならない。署名が数学的に検証できるだけで証明経路を有効とせず、各段で権限・範囲の適合も検証する。

例えば、管内の自治体を証明できる鍵から、自組織の発信端末だけを証明できる鍵へ委任し、その発信端末には証明・再委任権限を与えない構成を表現できるようにする。この例は国・都道府県・市町村という階層を全世界に強制するものではない。

多段対応は無制限の探索・ネストを意味しない。[0020 §2–3](0020-wire-v1.md) はBSAF importer向けにsecp256k1 low-S ECDSA証明、最大4証明の単一経路、exact-matchの組織IDとBot DID/type部分集合、issuer/importer roleと再委任を定義する。初期実装はroot→leafだけでもよく、中間証明を未検証でroot扱いしてはならない。一般の公的発信・更新取消等へこのimport-only permissionを拡大してはならない。

### 3.2 アプリアカウントと公開鍵の対応の証明

本プロトコルを実装したアプリの開発元は、自ら管理するアカウントIDと投稿用公開鍵の対応に署名できる。この証明を既存の `identity` 拡張（`dev.oriom.mosimo.defs#identity`）で扱う。自治体の身元証明とは別の用途であり、新たな基本投稿型や配送方式は追加しない。

```text
アカウント証明用に信頼したアプリ開発元のルート公開鍵
  → 必要に応じて、そのアプリのアカウント証明者への委任
  → アプリ識別子・アカウントID・DID・atproto公開鍵への署名付き証明
  → その鍵に対応する投稿の署名
```

末端証明は、少なくとも次の情報を一体として署名対象に含める。これは論理構造の定義であり、フィールド名や wire スキーマの確定ではない。

| 情報 | 意味・制約 |
|---|---|
| 証明の用途 | アプリアカウントと鍵の対応。自治体の身元や公的情報の更新権限には転用しない |
| アプリ識別子 | 表示名だけでなく、開発元と信頼設定に結び付く安定した識別子。具体形式は未決定 |
| アカウントID | そのアプリ内の安定したID。アプリ識別子と組にして扱い、変更可能な表示名で代用しない |
| 発信者DID・atprotoリポジトリ署名公開鍵 | §3 の末端証明と同じ鍵の結び付けを使う。Nostr鍵は相互署名付き鍵対応宣言で確認する |
| 発行者と証明権限 | 信頼するルートから、このアプリのアカウントを証明する権限が続いていること |
| 有効期間 | §6 に従い、署名の検証と期限・失効の確認状態を分ける |

開発元は、当該アカウントの認証と対象秘密鍵の所持を確認してから証明を発行する。具体的な認証・所持確認手順は未決定であり、任意の申告IDと鍵に無条件で署名するものではない。署名対象には用途とアプリの識別を含め、別アプリや別用途への証明の流用を防ぐ。

受信側は、発行者の署名・委任範囲・有効性を検証し、証明対象のDID・鍵と投稿者の対応を確認する。これにより確認できるのは「この開発元が、このアプリのこのアカウントに結び付けた鍵による発信」であり、利用者の実名・一人一アカウント・内容の真実性を保証しない。鍵やアカウントの共有・侵害による利用者の区別も保証しない。

アカウントの削除・再割当て、鍵の更新、証明の失効と過去投稿の評価は今後定義する。同一IDの再割当て後も、古い証明を現在の所有者の証明として扱わない。証明の提示は任意であり、アカウントIDの公開と投稿間の関連付けが可能になることを発信者に示す。省略・未対応・検証不能の場合はアプリアカウント未確認として扱い、通常の本文表示・著者署名の検証・中継を妨げない。

## 4. 拡張ブロックとしての配送

身元証明を提示する場合、署名チェーンを本プロトコルの論理的な拡張ブロックとして含める。この「ブロック」は BPv7 extension block のみに格納することを意味しない。[0020 §5](0020-wire-v1.md) は `dev.oriom.mosimo.defs#identity` の `version`・`chain`・`binding` を定義し、既存の自己完結拡張タグとatproto extensions、メッシュ共通変換で運ぶ。

未知の拡張を保持・中継する既存方針に従う。身元証明に未対応、証明がない、または検証に必要な情報が不足していても、通常の著者署名による本文の検証・表示とは区別する。身元を未確認のまま、自治体の検証済み公式発信と表示しない。

チェーンの検証には各証明自身の署名を用いる。配送者・集約サービスの署名だけで、証明対象の機関や本人の署名が成立したとは扱わない。0020ではleafのDID/atproto key、相互署名binding、commit.did/署名、Nostr pubkey/署名を照合し、root-signed snapshotと受信時刻で期限・失効・rollbackを確認する。転載者の認可は原Bot本人の署名を証明しない。

## 5. Label と信頼判断

表示では、自治体自身が署名した情報、既存の公的情報を取り込んで変換配信者が署名した情報、アプリアカウントとの対応だけが確認できた投稿を区別する。変換配信者の身元が確認できても、原発表機関自身の署名があるとは扱わない。信頼度表示は、検証できた役割・用途・権限と確認状態を根拠に各クライアントが決め、一律の点数や全アプリ共通の信頼順位は定めない。

標準 Label の `src` は集約サービスの DID とし、自治体本人の DID に偽装しない。Label の根拠である元の注釈、その著者署名、身元証明チェーンを確認できるようにする。確認済み自治体の誤情報指摘を強い判断材料として扱えるが、署名チェーンは投稿内容の真実性や一律の確率を保証しない。

ルートを信頼する設定、リレー候補一覧の発行者への信頼、取り込みサーバーへの信頼、Labeler への信頼はそれぞれ役割が異なる。同じ鍵・運用者を採用した場合でも、一つの役割への信頼から他の全権限を自動的に導かない。

### 5.1 公的情報の更新・取消の認可（合意済み）

公的情報を置換する更新・取消は、事前に保持した信頼するルートへつながる署名チェーンを根拠として採用する。イベント署名の正しさ、チェーンで証明された発信元、対象情報を発信・更新できる用途と範囲を対応付ける。ある組織の鍵として証明されたことだけで、別組織の情報を置き換える権限を得るとは扱わない。権限は各段の委任範囲を超えて拡大しない。

取り込みサーバーを利用する場合も、単に受信者の取り込み先リストに載っていることだけでは公的情報を置換する権限を与えない。取り込み・変換した対象情報の更新を伝える発信元として、ルートからの証明と委任範囲が対応している必要がある。取り込みサーバーの署名を原発表機関自身の署名と表示しない。

チェーンと対象 Nostr イベントの署名鍵は §3 の末端証明・相互署名付き鍵対応宣言で結び付ける。通常投稿の表示・中継にこれらの毎回の同梱やDID認証を追加要求するものではない。情報が不足して認可を確定できない場合、更新の主張を保持できるが、他の投稿の新たな拡散を停止する根拠にはしない。有効期間・失効情報の確認状態は §6 に従い、確認できた範囲を越えて認可済みとは扱わない。

認可条件の符号化、原形式の発信元識別子と証明された範囲の対応、オフライン時に採用できる時刻・失効情報の条件は未決定である。ルートへのチェーンが必要という信頼モデルの合意だけで、証明書のwire形式まで完成したとはしない。

## 6. オフライン時と未決事項

発行する身元証明には有効期間を設け、期限切れの証明を現在有効な身元証明とは扱わない。0020の証明はUTC秒精度Timestamp、最大366日、`notBefore <= now < notAfter` とする。root署名の完全CRL snapshotは最大1時間有効、sequenceと失効集合を単調に永続保持し、時計・fresh snapshotが確認できない新規BSAF ingressはfail closedとする。あらかじめ信頼した裸のルート公開鍵の設定と、そこから発行する署名付き証明の有効期間は区別する。

検証状態は少なくとも、チェーンの署名・権限の検証、利用可能な時刻による有効期間の確認、失効情報の確認とその取得時点、情報不足による判定不能を区別する。署名が正しいだけで、期限・失効まで確認済みとは扱わない。取得した失効情報だけで、それ以降の未失効を保証するものでもない。

証明チェーンと信頼の起点があればオフラインで署名を検証できる構成を目指す。ただし現在の未失効や鍵の安全性まで常に確認できるわけではない。時計や失効情報が不足する場合、その未確認状態を隠して現在有効な公式発信者として確認済みと表示しない。配送期限の実施をベストエフォートとした方針は、身元証明の有効性確認まで省略してよいという意味ではない。

証明の期限切れや確認不能は、投稿の著者署名そのものの無効化・削除とは区別する。失効情報の形式・配送・鮮度とBSAF ingressの受信時点評価は0020に従う。過去投稿の当時の公式認証、信頼時計のプラットフォーム実装、本番rootの帯域外更新・侵害対応は今後定義する。

初期の身元確認を固定 DID 一覧だけで管理する案の代わりに、本書のルート公開鍵と署名チェーンを採用する。特定の既存PKIを採用するものではない。0020でexperimental wire-v1の実装契約を定めたが、この文書更新だけで証明発行・検証の実装や相互運用試験の完了を宣言しない。
