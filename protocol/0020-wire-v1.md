# 0020: Experimental wire-v1 — BSAF importer identity and verified ingress

状態: **experimental wire-v1、実装用契約（2026-10-19）**。MUST / MUST NOT / SHOULD は本プロファイルの要件。正式 Lexicon の公開・本番 PKI・相互運用試験の完了を意味しない。基本版1・メッシュ版1は変更しない。本書は0009の具体化であり、以下で確定した形式について従来の「未決定」記述に優先する。初期実装は **root → leaf** のみでもよいが、多段を未検証のまま受理してはならない。

## 1. 固定した経路と信頼の境界

```text
事前設定された root 公開鍵
  → importer の DID + atproto 公開鍵を証明する leaf certificate
  → 両鍵署名の binding により Nostr 公開鍵へ接続
  → server が BSAF を取得し、新しい Mosimo record / commit / kind-1 event を署名
  → Mosimo Nostr relay
  → Android / ESP32 が元の event を取得・独立検証
  → ローカルで許可したものだけを新たに mesh へ投入
```

- root は証明専用の鍵。leaf は **組織名 + DID + atproto repository signing key** を証明する。leaf に Nostr key を重複格納しない。binding と event signature がその対応を示す。
- trust anchor はアプリ・運用者が事前設定する。証明、NIP-11、取得した snapshot、リレーのURLから root を自動追加しない。秘密鍵は発行者のみが保有する。
- 本プロファイルの唯一の permission は **`bsaf-import`**。指定 Bot DID / `type:` の転載を許可するだけであり、原Bot・発表機関本人の署名、内容の真実性、訂正取消による他投稿の拡散停止、Labeler、PDS参加、root追加の権限は与えない。
- server と receiver の双方に明示的な `(botDid, type)` 選択が必要。証明のscopeはその選択を自動で有効化しない。初期値は空。受信者が一つの許可済み importer を信頼する構成でよいが、信頼した一者の侵害で偽の転載が成立し得る。
- Nostr署名付き本文の閲覧・一般のローカル中継と、**インターネットからの認可済みBSAF自動投入**は別の判定。後者は §7 の fail-closed 条件を満たす必要がある。認可失敗した転載を「通常投稿」へ分類し直して同じ自動ingressを通すfallbackは禁止する。

## 2. 共通符号化・署名

### 2.1 Canonical CBOR（Node / Kotlin / ESP32 共通）

`C(x)` は既存 Android `CanonicalCbor.encode` と同じ atproto deterministic CBOR とする。

- definite lengths、整数と長さは最短表現、map key は text のみ。
- key 順は **UTF-8 byte length 昇順、その後 unsigned UTF-8 bytes の辞書順**。単なる JavaScript のキーソートや一般の JSON canonicalization ではない。
- text は正しい UTF-8。Unicode正規化を行わない。float、indefinite length、重複map key、未知CBOR tag、末尾データを拒否する。既存commitのCID linkには既存のtag42を使用するが、本書の新しい署名オブジェクトではCBOR tagを使用しない。
- 全整数は `0..9007199254740991` の整数。日時フィールドは特記しない限り既存の UTC `Timestamp` 文字列。Unix秒の整数へ変更しない。新規certificate/snapshotは `YYYY-MM-DDTHH:mm:ssZ` の秒精度、実在する日時、1970年以降を使用する。
- 署名オブジェクトは下記の **exact fields** のみ。未知フィールド・nullによる省略代用は、そのv1の意味を検証する実装では拒否する。未知拡張の不透明な保持は引き続き可能。非互換変更は新しい拡張 `$type` を使う。
- CBORは再符号化一致を確認する。JSONで運ぶ場合も重複key、不正UTF-8、非整数・safe integer範囲外を拒否し、型検証後 `C(x)` を生成する。JSON自体は署名対象ではない。

`H(x) = SHA-256(C(x))`。certificate と snapshot の `body.type` が署名用途を分離する。追加prefix、二重hash、JSON文字列への署名は **しない**。

### 2.2 鍵・署名・ID

| 値 | 正確な表現 |
|---|---|
| root / intermediate / atproto public key | SEC1 compressed secp256k1、33 bytes、02/03 prefix、**66文字小文字hex string**。曲線上の有効点を確認 |
| Nostr public key | BIP-340 x-only、32 bytes、64文字小文字hex string。有効点を確認 |
| certificate / snapshot の `sig` | secp256k1 ECDSA、`H(body)`への署名、compact `r || s` 64 bytes、**128文字小文字hex string**。DERでない。`1 <= r < n`, `1 <= s <= n/2`、high-Sを拒否 |
| `rootId` | `hex(SHA-256(unhex(rootPubkey)))`、64文字。CBOR化したkeyやhex文字列をhashしない |
| `certId` | `hex(H(certificate.body))`、64文字。署名はIDに含めない |
| atproto commit | 既存0012どおり、`sig`はCBOR bytesの64-byte low-S ECDSA。`sig`を除いたcommitの `H` に署名 |
| Nostr event | NIP-01 event ID・BIP-340 Schnorr、そのまま。上記のcertificate署名方式と混同しない |

同じcertificate bodyの再署名でもcertIdは変わらない。発行内容を変える場合は `serial` も変更する。証明署名者は常に `body.issuerPubkey`、snapshot署名者は事前設定rootである。

## 3. Certificate と bounded delegation

以下の型は正式Lexiconではないが、**フィールド名・型・必須性はwire-v1の契約**。`Hex33`等はbytesではなく前節の文字列型。

```ts
type Scope = {
  orgIds: string[];
  bsaf: { botDid: string; types: string[] }[];
};
type CertificateBody = {
  type: "mosimo.oriom.dev/identity-certificate";
  version: 1;
  serial: string;             // 32 lowercase hex chars; issuer-generated unique 16 bytes
  rootId: string;
  issuerPubkey: Hex33;
  subjectPubkey: Hex33;
  subjectDid: string;         // leaf: did:plc:[a-z2-7]{24}; intermediate: exactly ""
  orgId: string;              // opaque stable ID, exact matching; no hierarchical inference
  orgName: string;            // display name only; never used for scope matching
  role: "importer" | "issuer";
  permissions: ["bsaf-import"];
  canDelegate: boolean;
  scope: Scope;
  notBefore: Timestamp;
  notAfter: Timestamp;
};
type Certificate = { body: CertificateBody; sig: Hex64 };
```

`orgId` は1..128 UTF-8 bytes、`orgName` は1..256、制御文字 U+0000..001F / U+007F は不可。orgIds配列の各値にも同じorgId規則を適用する。空白除去・大小文字変換・prefix包含はしない。Bot DID は `did:plc:[a-z2-7]{24}`。type値は1..128 UTF-8 bytes、制御文字不可で、`type:` prefixを除いた原値。`*` も単なるリテラルであり wildcard ではない。

- `scope.orgIds`: 1..16 distinct values。`scope.bsaf`: 1..16 distinct botDid entries。各 `types`: 1..32 distinct values。全Botを合計した `(botDid,type)` は64組以下。Botごとの上限のみ16から32へ拡大し、0019 §5.2.3のKikikuru Bot固定23種と既存JMA Botの5種を同時に表現可能にする。既存の選択・証明・root scopeは自動拡張しない。32を認めない旧validatorは23種のscopeを拒否するため、発行側・receiver双方の上限対応が必要。暗号・署名preimage・scope包含判定は変更しない。
- 上記全リストはUTF-8 bytesの**辞書順**（length-firstではない）で昇順、重複不可。`bsaf` はbotDid順。map keyのCBOR順とは別の規則。
- `role:"importer"`: `canDelegate:false`、`subjectDid`非空、`scope.orgIds`は **`[orgId]` のみ**。`subjectPubkey`はleafのatproto key。
- `role:"issuer"`: `subjectDid:""`。`subjectPubkey`は証明専用key。`canDelegate:false` のissuerでもleafを発行できるが、issuerの再委任はできない。importerは他のcertificateを発行できない。
- 全証明で `orgId ∈ scope.orgIds`。root→最初の証明にも、事前設定rootの許可scopeとの包含判定を適用する。
- 子の `scope.orgIds` は親の部分集合。子の各 `(botDid,type)` は親scopeの組に含まれる。`permissions` は親の部分集合（v1では常に上記1要素）。子の期間は親期間に包含される。
- 親のsubject keyが子のissuer keyに完全一致する。子がissuerなら親は `role:"issuer", canDelegate:true`。子がimporterなら親はissuerであればよい。rootの発行権限は事前設定による。
- 経路はroot直下からleafへ並べる **1..4 certificates**（root自身の自己署名証明は含めない、intermediateは最大3）。最後だけがimporter、それ以前はissuer。rootIdは全段で同じ。鍵の再出現・root keyのsubjectへの使用・certId重複・循環・別経路の混在を拒否。受信時の経路探索・AIA fetchは不要。一つのidentityに一つの経路のみ。
- `notBefore < notAfter`、有効期間は最大366日（31,622,400秒）。境界は **`notBefore <= now < notAfter`**。未知時計・範囲外時計で期限確認成功としない。発行者は鍵の保持とDIDの対応を発行前に確認し、鍵交換では新しい証明を発行する。
- 発行者のserial再利用禁止。同じissuer+serialで異なるbodyを見たら、その組の衝突を永続記録し、先に観測したbodyも含め以後認可しない。衝突記録は投稿の拒否やtransaction rollbackで失わず、保存に失敗した場合も認可しない。署名・scope・期間が確認できたことと、未失効の確認は別々に記録する。

rootのローカル設定は最低限 `{rootPubkey, enabled, scope, snapshotUrl, minSequence}`。`rootPubkey`はHex33、`enabled`はboolean、`snapshotUrl`は絶対HTTPS URL、`rootId`は鍵から導出する。`scope` は同じScope型、rootの権限上限。`minSequence` は1..9007199254740991の事前設定されたsnapshot sequenceの下限。新しいrootの設定は明示的な信頼操作であり、受信データで変更できない。

### 3.1 Root→leaf 発行の最小手順

1. 運用者がrootのsecp256k1秘密鍵を安全な発行環境で生成・保持し、compressed公開鍵・scope・snapshot URL・minSequenceだけをreceiverへ事前設定する。root秘密鍵をserver importerやreceiverへ配らない。
2. importerは既存Androidと同じ独立のNostr/atproto/PLC鍵とDIDを準備し、§4のbindingを作る。root発行者へDID、compressed atproto公開鍵、binding、組織の確認資料と要求するBot/type scopeを渡す。秘密鍵は渡さない。
3. 発行者は両binding署名による鍵保持、要求DID/keyの対応、組織の確認とscopeを審査する。登録済みDIDでは検証したPLC状態のatproto keyと照合する。未登録genesisを許容する実験運用では、署名済みPLC初期操作からDIDを再導出し、atproto keyを照合して、**未登録・genesis時点のみ**という確認状態を発行記録へ残す。後者を現在のDirectory認証と表示しない。組織確認自体は暗号だけでは成立せず、運用者の帯域外審査が必要。
4. 新serial、role importer、canDelegate false、subjectDid、subjectPubkey、単一orgId、承認したscope、期間を設定して `body` を構成する。root鍵で `H(body)` にlow-S ECDSA署名し `{body,sig}` を返す。証明生成にimporterの秘密鍵は不要。
5. rootが初回sequence（minSequence以上）の空CRLまたは実際の完全CRL snapshotを署名して公開する。snapshotなしではcertificate単体が正しくても新規ingressは認可されない。
6. importerは返されたleaf署名・DID/key一致を自己検査し、`chain:[leaf]` と既存bindingをidentityに載せ、§5の投稿を作る。root発行API・オンラインCAサーバーは必須ではなく、オフライン発行とファイル配置でよい。

## 4. Reciprocal binding — 既存 Android との互換性

`AtRepository.binding()` の既存formatを **そのまま固定**する。古い `mndt` / `MNDT` の文字列は意図的に維持し、書き換えない。

```ts
type Binding = {
  declaration: {
    type: "mndt.keyBinding";
    version: 1;
    did: string;
    atprotoPubkey: Hex33;
    nostrPubkey: Hex32;
    consent: "Use this key pair for this DID's MNDT publications";
  };
  atprotoSig: string;
  nostrSig: Hex64;
};
```

`h = H(binding.declaration)`。`atprotoSig`はhへのcompact low-S ECDSA 64 bytesを **RFC4648通常Base64、paddingあり（末尾 `==`、全88文字）**で表す。これは既存binding内部フィールドに限定した0012 §3.5の明示的例外。`nostrSig`はhへのBIP-340 Schnorr 64 bytes、小文字hex。これはNostrイベント署名ではない。BIP-340 auxiliary randomnessは任意、検証結果に影響しない。

leaf `subjectDid == declaration.did == commit.did`、leaf `subjectPubkey == declaration.atprotoPubkey`、`declaration.nostrPubkey == event.pubkey` を確認する。**両方のbinding署名**とevent署名、commit署名をすべて検証する。共通曲線でも三用途の秘密鍵（Nostr / atproto / PLC）を共用しない。

本プロファイルではbindingを §5 のidentityに **埋め込む**。独立制御イベントや参照の解決を待たずにオフライン検証できる。一般投稿すべてへの同梱義務は追加しない。独立制御イベントのkind・更新配送は未決定のままで、本契約で仮kindを割り当てない。

bindingだけで現在のPLC状態によるDID認証は成立しない。root証明のDID/keyに対する証言、PLC genesisの自己整合性、Directoryの現在状態の検証を別々に表示する。正規PDSでの公開には従来どおりPLC状態を別途確認する。

## 5. 投稿に含める拡張と出典

```ts
type IdentityExtension = {
  $type: "dev.oriom.mosimo.defs#identity";
  version: 1;
  chain: Certificate[];       // root直下 → leaf、root自己証明なし
  binding: Binding;
};
type PriorityExtension = {
  $type: "dev.oriom.mosimo.defs#priority";
  version: 1;
  level: 0 | 1 | 2 | 3;       // bulk / normal / important / urgent のauthor hint
};
```

認可済みBSAF転載はidentityを **ちょうど1個**、0019のbsafV1を **ちょうど1個**含め、`bsafV1.original`を必須にする。priorityは0..1個、未指定はlevel1。多重・不正priorityはヒントを採用せずlevel1とし、より高い値へ修復しない。不正identityは認可を失敗させるが、通常本文の署名を無効化する意味ではない。

Nostrでは次の2要素tag。値は **`$type`だけを除いた全mapの `C` → 通常Base64、paddingなし**。binding内部のpadded stringはそのままCBOR textとして保持する。

```text
["mosimo.oriom.dev:ext:dev.oriom.mosimo.defs#identity", B64(C({version,chain,binding}))]
["mosimo.oriom.dev:ext:dev.oriom.mosimo.defs#priority", B64(C({version,level}))]
```

atproto形式の`extensions`に同じオブジェクトを含めてからcommitし、通常の0012タグとNostr署名を生成する。BSAF再配信のcommitは既存の署名検証用であり、atprotoへの再公開を意味しない。`bsafV1.original` を持つ再配信はNostr専用とし、PDSのatproto公開ジョブ・リポジトリ公開・firehoseへ投入しない。本文は原レコードの `text` と一致させ、DID等の説明を追記しない。署名後にrelay/gatewayが拡張を追記しない。メッシュでは0012の既存共通ルールでtag値を生CBOR bytesへ可逆変換する。メッシュ7要素配列・基本タグ・kindは変更しない。

BSAFのoriginal.uriは `at://<botDid>/app.bsky.feed.post/<rkey>`（query/fragment不可、rkeyはatproto record-keyの構文）、CIDはCIDv1 dag-cbor SHA-256のcanonical lowercase base32（既存 `cidBytes` と同じ）、createdAtは原文字列。BotはURIのDID、typeは一意の `type:` タグから得る。0019のbsaf:v1と5つのcoreタグを各1個要求する。source文字列をBot DIDの代用にしない。tagsは最大8、各640 UTF-8 bytes以下、langsは最大3、各1..64 ASCII bytesのBCP-47 language tag。原タグ・言語を並べ替えない。serverは取得した原recordのCIDを検算し、帰属を確認した取得経路と原recordを保存する。AppView経由だけなら原Botのrepository署名・包含まで検証したとは表示しない。

receiverが検証するのは **認可されたimporterの転載証言**。原record全量やMST inclusion proofの同梱は必須にしない。通常commit復元・署名検証はMST包含の証明ではなく、途中commit未取得でも本文の署名検証とは独立する。原Botが署名したNostrイベントとは表示しない。

## 6. Root-signed trust snapshot（完全CRL、短い鮮度）

snapshotはイベント外の更新可能なデータである。期限の短いsnapshotをimmutableな各投稿に必須埋め込みしない。事前設定 `snapshotUrl` からHTTPSで取得し、cacheした署名済みsnapshotをオフラインでも同じ期限まで利用できる。URLは鍵発見ではない。redirect先・サイズ・timeoutを制限する。署名の一致だけでは時計の正しさを証明しない。

```ts
type TrustSnapshotBody = {
  type: "mosimo.oriom.dev/trust-snapshot";
  version: 1;
  rootId: string;
  sequence: number;             // integer, 1..9007199254740991
  issuedAt: Timestamp;
  validUntil: Timestamp;
  revokedCertIds: string[];     // certId, lowercase hex64
  revokedPubkeys: Hex33[];      // root/intermediate/leaf atproto key
};
type TrustSnapshot = { body: TrustSnapshotBody; sig: Hex64 };
```

- root keyで §2 のECDSA署名。HTTPは `application/cbor` の `C(TrustSnapshot)` をMUST提供する。ファイルミラー・アプリのcacheも同じCBOR bytesでよい。JSONでの実装間受け渡しも §2 の変換に従えば同じ署名対象となる。配送者の認証はroot署名の代用にならない。
- **`issuedAt <= now < validUntil`**、`0 < validUntil-issuedAt <= 3600 seconds`。未来snapshot、期限切れ、時計未確認、取得失敗で有効snapshotがない場合は **新たな自動ingressを拒否/保留**。HTTP Dateやevent.created_atを信頼時計として自動採用しない。端末の時刻同期の仕組みはローカルだが、確信できない時計はunknownとして失敗させる。時刻の不確かさを区間で保持するなら区間全体が証明・snapshotの期間内である必要がある。
- これは **issuedAt時点の完全なCRL**。差分・ページング・委任CRL・失効解除はv1にない。rootは全intermediateとleafの失効を一元掲載する。新たな失効はより大きいsequenceで直ちに公開する。攻撃者が更新を隠す場合、現在のsnapshotのvalidUntilまで（最大1時間）の失効遅延は残る。「現在の未失効が絶対保証」と表示しない。
- リストは小文字hex文字列の辞書順、distinct。両リストの合計は最大256 entries。前のsnapshotで失効した項目を削除しない。上限に近づいたら明示的なroot移行が必要で、切り詰めたCRLを発行・受理しない。
- 検証済みsnapshotのみ、rootIdごとに **最大sequence + body hash + issuedAt +累積失効集合**を永続保存する。`sequence < max(minSequence, savedSequence)` を拒否。同sequenceは同じbody hashの再取得だけ許可し、期限を延長しない。上位sequenceはissuedAtが以前以上、かつ以前の失効集合を包含することを必須にし、状態を原子的に更新する。署名が異なってもbodyが同じなら同sequenceの同一snapshotである。
- 期限切れでもhigh-water markと失効集合は消さない。root更新・アプリ再起動・再取得失敗で巻き戻さない。保存失敗時は認可しない。初回・データ消失後は事前設定minSequenceと時計による最大1時間のreplay窓が残る。バックアップ復元からの完全な巻き戻り防止はハードウェアのrollback-resistant状態なしには保証できない。
- 経路の任意のcertId、root key、任意のissuer/subject keyが失効集合にあれば拒否する。root keyの失効を一度受理したらローカルでも無効として保持し、同rootでの自動復活不可。root秘密鍵の侵害そのものはそのrootによる署名では安全に回復できず、アプリ/利用者による帯域外の削除・新root導入が必要。
- Nostr key単体の失効はこのCRLのkey欄には入れない。対応leaf certIdまたはleaf atproto keyを失効し、新binding + 新leafを発行する。binding自体に独立した「最新版」規則はない。

## 7. Receiver / gateway の認可アルゴリズム

以下を **新たなインターネット→mesh自動投入ごとに**実行する。serverで検証済みという自己申告を信用しない。

1. payload/JSONの資源上限を先に適用。NIP-01 event IDとSchnorr署名、kind1、0012基本版/必須tag/期限を検証。元のevent/tag順を維持する。
2. identity・bsafV1の個数・型・上限を確認。bsafV1.originalからBot DID、一意のtypeタグからtypeを得る。receiverのローカルBot/type選択がなければ投入しない。
3. chain先頭のrootIdを**事前設定済み・enabledなroot**へ照合。一つの提示経路を §3 に従って検証。root scopeとの包含、各証明署名、issuer linkage、role/delegation、期間を確認する。root→leafのみの実装は長い経路をunsupportedとして保留し、leaf直前の中間鍵をroot扱いしない。
4. §4 のbinding完全一致・両署名を検証。commitを復元し、leaf atproto keyでcompact low-S署名を検証。commit.did、binding.did、leaf.subjectDidを一致させる。復元recordからCIDも算出可能だがMST包含検証済みとはしない。
5. 信頼できる **受信時刻now** に全証明が有効であること、およびevent作成時刻も各証明期間内であることを要求する。未来eventは認可しない。配送期限はnowより後であること。deadlineを証明期限に切り詰めて再署名する必要はないが、証明が先に切れたら以後の新規ingressは認可しない。
6. 対応rootの最新受理snapshotについて §6 の署名・freshness・monotonicity・失効を確認。event.created_at時点でなく **now** の鮮度を要求する。期限切れsnapshotをイベント添付やcacheから再提示しても通らない。
7. Bot DID/typeが経路の全scopeとローカル選択に含まれることを確認する。認可結果にはrootId、leaf certId、Bot/type、snapshot sequence/issuedAt/validUntil、確認時刻を記録する。
8. 既存event ID重複抑止、delivery deadline、BPv7 lifetime、hop、容量/帯域上限を適用して元eventを投入。serverは `(original.uri, original.cid)`→生成済みeventを永続記録し、再取得/再試行で期限延長・新転載を繰り返さない。receiverは最低限event IDで重複抑止し、未検証の原URI/CIDだけで別署名イベントを配送済みとしない。

キューで待機した場合は実際の投入時にも期限・snapshot・失効を再確認する。判定不能は成功にしない。最低限 `authorSignature`, `binding`, `chainScope`, `certificateTime`, `revocation` を独立状態として保持し、revocationは `fresh-as-of(issuedAt, validUntil, sequence)` / revoked / stale / unknown を区別する。証明失効・期限切れは原eventの署名の破壊・削除ではなく、以後の認可の停止である。オフラインで既存メッシュデータを表示・保持する際も現在の公式認証と誤表示しない。

## 8. Priority hint と opt-in relay ordering

署名されたpriority.levelは著者の要求にすぎない。受信ノードの **effectivePriority** はローカル信頼・地域関連・鮮度・資源状況で決定し、署名eventへ書き戻さない。初期の安全な既定実装は次とする。

```text
hint = valid single priority extension ? level : 1
effectivePriority = ingress authorized by §7 ? hint : min(hint, 1)
```

receiverはさらに下げてよい。独立に信頼する緊急発信者等のローカル方針を将来追加してもよいが、単なるBSAF.value・orgName・自己署名証明から引き上げない。優先度は証明・失効・期限・quotaを免除しない。公平性・具体的なmesh schedulingはローカルであり、level3に無制限の帯域を与えない。

### 8.1 標準 NIP-01 を変更しない

通常の `REQ` は通常のNIP-01のフィルタ・limit・保存イベントの順序（created_at降順、同時刻はid辞書順昇順）を維持する。標準REQの結果をpriority順へ変更しない。未知のfilter fieldを入れただけでopt-inしたと扱わない。

対応relayはNIP-11に次の任意追加情報を示す。自己申告はtrust anchorや認可を与えない。

```json
{"mosimo":{"wire":1,"priority_order":["priority-v1"]}}
```

priority順取得は **独自message verb** を明示的に選ぶ。標準NIPの番号を自称しない。

```json
["MOSIMO-REQ", "bsaf-priority", {"order":"priority-v1","filter":{"kinds":[1],"#t":["mosimo.oriom.dev"],"limit":100}}]
```

- request objectの必須fieldsはorder/filterのみ。subscription IDは1..64 ASCII printable bytes、同接続の既存IDと衝突させない。filterは一つのNIP-01 filter、kindは `[1]`、`#t`に `mosimo.oriom.dev`を含むこと、limit整数1..100が必須。他の標準filter条件はAND、値リスト内は通常のORとする。
- これは **保存済みイベントの有限snapshot取得**（新着live購読ではない）。受理時点の候補・relayの認可状態・時刻を固定し、通常filterに一致する集合を **effectivePriority降順 → created_at降順 → id辞書順昇順**でsortした後にlimitを適用する。通常REQのlimit後に並べ替えるのではない。expiry等で現時点のingress不適格なeventはpriority1を上限とし、削除は意味しない。
- 応答は同IDの標準形 `EVENT` を使用し、完了時 `EOSE` を送ってこの有限requestを解放する。`CLOSE`で中止できる。対応relayで不正/超過なら `CLOSED` と理由を返す。計算・保存資源上限で処理不能なら黙って別順にせずCLOSEDにする。
- relayは自身のroot/snapshot/ローカル選択でeffectivePriorityを評価する。receiverがrelay順を信用して認可検証を省略しない。relayとreceiverのpriorityが一致する保証はない。
- 非対応・timeout・CLOSEDならクライアントは **別のsubscription IDで標準REQへfallback**し、受信後に自身のpriorityで処理する。MOSIMO-REQの無応答を空の成功としない。live購読が必要なら別の標準REQを使う。

## 9. 実装時の資源上限と適合チェック

- 1 certificateの `C(Certificate)` は最大4,096 bytes、identity全体の `C(IdentityExtension)` は最大20,480 bytes。chain最大4、snapshotのCBORは最大32,768 bytes、失効リスト合計256。上限超過時に途中を削らない。
- 本プロファイルのeventは最大64 tags、16 extensions。CBOR深さ最大16、各CBOR文書のitem数最大8,192（map keyも数える）、メッシュevent payloadは既存上限32,768 bytes。HTTP/Nostr JSON受信は展開前最大262,144 bytesとしてよい。より小さい端末上限は公開し、超過をunsupported/resource-limitとして扱う。すべての最大値の同時利用が32KiBに収まる保証はない。
- root→leafの最小構成にintermediate発行UI、OCSP、delta CRL、自動root rotation、証明のネットワーク探索、binding専用control kindは不要。
- 実装の最低限の共通fixtureは、同じroot/leaf/binding/post/snapshotでNode/Kotlin/ESP32の `C(body)` bytes・hash・certId・署名検証が一致すること。例示用秘密鍵はテスト専用、アプリへroot秘密鍵を同梱しない。
- 必須negative checks: unknown root、DID/key/binding mismatch、binding片署名、high-S/DER署名、非canonical CBOR、重複key、scope拡大、leafによる発行、5段、期限境界、時計unknown、stale/future snapshot、sequence rollback/equivocation、失効したintermediate/leaf、未選択Bot/type、priority自己申告だけでの昇格。これは実装者への適合要件であり、本書追加で試験実行済みという意味ではない。
