# 個別通信（DM）

識別子: `dev.jisaku.mosimo.dm`

## 目的

Mosimo の鍵を持つ二者の間で、暗号化した 1 対 1 のメッセージをメッシュとリレーで運ぶ方法を定義する。メッセージはテキストのほか、`$type` 付きの構造化オブジェクトを運べる。これにより、人同士のやり取りだけでなく、認証局への失効要求（[失効要求](../attest/revocation/request/README.md)）のようなプロトコル内の要求も、HTTPS のエンドポイントに届かない状況でメッシュ経由で送れる。

本プロトコルが保証するのは、宛先が配送期限内にメッシュ上またはリレー経由で届く範囲にいた場合に、宛先だけが平文を読めることである。誰と誰が通信しているか（`pubkey` と `p` タグ）は隠さない。グループ、メディア、既読通知、鍵の失効・更新は範囲に含まない。

## 前提

| 識別子 | 役割 |
|---|---|
| [`dev.jisaku.mosimo`](../README.md) | Nostr イベントの構造、発見用 `t` タグ、配送期限タグ `mosimo:exp`、JSON での `Bytes` の表現 |
| [`dev.jisaku.mosimo.mesh`](../mesh/README.md) | kind を問わない保存・中継、配送期限、発信頻度の上限 |

## 1. イベント

いずれも通常の Nostr イベントであり、メッシュ用 CBOR で Bundle に入る。発信者は自身の Mosimo の Nostr 鍵で署名し、配送期限タグ `mosimo:exp` を付ける。既定の配送期限は 24 時間である。atproto commit は付けない。既存の Nostr の kind に意味が一致するため、固有の制御 kind は用いない。

| 用途 | kind | タグ（この順） | content |
|---|---|---|---|
| メッセージ | `4` | `["t", "mosimo.jisaku.dev"]`、`["p", <宛先 pubkey>]`、`["mosimo:exp", Timestamp]` | NIP-04 暗号文 |
| 配達通知 | `4` | `["t", "mosimo.jisaku.dev"]`、`["p", <宛先 pubkey>]`、`["e", <受け取ったメッセージの event ID>]`、`["mosimo:exp", Timestamp]` | 空文字列の NIP-04 暗号文 |
| 表示名 | `0` | `["t", "mosimo.jisaku.dev"]`、`["mosimo:exp", Timestamp]` | `{"name": "<最大 40 文字>"}` |

- 受信側は `p` が一つだけで自分を指す kind 4 のみを読む。`e` があれば配達通知、なければメッセージである。
- 暗号文の本文は UTF-8 で 2,000 バイト以下とする。Bundle の上限に収めるための値である。
- 表示名は起動時と変更時に発信する。同じ pubkey の表示名は `created_at` が新しいものを採る。表示名は自己申告であり、本人確認ではない。組織名として表示してはならない。組織の確認は[署名チェーン](../attest/chain/README.md)だけが与えるためである。

## 2. 暗号化

NIP-04 を用いる。送信者の秘密鍵と宛先の公開鍵の ECDH で得た共有点の x 座標（32 バイト）を鍵とし、AES-256-CBC でランダムな IV により平文を暗号化する。`content` は `base64(暗号文)?iv=base64(iv)` である。Nostr の公開鍵は x-only なので、相手の公開鍵は y 座標が偶数の点として持ち上げる。復号側も同じ共有点を得るので、送信者と宛先だけが平文を読める。

NIP-04 は通信相手を隠さず、Nostr 本体でも後続の方式（NIP-17）に置き換えられている。本プロトコルで NIP-04 を採るのは、既存の Nostr 実装との互換、ESP32 級の端末で実装できる軽さ、宛先 `p` タグによる受信側の選別の単純さのためである。秘匿が必要な用途は範囲外である。

## 3. 平文の形式

復号した平文は次のどちらかである。

| 形式 | 判別 | 扱い |
|---|---|---|
| テキスト | JSON オブジェクトとして解釈できない、または `$type` を持たない | 人が読む本文としてそのまま表示する |
| 構造化オブジェクト | `$type` を持つ JSON オブジェクト | `$type` に対応するプロトコルが処理する。`Bytes` はコアの規則どおり通常の Base64・padding なし |

構造化オブジェクトの `$type` は Mosimo の型識別子であり、受信アプリは対応する型だけを処理し、未知の型は「対応していないメッセージ」として表示する。平文を JSON として解釈できる場合でも、`$type` のないものはテキストとして扱う。構造化オブジェクトの例は、認証局の鍵へ送る失効要求（`dev.jisaku.mosimo.attest.revocation.request`）と、その応答（`#response`）である。

## 4. 配達通知と配送状態

宛先はメッセージを復号できた時点で配達通知を返してよい。送信側は次の状態を表示する。いずれも観測であり、保証ではない。

| 状態 | 条件 |
|---|---|
| 送信中 | 端末に保存済み。どの隣接ノードにも渡っていない |
| 中継 | 隣接ノードが Bundle を受理した、または照合で所持を示した |
| 配達 | 宛先から該当 event ID の配達通知を受け取った |
| 期限切れ | 配達通知がないまま配送期限を過ぎた |

配達通知も発信者ごとの発信頻度の上限（1 分あたり 12 件）に数える。期限切れのメッセージの自動再送はしてはならない。再送は配送期限を発信者の意図を超えて延ばすことになるためである。送り直す場合は新しいメッセージとして作成する。

## 5. ノードでの扱い

- 中継ノードは kind を問わず保存・中継し、投稿の UI は kind 1 のみを表示する。
- PDS は kind 1・5・1984 のみを受け付けるため、本プロトコルのイベントは PDS へ搬出せず、PDS 受入待ちによる追い出し保護の対象にもしない。
- Nostr リレーへは搬出してよい。リレー経由で届く場合、暗号文と `p` タグは公開される。
- DM だけを扱うアプリはリレーへ接続せず、メッシュのみで動作してよい。
- 同じ端末の他の Mosimo アプリと共存する場合は [メッシュ配送 §4.6](../mesh/README.md#46-同一端末の複数アプリ) に従い、BLE と LAN は端末内の担当アプリ一つだけが動かす。
