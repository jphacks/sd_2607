# 個別通信（DM）プロファイル

識別子: `dev.jisaku.mosimo.dm`

## 目的

Mosimo のメッシュは、署名・配送期限が正しい署名済みイベントであれば kind を問わず保存・中継する。本プロファイルはこの性質を使い、投稿以外の用途のアプリが同じメッシュを共有できることを、1 対 1 のテキストメッセージで示す。対象はテキストのみの 1 対 1 メッセージ、配達通知、表示名である。

本プロファイルが保証するのは、宛先が配送期限内にメッシュ上で接触できた場合に暗号文が届くことまでである。グループ、メディア、既読通知、通信相手の秘匿、鍵の失効・更新、オンライン経由の配送は範囲に含まない。

## 前提

| 識別子 | 役割 |
|---|---|
| [`dev.jisaku.mosimo`](../README.md) | Nostr イベントの構造、発見用 `t` タグ、配送期限タグ `mosimo:exp` |
| [`dev.jisaku.mosimo.mesh`](../mesh/README.md) | kind を問わない保存・中継、配送期限、発信頻度の上限 |

## 1. イベント

いずれも通常の Nostr イベントであり、メッシュ用 CBOR で Bundle に入る。発信者は Mosimo の Nostr 鍵で署名し、配送期限タグ `mosimo:exp` を付ける（既定 24 時間）。atproto commit は付けない。既存の Nostr の kind に意味が一致するため、固有の制御 kind は用いない。

| 用途 | kind | タグ（この順） | content |
|---|---|---|---|
| メッセージ | `4` | `["t", "mosimo.jisaku.dev"]`、`["p", <宛先 pubkey>]`、`["mosimo:exp", Timestamp]` | NIP-04 暗号文 |
| 配達通知 | `4` | 上記に `["e", <受け取ったメッセージの event ID>]` を `p` の直後に加える | 空文字列の NIP-04 暗号文 |
| 表示名 | `0` | `["t", "mosimo.jisaku.dev"]`、`["mosimo:exp", Timestamp]` | `{"name": "<最大 40 文字>"}` |

- 暗号化は NIP-04（ECDH の x 座標を鍵とする AES-256-CBC、`base64(暗号文)?iv=base64(iv)`）。相手の x-only 公開鍵は偶数 y として持ち上げる。
- 受信側は `p` が一つだけで自分を指す kind 4 のみを読む。`e` があれば配達通知、なければメッセージである。
- 本文は UTF-8 で 2,000 バイト以下とする。Bundle の上限に収めるための値である。
- 表示名は起動時と変更時に発信する。同じ pubkey の表示名は `created_at` が新しいものを採る。表示名は自己申告であり、本人確認ではない。

## 2. 配送状態

送信側は次の状態を表示する。いずれも観測であり、保証ではない。

| 状態 | 条件 |
|---|---|
| 送信中 | 端末に保存済み。どの隣接ノードにも渡っていない |
| 中継 | 隣接ノードが Bundle を受理した、または照合で所持を示した |
| 配達 | 宛先から該当 event ID の配達通知を受け取った |
| 期限切れ | 配達通知がないまま配送期限を過ぎた |

配達通知も発信者ごとの発信頻度の上限（1 分あたり 12 件）に数える。再送はしない。

## 3. 既存ノードでの扱い

- 中継ノードは kind を問わず保存・中継する。投稿の UI は kind 1 のみを表示する。
- PDS は kind 1・5 のみを受け付けるため、本プロファイルのイベントは PDS へ搬出せず、PDS 受入待ちによる追い出し保護の対象にもしない。一般の Nostr リレーへは搬出され得るため、暗号文と `p` タグは公開される。
- 本プロファイルのアプリはリレーへ接続せず、メッシュのみで動作してよい。

## 4. 限界

NIP-04 は誰と誰が通信しているか（`pubkey`・`p`）を隠さず、Nostr でも非推奨である。秘匿が必要になれば NIP-17（gift wrap と NIP-44）へ移行する。

## 未確定事項

- 同一端末の複数アプリ。各アプリが独立したメッシュノードとして同じ GATT Service UUID を広告する構成では、LAN（`_mosimo._tcp`）上で同一端末内のアプリ同士が相互に中継できることは確認済みだが、BLE での共存は未検証。端末あたり 1 ノードとし他アプリがプロセス間通信で利用する構成が候補。
- 個別通信を正式に採用する場合の kind・暗号方式・宛先 EID の選択。
