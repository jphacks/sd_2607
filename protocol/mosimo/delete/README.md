# 削除要求

識別子: `dev.jisaku.mosimo.delete`

## 目的

著者が自分の投稿の削除を求める方法を定義する。削除要求は [NIP-09](https://github.com/nostr-protocol/nips/blob/master/09.md) の `kind: 5` イベントであり、投稿と同じくメッシュとリレーで運ぶ。投稿を削除する場合は、対象レコードを著者のリポジトリから除いた状態を指す atproto commit を同じイベントに収め、PDS が著者の署名を保ったまま削除後のリポジトリを再構築できるようにする。

本プロトコルが保証するのは次の二点である。第一に、削除要求が対象の著者自身の鍵で署名されたことを、イベント単体で確認できる。第二に、削除要求を受け取った PDS は、削除後のリポジトリ状態を著者が署名した commit として検証できる。

全ての保有者による消去と、ノード・リレー・クライアントが削除要求に従うことは保証しない。削除要求を受け取ったノードがそれに従うか、何を消すかは実装が決める。他人の投稿を削除する手段は本プロトコルにはない。不適切な投稿への対応は[通報](../report/README.md)が扱う。

## 前提

| 識別子 | 文書 | 依存する理由 |
|---|---|---|
| `dev.jisaku.mosimo` | [コア](../README.md) | 投稿の単位、レコードキー、commit の構造と基本タグ（`mosimo:commit`・`mosimo:base`・`mosimo:rkey`・`mosimo:exp`）、発見用 `t` タグ |
| `dev.jisaku.mosimo.mesh` | [メッシュ配送](../mesh/README.md) | kind を問わない保存・中継、配送候補・ブロック・照合集合の扱い |

## 1. イベント

削除要求は対象 1 件につき 1 件の `kind: 5` イベントとし、対象の著者と同じ Nostr 鍵で署名する。一つの commit はちょうど一つのレコードを除くため、複数の投稿を削除する場合は削除要求を対象ごとに発行する。

| 項目 | タグ配列 | 個数 |
|---|---|---|
| プロトコル識別 | `["t", "mosimo.jisaku.dev"]` | 1 個 |
| 対象 | `["e", <対象の event ID>]` | 1 個 |
| 対象の kind | `["k", <対象の kind の十進文字列>]` | 1 個 |
| 削除後の commit | `["mosimo:commit", commitBase64]` | 対象が投稿（`kind: 1`）の場合に 1 個 |
| 適用元 commit | `["mosimo:base", baseCid]` | 同上 |
| 除くレコードのキー | `["mosimo:rkey", tid]` | 同上 |
| 配送期限 | `["mosimo:exp", Timestamp]` | 1 個 |

- タグはこの表の順に置く。対象が投稿でない場合は commit・適用元・レコードキーのタグを置かない。
- `content` は削除理由の任意の文字列であり、UTF-8 で 280 バイト以下とする。省略時は空文字列とする。理由も公開される。
- 配送期限は、対象の配送期限より前に満了しないことを推奨する。削除要求が先に満了すると、後から対象を受け取ったノードに削除要求が届かなくなるためである。アプリの既定値は、対象の配送期限と作成時から 24 時間の遅い方とする。
- タグの値の表現と、メッシュ用 CBOR での可逆な型変換はコアと[メッシュ配送 §2.1.1](../mesh/README.md#211-タグ値の可逆な型変換) に従う。

`kind: 5` は NIP-09 の削除要求そのものであり、本拡張に未対応のリレー・クライアントも対象の非表示や削除に用いることができる。本拡張が加えるのは、投稿の削除を atproto リポジトリでも成立させるための commit タグと、メッシュでの扱いである。

## 2. 削除後の commit

投稿を削除する著者端末は、リポジトリから `dev.jisaku.mosimo.post/<tid>` のエントリを除き、MST を更新して新しい v3 commit に署名する。

| 項目 | 値 |
|---|---|
| `data` | 対象を除いた MST の root |
| `rev` | 新しい TID。リポジトリの改訂として単調増加させる |
| `prev` | コアと同じく `null` |
| `mosimo:base` | 端末が直前に確定した commit の CID |

削除後の commit は以後の投稿の適用元になる。次の投稿の `mosimo:base` は削除後の commit の CID を指し、その `data` は対象を含まない。MST から除くのは path → record CID のエントリであり、過去の commit・レコードのバイト列を書き換えるものではない。

著者端末は、削除後の commit を確定してから削除要求を外部へ出す。確定前に送ると、同じ TID・commit を再利用する余地が生じるためである。

## 3. ノードでの扱い

ノードは削除要求に従うかを自ら決めてよく、受け取った削除要求を無視する実装もあり得る。従う場合は本節のとおりに扱う。

削除要求は、`pubkey` が対象の著者と一致する場合に限り有効である。一致しない削除要求は対象に作用しない。対象がまだ届いていない場合は、対象の event ID と削除要求の `pubkey` を記録し、後から届いた対象の著者が一致すれば同じ扱いを適用する。

| 対象 | 有効な削除要求に従うノードの扱い |
|---|---|
| 対象の投稿 | 直ちに表示をやめ、配送候補・照合集合（[メッシュ配送 §5.5](../mesh/README.md#55-reconcile-による差分照合)）・`INVENTORY` から外す。保存している本体は消去してよい。以後は `WANT` せず、`BEGIN` を受けた場合は理由コード 5 で拒否する |
| 削除要求そのもの | 通常のイベントとして配送期限まで保存・中継し続ける。後から対象を受け取るノードにも削除を伝えるためである |

本体を消去するか、消去までの猶予、記録の保持期間は実装が決める。ただし削除要求そのものを、対象と一緒に配送から外してはならない。

著者自身の端末は例外として、PDS へまだ搬出していない対象を、PDS のリレーへだけ搬出してよい。PDS が削除後の commit を検証するには削除前の状態、すなわち対象を追加した commit が必要であり、対象が PDS に届かなければ以後の投稿もすべて検証できなくなるためである。この搬出は表示・メッシュ配送の再開ではない。

## 4. PDS とリレー

[論理 PDS と物理 PDS](../pds/README.md) は、対象が投稿である削除要求の commit を、通常の投稿の commit と同じく著者の署名済み状態として検証し、リポジトリへ適用しなければならない。これは削除を受け入れるかという運用方針の判断ではなく、リポジトリの整合性の要件である。以後の投稿の適用元は削除後の commit を指し、その MST は対象を含まないため、削除後の commit を適用しない PDS は以後の投稿を検証できなくなる。

- PDS は削除要求だけを根拠に、著者の新しい commit を自ら生成してはならない。commit の署名は著者だけが行える。commit タグのない削除要求（対象が投稿でない場合、または他の実装の NIP-09）は、Nostr リレーとしての非表示・配信停止にだけ用いる。
- 適用元の commit や対象の追加が未着の場合は、他の変更操作と同じく検証を保留する（[PDS §2.2](../pds/README.md)）。
- 適用後は対象を atproto の同期・Nostr の `REQ` への応答に含めない。保存済みバイト列の物理的な消去と保持期間は運用者が決める。
- Nostr リレーは `kind: 5` を受け付け、NIP-09 に従って対象の配信を止めることを推奨する。

## 5. 投稿以外の対象

`kind: 1` 以外のイベント（[通報](../report/README.md)、DM 等）も、同じ鍵で署名した削除要求で取り下げを求められる。この場合は commit・適用元・レコードキーのタグを置かず、ノードは第 3 節と同じく対象を配送から外す。通報を取り下げた場合、その通報は集計から除かれる。

## 未確定事項

- 削除要求の記録（対象未着の記録を含む）の保持期間と件数の上限。
- 削除要求の配送期限の上限と、対象の配送期限が不明な場合の既定値。
- 削除後の commit の配送が失われた場合に、著者端末が同じ削除要求を再送する規則。
