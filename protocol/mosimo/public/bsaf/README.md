# BSAF v1 互換拡張

識別子: `dev.jisaku.mosimo.public.bsaf`

## 目的

本プロトコルは、Bluesky Structured Alert Feed（BSAF）の `bsaf:v1` 投稿と本プロトコルの投稿との相互運用を定義する。定義する範囲は、BSAF のタグ・言語・原投稿参照・Bot 定義参照を保持する拡張、既存 BSAF 投稿の AppView 収集、本プロトコルへの取り込み（取り込み側が明示的に選んだ Bot と情報種別に限る自動再配信）、本プロトコルからの新規作成、BSAF 形式での別途公開、循環再配信の抑制、表示上の重複折りたたみである。採用する BSAF 仕様は参照に示す固定リビジョンとする。

保証するのは、原投稿のタグ・言語・URI・CID を改変せずに保持し、取り込み者の署名による転載であることを常に区別できることである。保証しないのは、本拡張を付けた投稿を既存の Bluesky/BSAF クライアントが収集・表示すること（それには `app.bsky.feed.post` の公開が必要）、BSAF 投稿に本プロトコルの配送期限・署名・拡張を要求すること、タグの存在による公的警報の認定、`target:` からの正確な地理境界、原投稿の添付・返信・引用・ラベルの完全復元、第三者がコピーした投稿まで追跡して止めることである。BSAF は防災専用ではなく、スポーツ・ニュース等を含む汎用の Bot 投稿規約である。

## 1. 三つの経路

```mermaid
flowchart LR
  bsky[既存 BSAF 投稿<br/>app.bsky.feed.post] -->|収集| av[AppView<br/>原レコード + 派生索引]
  bsky -->|importer が取得・署名| mo[本プロトコルの投稿<br/>+ bsaf (original あり)]
  mo -->|Nostr リレー| recv[受信者: 独立に検証し<br/>ローカル選択内なら認可済みとして表示・優先]
  own[本プロトコルで新規作成<br/>+ bsaf (original なし)] -->|公開権限のあるアカウント| out[別の app.bsky.feed.post]
```

| 経路 | 入出力 | 保持する責務 |
|---|---|---|
| 既存投稿の収集 | `app.bsky.feed.post` → 対応 AppView | 原レコードを保持し、表示・検索・フィルタの索引を付ける。新投稿やメッシュ投入は伴わない |
| 本プロトコルへの取り込み | BSAF 投稿 → `dev.jisaku.mosimo.post` + 本拡張 | 取り込み者が新規投稿へ署名する。元投稿の出典・タグ・言語を保持し、Nostr・BPv7 へ配送できる |
| BSAF 形式での公開 | 本プロトコルの投稿 + 本拡張 → 別の `app.bsky.feed.post` | 公開権限を持つアカウントが BSAF タグ・言語・出典付きの別レコードを公開する |

1 件の本プロトコルの投稿は 1 レコード・1 commit・1 Nostr イベントである。BSAF 向けの別レコード公開は、同じ署名付き投稿の形式変換ではない。自動の再配信・公開の有効化は、本型の追加とは別の運用判断である。

タグ保持と基本表示は、他の拡張やオンラインでの Bot 定義取得なしで行える。本型を追加しても基本プロトコル・メッシュ符号化の版は変わらない。

## 3. データ型

```ts
type BsafOriginalPost = {
  uri: string;       // DID を authority とする at://.../app.bsky.feed.post/<rkey>
  cid: string;       // 取得した原レコードの CID
  createdAt: string; // 原レコードの createdAt。原文字列を保持
};

type BsafBotDefinitionReference = {
  url: string;
  retrievedAt?: Timestamp;
  sha256?: Bytes;    // 取得した JSON 文書の生バイト列に対する SHA-256、32 bytes
};

type BsafExtension = {
  $type: "dev.jisaku.mosimo.public.bsaf";
  tags: string[];
  langs: string[];
  original?: BsafOriginalPost;
  botDefinition?: BsafBotDefinitionReference;
};
```

Lexicon は [lexicon.json](lexicon.json) に置く。

### 3.1 タグと言語

`tags` は `app.bsky.feed.post.tags` と同じ並び・文字列を保持する。`bsaf:v1` と 5 種類のコアタグに加え、未知の追加タグも含む。パース結果の `type`・`value`・`time`・`target`・`source` を型内に重複格納してはならない。原文字列と解釈結果が食い違ったときにどちらが署名対象か不明になるためである。

`langs` は BSAF 本文の言語配列である。取り込みでは原投稿の `langs` を保持し、新規作成では本文の言語を指定する。本プロトコルのトップレベルに `tags`・`langs` は増やさない。

新規作成・相互運用対象では、`bsaf:v1` 1 件と、空でない各コア値を一つずつ持つ。追加タグを含めても、出力先のレコード仕様の上限（§9.1）を超えない。矛盾する複数の同名コアタグ、未知版・必要項目の欠落を、後勝ちや推測によって一組へ補修してはならない。補修した結果は原投稿の署名対象と異なり、原 Bot の発信内容として扱えないためである。AppView はそのような原投稿も本文表示用に保持できるが、解釈可能な BSAF v1 への変換成功とは扱ってはならない。

タグは最初の `:` だけで名前と残りの値に分ける。例えば `time:2026-10-18T03:04:05Z` の値は `2026-10-18T03:04:05Z` 全体である。日時内の `:`、名称の改行、空白や記号で配列を再分割したり、大文字小文字・先頭ゼロ・日時の綴りを正規化したりしてはならない。画面・ログ・通知先向けのエスケープや 1 行表示用の整形は派生表示で行い、元の値は変えない。

### 3.2 原投稿への参照

BSAF 投稿を取り込んだ場合は `original` を含める。著者は DID を authority とする `uri` から得られるため、別の `authorDid` は持たない。ハンドル表記の URI を取得した場合、取り込み時に DID を確定して原レコードの場所と対応付ける。URI の場所が同じでも CID が違えば別の内容として扱う。

原 BSAF 投稿を経由せず作成した場合は `original` を省略する。架空の Bluesky 投稿・CID や、将来公開する予定の URI を入れてはならない。この場合、BSAF 上の発信者に対応するのは本プロトコルの投稿著者であり、機関の認証は別の問題である。

参照と CID は原著者の署名そのものではなく、参照を含む投稿への Nostr 署名も取り込み者の署名である。AppView からの取得だけで原リポジトリ署名・包含を確認したと表示してはならない。原著者 DID の主張、取得内容、認証済みの帰属を区別し、通常中継は原 Bot の署名証明なしで行える。

### 3.3 Bot 定義の参照

`botDefinition` は、その BSAF メタデータを解釈する Bot 定義への任意の参照である。取り込みの場合は原 Bot の定義、新規作成の場合は発信者が管理する定義に対応させる。別 Bot の定義を流用して、その Bot として発信したことにしてはならない。

`retrievedAt` と `sha256` は取り込み側が実際に取得した版を追跡するための任意項目であり、Bot 定義自身の `updated_at` や署名ではない。ハッシュは取得バイト列全体に対する値とし、JSON キーの並べ替え等をしてから計算した値とは区別する。Bot 定義の全 JSON を投稿ごとに同梱してはならない。サイズ上限を占有するためである。

取得済みの定義・ラベルはキャッシュまたはアプリ同梱で利用できる。オフライン時の表示・中継は `self_url` の取得なしで行える。URL だけで機関の認証や取得先の安全性を認めず、取得する実装はリダイレクト・サイズ・取得頻度・接続先をローカル方針で制限する。

## 4. BSAF コアタグの対応

| 原タグ | 解釈・用途 | 区別する別の概念 |
|---|---|---|
| `bsaf:v1` | BSAF 規約版の識別 | 本プロトコルの基本版・Nostr の kind |
| `type:` | Bot が定義する情報種別 | タグの存在だけによる公的警報の認定 |
| `value:` | Bot が定義する規模・程度の離散値 | 数値比較、配送優先権、CAP の severity や観測／予測震度への一律変換 |
| `time:` | 元のソースイベントの UTC 時刻 | 原 Bot の投稿時刻、取り込み時刻、有効期間、配送期限 |
| `target:` | Bot 定義の対象コード。地理以外の対象もある | Geohash、行政区域、GPS 位置、厳密な影響範囲 |
| `source:` | 原情報源の識別文字列 | 発信 Bot の DID、機関署名、更新取消の権限 |

本プロトコルから新規に BSAF メタデータを作る場合は、その Bot の公開定義に従い、同じソースを扱う既存 Bot の `value`・`target` を尊重する。`5+` を `震度5強`、`jp-kanto` を独自の別名へ置換してはならない。表示ラベルと機械値は別にする。

`source:jma` だけから `value:5+` が予測震度か観測震度かは確定できない。複数の地域投稿を同じ広域 `target` に対応させる場合、その値は検索・表示上の広域分類であって、各投稿が広域全体の詳細を持つ意味ではない。

## 5. 経路ごとの処理

### 5.1 既存 BSAF 投稿の AppView 収集

原 `app.bsky.feed.post`、DID、at-URI、CID、取得経路・取得時刻を保持し、BSAF の版とタグを派生索引へ対応付ける（[公的情報の取り込み §11](../README.md#11-appview-統合)）。原レコードを独自 Lexicon へ書き換えてはならない。Bot 定義の `bot.did` と原投稿著者との対応を確認できる範囲で、その Bot 用のフィルタ UI を作る。ハンドルの一致だけで恒久的な同一著者と扱ってはならない。ハンドルは変更され得るためである。

`type`・`value`・`target` の選択肢は Bot ごとに扱い、同じ文字列が全 Bot で同じ意味とは限らない。未登録 Bot、未知の値、不完全なタグ、Bot 定義が取得できない場合も本文を捨てず、未解釈の値と出典を表示できるようにする。値が一意に解釈できない場合は、構造化フィルタや重複折りたたみの適用を保留する。

### 5.2 BSAF から本プロトコルへの取り込み

#### 5.2.1 自動再配信の対象

各取り込み側の運用者・利用者が、再配信する Bot と情報種別を明示的に選ぶ。自動再配信はその組み合わせに該当し、公開再配布条件と通常の資源・期限等の制約も満たす投稿だけを対象とする。BSAF タグの発見、Bot のフォロー、Bot 定義のインポート、AppView での収集・表示だけでは再配信は有効にならない。再配信対象の設定がなければ自動再配信は行われない。

これは各取り込み側のローカルな運用方針であり、中央の Bot 登録、原 Bot の本プロトコルへの参加、第三者の拡張定義への承認なしで運用できる。取り込み側ごとに選択対象は異なってよい。未選択の投稿も、別の AppView 収集・閲覧設定に従って表示できる。取り込み対象の制限は、ネットワーク全体で当該著者の投稿を拒否する規則ではない。

対象 Bot は原投稿著者の DID、情報種別はその Bot の `type:` の機械値で対応付ける。ハンドル・表示名・`source:jma` の一致だけで選択済み Bot としてはならない。ハンドルは変更され得て、`source:` は誰でも書けるためである。転載者が自己申告した `original` の URI だけで、選択済みの原 Bot が投稿したと認定してはならない。

Bot だけを選び情報種別を未選択の状態や、未知・複数値等により `type:` を一意に解釈できない投稿を自動再配信してはならない。Bot 定義へ新しい情報種別が追加された場合も、その種別の再配信には別途の明示的な選択を必要とする。

#### 5.2.2 投稿への変換

対象の投稿を取り込み者が取得し、新しい基本投稿を生成する。サーバー側の転載経路（importer）は [`dev.jisaku.mosimo.attest.importer`](../../attest/importer/README.md) に従う。転載投稿は信頼の起点からの身元証明チェーン（末端が `import` 役割、Bot DID と `type` を限定した `importScope`、`organization`）を同梱し、本拡張（`original` 必須）と任意の `priority` を付ける。Nostr リレー経由で取得した受信者は独立に検証し、ローカル選択と時刻・失効条件を満たす場合だけ新規メッシュ投入を許可する（[受信者の認可](../../attest/importer/README.md#3-受信者の認可)）。これは一般の BSAF 閲覧や通常 Nostr 本文検証への必須条件ではない。

- 原レコードは取り込み側に保持する。
- `tags`・`langs` は原値、`original` は原 URI・CID・原 `createdAt` とする。
- 基本本文は原レコードの `text` をそのまま保持する。DID・CID・取り込み者・原投稿参照・再配信の説明等を追記してはならない。本文の一致が原投稿との対応の確認手段であるためである。帰属と再配信の区別は署名付き拡張と表示用メタデータで扱う。
- 新投稿の `created_at` は変換投稿の作成時刻、`exp` は取り込み時に運用方針により確定する。古いイベントを再取得しただけで配送期間を繰り返し延ばしてはならない。
- `source` を併用する場合、原投稿参照と矛盾する著者・取得内容へ置換してはならない。
- 取り込み者の鍵でレコードと commit・Nostr イベントを生成し、Nostr リレーと通常の CBOR・BPv7 経路へ流す。`original` を持つ再配信は Nostr 専用とし、PDS の atproto 公開ジョブ・リポジトリ公開・firehose へ再投入してはならない。原投稿が既に Bluesky 上に存在し、再投入は同じ内容の重複レコードを増やすだけであるためである。commit は受信側の既存の鍵対応・署名検証用データであり、atproto への公開指示ではない。

共通の災害情報拡張と都道府県単位の影響範囲は、[BSAF から災害情報への対応](hazard/README.md)の対象 Bot・値に限り、その規則で生成する。BSAF だけを根拠に、元の CAP・JMA XML や機関による認可を復元した拡張を捏造してはならない。Bot が作った要約の原情報にない詳細を補ってはならない。原投稿の添付・返信・引用・ラベル等が意味に重要な場合は、明示的な対応または取り込み保留とする。画像・動画の本体は配送対象に含めない。32 KiB に収めるため重要な本文・BSAF のコア値・原投稿参照を削ってはならない。

Bot の DID と定義はソース候補の記録であり、現在のハンドル解決・鍵保持・原レコードの帰属検証や公的認証の代わりではない。実運用では原投稿 DID との対応を確認する。

固定 23 種を一括で自動取り込みする選択肢を用意する場合も、JMA Bot の選択とは別の明示的な opt-in とする。両方を選ぶ場合は 2 Bot・28 組となる。身元証明チェーンの `importScope` とローカル選択のそれぞれに明示的な許可が必要で、Bot 定義の取得や上限の拡大だけでは有効にならない。importer の推奨上限（Bot ごとの `types` 32、全 Bot 合計 64 組）は 23 種を一つの Bot entry に保持できる。Bot 定義の将来の種別追加は固定 23 種には含まれず、別途の選択を必要とする。一覧は選択可能な語彙である。README の旧表・担当電文の記述には定義 JSON との不一致があるため、定義 JSON の語彙と実際の取得投稿を分けて扱う。

Kikikuru Bot の投稿も本拡張として取り込み、`value:cancelled` を公式 XML の取消や旧投稿停止権限に変換してはならない。原 XML 用の構造化は [気象防災情報](../jma/weather/README.md) が扱うが、Bot 本文・タグ・定義だけを根拠に同拡張を合成してはならない。BSAF で扱える津波・火山等が JMA の XML 拡張でも対応済みになるわけではない。

### 5.3 本プロトコルでの新規作成

投稿者は単独で読める基本本文へ出典を明記し、BSAF のタグ・言語を本拡張に保持できる。原イベント時刻が不明なら投稿時刻を `time:` として補ってはならない。`time:` は元のソースイベントの時刻であり、補うと時刻の意味が変わるためである。`original` は省略する。

CAP・JMA 等の独立した拡張と併用できるが、BSAF の値をそこから導出する規則・Bot 定義を必要とする。全国最大震度を地域別の値として使う、予測値を観測値として使う、未知の対象に架空の `target` を割り当てるといった単純変換は禁止する。BSAF の値はそれだけで表示・フィルタに使われ、誤った値は訂正手段を持たないためである。本文で省略を明示した JMA の地域要約を BSAF に公開する場合も、その要約を全地域の完全な原電文と表示してはならない。

### 5.4 BSAF 形式での別途公開

公開権限のある著者または中継 Bot が、別の `app.bsky.feed.post` を作成する。`tags`・`langs` は互換な値を使い、本文末尾の `（出典：...）`、BSAF Bot 定義の公開等の BSAF 側の要件を満たす。取り込み者が公開する場合はその取り込み者のアカウントの投稿であり、元 Bot のアカウント・署名・CID を再利用してはならない。自分の Bot としての公開定義と原 Bot の定義を区別する。

Bluesky の本文上限に収まらない場合は、重要な条件・指示・出典を失わない別途の要約規則が必要である。文字数だけで末尾を切り捨ててはならない。元本文を編集するときは facets のバイト位置を流用してはならない。バイト位置が変わるためである。

別途公開されたレコードは新しい URI・CID と履歴を持ち、本プロトコルの元投稿とは別に管理する。公開先へ本プロトコルの Nostr 署名は引き継がれない。既存 Bot が自動フォロー・登録されている場合でも、別の中継 Bot が既存利用者に自動的に購読されるとは限らない。

### 5.5 循環再配信の抑制

取り込み側は `(original.uri, original.cid)` と生成済みの本プロトコル投稿の対応を永続記録し、同じ原投稿の再取得・再試行で新しい転載を作らない。BSAF への公開側も、元の本プロトコル投稿と公開済み URI・CID の対応を記録し、再試行で別投稿を増殖させない。

自分の公開アカウント・公開済みレコードを再取り込み対象から除く。取り込み済み BSAF 投稿を別 BSAF 投稿へ自動再公開する経路を有効化してはならない。元 Bot → 取り込み → 公開 → 再取り込みの循環が止まらなくなるためである。本文一致だけで別の原投稿を破棄したり、BSAF の予備タグへ未定義のループ制御タグを挿入したりしてはならない。

## 6. フィルタ・重複表示と配送

BSAF の `type + value + time + target` が異なる Bot 間で一致した場合の折りたたみは表示用の規則である。元の著者・URI・CID・出典・各本文を残し、利用者が展開して確認できるようにする。原 Bot が同じで変換者だけ異なる転載を、「別の Bot からの独立した報告」として件数に数えてはならない。

この組は原電文 ID・ハッシュ・真正性を含まないため、Nostr イベントの重複排除、配送同値、内容の訂正取消、原投稿削除のキーへ流用してはならない（[公的情報の取り込み §7](../README.md#7-配送同値性)）。同じ広域タグを持つ別地域の詳細も折りたたまれ得るため、折りたたみを情報の破棄や完全な意味同値の判定として扱ってはならない。

フィルタは閲覧者の関心に合わせるためのものであり、公的な優先権ではない。`value:7`・`warning` 等の自己申告で保存枠・帯域・即時通知の権限は得られない。BSAF に非対応でも、通常の Nostr 署名・期限・資源上限に従って中継できる。

## 7. 地域・時刻・信頼

`target` を共通 `area` へ変換するのは、Bot 定義と別途のコード体系・境界対応を解決でき、意味が地理的範囲に一致する場合だけとする。対象 Bot と境界対応は [BSAF から災害情報への対応 §2.3](hazard/README.md#23-影響範囲) が定める。`jp-kanto` から都県の範囲や境界を文字列の見た目で創作してはならない。元領域全体を覆う近似は[影響範囲](../../geo/README.md)に従い、不明なら `area` を省略して対象文字列を残す。スポーツチーム等の対象から地理領域を生成してはならない。

`time:` は原イベント時刻、`original.createdAt` は原 Bot の作成時刻、基本投稿の `created_at` は変換投稿の作成時刻である。いずれも配送期限とは異なる。BSAF v1 自体は共通の有効終了・メッシュ配送期限を持たない。

`source:`・Bot 定義・原投稿参照だけでは、公式機関の認証や他投稿を置換する権限は得られない。BSAF に載った取消らしい文章を見て、同じ `type/time/target` の全投稿の拡散を止めてはならない。公的な置換には [公的情報の取り込み §9](../README.md#9-更新による置換と旧版の拡散停止) の認可を別途必要とする。認可された転載の表示は「`orgName` が転載した `botDid` の情報」とし、原 Bot や原発表機関自身の署名があるとは表示してはならない。

## 8. 訂正・削除

同じ at-URI で別 CID の内容を取得しても、既存の署名付き転載は保持し、訂正の新投稿・参照を別途扱う。取得順や CID の辞書順だけで最新版・置換関係を確定してはならない。BSAF v1 のコアタグ自体に一般的な更新・取消参照の形式はない。

原投稿が取得できないことを、削除・機関の取消・危険の解消の証拠としてはならない。原 Bot による削除と、再配信者の本プロトコル投稿の NIP-09 削除・atproto 削除は別の操作である。元 Bot の削除を根拠に再配信者の鍵で元 Bot の署名を作ることはできない。単なる URL の取得失敗から削除要求を発行してはならない。

## 9. データの運搬と例

```text
タグ名: mosimo:ext:dev.jisaku.mosimo.public.bsaf
タグ値: $type 以外の全フィールドの atproto deterministic CBOR を通常 Base64・padding なしで符号化
```

メッシュでは[コア](../../README.md)の共通変換に従って値を生バイト列にする。BSAF の `type:` 等を、意味の異なる Nostr 標準タグや検索目的だけの別名タグへ重複投影してはならない。別の意味のタグとして解釈されるためである。

原 BSAF 投稿を経由せず本プロトコルで新規作成する際の拡張の例である。本文には地震情報と「（出典：気象庁）」等の出典を別途含める。例示の値は実際の災害通知ではない。

```json
{
  "$type": "dev.jisaku.mosimo.public.bsaf",
  "tags": [
    "bsaf:v1",
    "type:earthquake",
    "value:5+",
    "time:2026-10-18T03:00:00Z",
    "target:jp-kanto",
    "source:jma"
  ],
  "langs": ["ja"]
}
```

取り込みではこの型に `original` を追加し、基本本文に原投稿の本文をそのまま置く。32 KiB 上限は本文・本拡張・commit 等を含むイベント全体に適用する。

### 9.1 外部レコードの上限

公式 `app.bsky.feed.post` Lexicon は、本文が最大 300 graphemes・3,000 bytes、`langs` が最大 3 要素、`tags` が最大 8 要素、各タグが最大 64 graphemes・640 bytes である。BSAF 文書の「合計 640 バイト」という説明とは区別する。BSAF 向けの新規出力では、互換性のためタグ総量も 640 UTF-8 bytes 以内とする保守的なプロファイルを用いる。

原投稿がこの保守的総量を超えることだけで、公式 Lexicon 違反と断定してはならない。受信した原タグはそのまま保持し、非互換の表示と互換な新規公開の可否を分ける。

## 10. 部分実装

- 基本対応端末は、本文と通常の配送期限を扱い、未知拡張を保持する。
- BSAF 対応端末は、本拡張のタグ・言語を読み、取得済み Bot 定義で表示・フィルタできる。原 Bot の帰属を確認できない転載は、確認済み Bot 本人の投稿とは区別する。
- 対応 AppView は既存 BSAF レコードと本拡張付き投稿を併置し、同じ原 URI・CID の転載は関係を表示できる。主張だけで原投稿と内容同一・認証済みと断定してはならない。
- BSAF 公開ブリッジは別の権限と出力規則を持つ任意の機能であり、中継端末ごとに実装の有無を選べる。
