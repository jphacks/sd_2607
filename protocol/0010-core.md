# 0010: 基本プロトコル

状態: draft-01 — 合意済み要件の体系化。共通時刻型は合意済み。型のフィールド名等には提案を含み、wire format 全体の確定ではない。

## 要旨

本仕様は、異なるアプリ間で公開テキスト投稿を共有し、ネットワーク不通時は BPv7 で保存・中継し、接続回復時は Nostr と atproto へ接続する基本モデルを定める。位置・公的情報等の意味は任意の拡張へ分離する。

## 1. 適用範囲と文書構成

| 層・機能 | 文書 | 担うこと |
|---|---|---|
| 基本 | 本書 | 投稿単位、基本型、識別子、作成・配送・公開の流れ |
| 著者の拡張 | [0011](0011-extensions.md) | 発信地点、影響範囲、有効期間、注釈、出典等 |
| データ表現 | [0012](0012-bindings.md) | atproto レコード・commit と Nostr・CBOR の対応 |
| メッシュ配送 | [MNDT](mndt.md) | BPv7 と可変な配送状態 |
| 公的情報・BSAF | [0013](0013-public-information.md) | CAP・EDXL・気象庁 XML の取り込み、既存 BSAF との統合 |
| オンラインサービス | [0006](0006-logical-pds.md)・[0007](0007-nostr-relay-profile.md)・[0008](0008-posts-and-labels.md) | 論理 PDS、リレー、Labeler |
| 身元証明 | [0009](0009-identity-attestations.md) | 公式発信者等への帰属 |

既存の合意は [0001](0001-repository-model.md) に記録されている。本書群の「要件」はその合意を整理したもの、「型案」「配置案」は未確定の具体化である。基本仕様のために新しい投稿種別や独自の暗号署名方式を追加しない。本書群はデータ構造と処理の流れを説明し、検証アルゴリズム・適合試験・テストベクトルは扱わない。

## 2. 参加者と責務

| 参加者 | 責務 | 行わないこと |
|---|---|---|
| 発信アプリ | 鍵・DID・リポジトリの保持、投稿作成、両形式への署名 | 他の発信者としての投稿・削除 |
| 中継アプリ | 署名済みイベントの保存・配送、対応する本文の表示 | 著者の本文・拡張の編集 |
| ゲートウェイ | 同じイベントの Nostr 投稿、条件付きのメッシュ投入 | 搬出時の著者署名の付け直し |
| 物理 PDS | Nostr リレー、レコードと操作からの MST 再構築、複製 | 著者の commit の新規署名 |
| 論理 PDS | DID が指す正規公開 endpoint、atproto 同期の提供 | 無調整な複数ホストを正規公開元とすること |
| 対応 AppView | 独自 Lexicon と既存 BSAF の収集、索引・一覧・地図 | 元レコードを書き換えたものを原投稿として扱うこと |

一つの実装が複数の役割を持てる。基本本文を表示するだけのクライアントに PDS の処理は要求しない。

## 3. 基本データ型（型案）

以下は説明用の TypeScript 風記法であり、実装コードや Lexicon 定義ではない。

| 型 | 論理上の値 | 表記・用途 |
|---|---|---|
| `Text` | Unicode 文字列 | UTF-8。署名後に改行・Unicode 正規化を変更しない |
| `integer` | 整数 | atproto の範囲内。巨大整数を JavaScript の number へ丸めない |
| `Timestamp` | 絶対時刻 | atproto `datetime` に適合する UTC・末尾 `Z` の日時文字列。秒未満は任意で固定桁数を要求しない |
| `Microdegrees` | 整数 | 緯度・経度。100万分の1度を1とする固定小数点表現 |
| `Millimeters` | 整数 | 円の半径・測位精度等の距離。1ミリメートルを1とする固定小数点表現 |
| `Bytes` | 生バイト列 | CBOR は byte string。本プロトコルの独自 Nostr タグでは通常の Base64・paddingなし。標準フィールド・CID は既存規則のまま |
| `Did` | DID 文字列 | 本プロトコルの発信者は `did:plc` |
| `Cid` | CID | 表示は文字列、atproto 内のリンクは標準 CID link |
| `RepositoryPath` | collection と record key | 投稿は `dev.oriom.mosimo.post/<record-key>`。record key の生成方式は未決定 |
| `AtUri` | atproto レコードの場所 | `at://<DID>/<collection>/<record-key>` |
| `NostrEventId` | Nostr のイベント識別子 | 32 バイトの値。Nostr JSON は小文字 hex |

atproto データモデルでは float を使用できない。文字列・整数・真偽値・bytes・CID link・配列・文字列キーのオブジェクト・null を利用する。`null`、省略、空配列は同じ意味ではない。具体的な値域・長さ・要素数の上限は未決定であり、無制限という意味ではない。

### 3.1 共通時刻型（合意済み）

`Timestamp` は UTC・末尾が大文字 `Z` の日時文字列とし、atproto の `datetime` 形式に適合させる。作成時刻・配送期限・有効期間・出典内の原発表時刻等に共通で用いる。

```text
2026-10-17T12:34:56Z
2026-10-17T12:34:56.789Z
```

- 秒までを含め、秒未満は必要な精度がある場合だけ付ける。固定の小数桁数は要求しない。小数桁数の資源上限は別途定める。
- 受信済みの文字列は、末尾ゼロの削除・精度の切り詰め・日時ライブラリ経由の再整形等で変更しない。同じ瞬間を表しても文字列が変わると元レコードの CID が変わり得る。
- 原情報のオフセット付き時刻は、新しい変換投稿を作成する際に UTC へ変換する。原表記が必要なら出典の形式別情報に保持する。既存の署名済み原データを書き換える規則ではない。
- 不明・曖昧な時刻を現在時刻や Unix epoch のゼロで補わない。任意の時刻項目は不明なら省略できる。必須項目を省略できるようにする決定ではなく、信頼できる時計がない場合の作成方針は別途扱う。
- Nostr の標準 `created_at` は Unix 秒整数とし、`createdAt` の秒未満を切り捨てる。レコードの元の `createdAt` は Nostr 独自タグに同じ文字列で保持する。
- BPv7・外部の原文・標準 Label・将来選定する証明書形式等が固有に持つ日時の符号化は、その標準に従う。本型を理由に書き換えない。

### 3.2 座標・距離の整数表現（合意済み）

バンドルのサイズ削減を重視し、共通の座標・距離は十進小数文字列ではなく、単位を固定した整数とする。

| 量 | 保存単位 | 例 |
|---|---|---|
| WGS 84 緯度・経度 | 100万分の1度 | 35.123456度 → `35123456` |
| 円の半径・測位精度 | ミリメートル | 2500メートル → `2500000` |

atproto のレコードとその CBOR では整数として格納する。Nostr の自己完結した拡張タグでは、内部 CBOR に整数のまま保持し、タグの値全体を Base64 で運ぶ。基本項目や標準タグとの直接対応で数値をタグの値へ出す場合は整数の十進文字列とし、レコードを構成する際は整数型へ戻す。単位を明示する説明用フィールド名は `latitudeMicrodegrees`・`longitudeMicrodegrees`・`radiusMillimeters`・`accuracyMillimeters` とする。正式なフィールド名には未決定事項が残る。公式のタグ名・型名は [0014](0014-namespaces.md) に従う。

固定単位は表現の分解能であり、測位の実精度を保証しない。表示は度・メートルへ換算できる。原情報がより細かい値を持つ場合の丸め・誤差・範囲の包含、最大距離等の資源上限は別途定める。受信した整数を中継者が再量子化しない。

メッシュ用 CBOR は共通の拡張タグの値を生バイト列へ戻せる。内側の座標・距離は既に CBOR integer であり、拡張固有の型を知る必要はない。直接表現した既知タグでは、対応規則に従って整数文字列を CBOR integer にする可逆な型変換も採用する。バイト列を表す既知の文字列も、完全に元へ戻せる場合は byte string にできる。運び方も未知のタグ・変換条件に合わない値は元の文字列、日時も内部・直接表現とも原表記のまま保持する。具体的なタグ別規則・識別方法は [0012 §4](0012-bindings.md#4-メッシュ用-cbor配置案) で今後固定する。サイズ削減率は未測定であり、全ての値が必ず短くなるとは保証しない。

### 3.3 三層の独立した版管理（合意済み）

| 対象 | 識別方法 | 互換性を壊す変更 |
|---|---|---|
| 基本プロトコル | Nostr の `mosimo.oriom.dev:version` タグ | 基本タグ・必須項目・共通の対応規則等を変更する場合に基本版を変える |
| 各拡張型 | 個別の `$type` | 新しい型参照を割り当てる。共通の拡張 `version` フィールドは追加しない |
| メッシュ用 CBOR | payload 自身の符号化形式の版 | payload の配置・文字列への復元規則等を変更する場合に符号化版を変える |

三つの版を同じ値に揃えることは要求しない。拡張の追加・未知の型の出現だけで、基本版やメッシュ符号化版を変更しない。メッシュ表現だけの変更でレコード型を変える必要もない。基本タグ内の版と CBOR payload の版は別の役割であり、どちらも単に投稿の更新回数や atproto commit の `version: 3` を意味しない。

各拡張型は Lexicon の進化規則に従う。互換な任意フィールド追加等では同じ `$type` を使えるが、既存フィールドの型・必須条件・意味等を互換性なく変更する場合は新しい型名を使う。古い型名の意味を書き換えず、旧型と新型は別々に識別する。未知の新型も、共通の運び方が既知なら保持・再構成できる。

未知の基本版・メッシュ符号化版を、既知の版と推測して解釈しない。元の Nostr イベントを取得できる場合、Nostr 標準としての署名・本文の扱いと、本プロトコルの意味を解釈できることを区別する。

初期の版の値、版の文字列表記、タグの必須範囲、payload 内の版の正確な位置・値域、新しい型名の命名規則は未確定である。これらの具体化と、三層を独立させる決定を区別する。

## 4. 投稿の構造

### 4.1 本文と任意の拡張

```ts
type Post = {
  text: Text;
  createdAt: Timestamp;
  deliveryExpiresAt: Timestamp;
  extensions: Extension[]; // 拡張がなければ空配列
};
```

| 項目 | 必須 | 意味 |
|---|---|---|
| `text` | 必須 | 拡張に未対応でも読める本文。公的情報では発表元・対象・主要な指示等を本文でも伝える |
| `createdAt` | 型案では必須 | この投稿を作成した時刻。原情報の発表時刻や取得時刻とは別 |
| `deliveryExpiresAt` | 必須 | 著者が署名するメッシュ配送の絶対期限 |
| `extensions` | 型案では必須 | [0011](0011-extensions.md) の著者署名付き拡張一覧 |

DID・Nostr 公開鍵・event ID・record CID・commit CID は、各形式の外側の情報から得る。本文にこれらの識別子を重複埋め込みすることは要求しない。`Post` は本文の意味を説明する構造であり、これだけで署名付きの配送単位を表すものではない。

### 4.2 投稿単位（合意済み）

```text
1投稿
  ├─ 著者自身のリポジトリへ1レコード追加
  ├─ その状態を指す端末署名済みatproto commitを1件生成
  └─ 本文・commit・適用元CID・path・レコードを表すNostrイベントを1件生成
```

通常投稿・訂正・補足・追認にこの単位を適用する。投稿の commit 等を別の Nostr イベントに切り離す方式や、複数投稿のバッチ commit は設けない。PLC 初期操作・鍵対応宣言は繰り返し利用する独立した制御データであり、投稿ごとの同梱は要求しない。

訂正・補足・追認は、対象投稿を参照する新しい投稿である。本人と他者の注釈を区別し、元投稿を上書きしない。注釈本文が自動的に標準 Label になるわけではなく、Labeler の集約配信は別の処理である。

削除は新規本文レコードの追加ではなく、著者端末がレコードを除いた新しい commit と NIP-09 `kind: 5` を発行する制御処理である。複数削除の単位・具体配置は未決定で、通常投稿の型へ無理に押し込まない。

### 4.3 時間の区別

| 時間 | 所有者・用途 | 省略・満了 |
|---|---|---|
| 投稿作成時刻 | 発信アプリ | 原発表・受信時刻の代わりではない |
| 情報の有効期間 | 任意の `validity` 拡張 | 省略は不明。無期限に有効ではない。終了は削除ではない |
| 配送期限 | 通常投稿の基本項目 | 必須。アプリ・運用者の既定期間から確定。中継で延長しない |
| BPv7 Lifetime・経過時間 | 配送層 | 署名付き期限とローカル上限に併せて適用 |
| リレー・PDS の保持期間 | サービス運用 | メッシュ配送期限とは別。永久保存は保証しない |

期限の判定不能と期限内を区別するが、時計不明だけで全中継を禁止しない。詳細は既存の [0001 §1.12](0001-repository-model.md#112-情報の有効期間と配送期限) に従う。

## 5. 作成から公開まで

### 5.1 平時の準備

アプリ初期化時に3用途の鍵・DID・リポジトリを自動準備し、PLC 登録と既定論理 PDS での受け入れを進める。鍵はインストールごとに独立して永続化する。災害時の起動まで登録を待たない。オフライン初回起動等の未登録時だけ、署名済み PLC 初期操作の代理登録を例外経路として使う。

### 5.2 発信

1. 本文と任意の拡張を作り、配送期限を確定する。
2. 独自 Lexicon のレコードを追加して MST を更新し、atproto commit に署名する。適用元は端末が直前に確定した commit の CID とする。初回は適用元なしを明示する。
3. 同じ投稿の本文・レコード・path・commit・適用元 CID を一つの Nostr イベントに表現し、Nostr 鍵で署名する。
4. オンラインなら Nostr リレーへ投稿する。メッシュでは元のイベントを CBOR 表現にして BPv7 の payload で配送する。

署名対象の生成はここで完了する。中継者は本文・タグ・拡張を補修せず、同じイベントを運ぶ。

### 5.3 受信・中継・再接続

本文を扱う端末は Nostr 公開鍵に対するイベント署名を基本とし、DID 認証のための PLC 情報取得を待たない。解釈できる拡張だけを表示・配送のヒントに使い、未知の著者拡張は元の表現を保持する。保持できなければ改変して転送せず、転送を見送る。

オンラインに戻った端末は、元の署名済みイベントを対応物理 PDS のリレー等へ投稿する。リレー候補は同梱・キャッシュ・AppView の一覧・Nostr 経由の発見を併用する。取得した全情報の無条件なメッシュ再投入はしない。

### 5.4 PDS・AppView

PDS はレコード・path・変更操作から適用元の状態を更新し、元の署名済み commit が指す MST を再構築する。MST ノード・包含証明はメッシュ入力へ同梱しない。履歴不足なら公開を保留し、推測した状態を正本にしない。欠落履歴の探索は今回の対象外である。

標準 atproto 同期向けの MST・CAR は PDS が構築する。DID ごとに一つの論理 PDS endpoint を指定し、背後で物理 PDS が複製する。AppView は独自 Lexicon と BSAF を、それぞれの著者・識別子を残して収集する。

## 6. 識別子と重複の扱い

| 識別子 | 同一とする対象 | 同一を意味しないもの |
|---|---|---|
| Nostr event ID | 同じ署名対象イベント | 同じ本文、同じ原発表 |
| record CID | 同じ符号化済みレコード内容 | 同じ著者、同じ repository path |
| atURI | 著者のリポジトリ内のレコードの場所 | 内容の特定版 |
| commit CID | 同じ署名済み commit | 同じ本文、単一レコード |
| BPv7 Bundle の識別 | 配送層の Bundle | 同じ Nostr イベントの別 Bundle |
| 配送同値キー（具体形式未定） | 信頼済み変換者による同じ原情報の配送抑制 | event ID・署名・個々のリポジトリの統合 |

AppView と Nostr の二経路の対応には、その投稿の DID・path・record CID 等を用いる設計を具体化する。本文一致だけで同じ投稿と断定しない。BSAF の表示折りたたみキーは配送同値キーとは別である。

## 7. 公開性と保証の境界

初期仕様は公開情報のみを扱う。位置・影響範囲による閲覧制限、全端末への配送、全コピーの削除、内容の真実性・GPS の真正性は保証しない。署名・DID への帰属・公式機関への帰属を区別する。個別通信、メディア本体、全面的な逆変換、端末状態の巻き戻り対応は延期する。

## 8. 今後固定する項目

公式の NSID・型名・タグ名は [0014](0014-namespaces.md) に割り当て済み。正式な表示名称・版の識別、wire 上のフィールド・値の配置・文字列のサイズ上限等は [0012](0012-bindings.md) と [未決事項](0003-open-questions.md) で管理する。これらの未確定値を合意済みの投稿単位と混同しない。
