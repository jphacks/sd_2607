# 0007: 物理 PDS の Nostr リレープロファイル

状態: draft-00（役割・受け入れ方針・NIP-11 拡張の採用は合意済み。kind・タグ・制限・具体スキーマは未定）

## 1. 目的と構成

物理 PDS は収集・復元サーバーであると同時に、標準 Nostr クライアントが接続できる Nostr リレーとして機能する。本プロトコルの投稿・取得に適したリレーを提供し、一般リレーの受け入れ方針だけに依存しない。

クライアントが物理 PDS のリレーに接続できる場合は、その接続へ元の署名済みイベントを直接投稿し、必要なイベントを直接取得・購読できる。一般リレーを先に経由することは要求しない。対応物理 PDS のリレーを優先的に利用し、一般 Nostr リレーも併用できる構成を目指す。具体的な発見・優先順位・接続数・再試行は未決定。

atproto の正規公開先は論理 PDS の HTTPS endpoint であり、物理 PDS の Nostr WebSocket endpoint と同一とは限らない。一つの物理 PDS が複数グループへ所属しても、イベントの受理だけでその全グループの正規公開対象になるとは扱わない。

## 2. 標準 Nostr 動作

NIP-01 の標準イベントと WebSocket の投稿・取得・購読を提供する。単なる独自 HTTP ダウンロード口や、他リレーへの転送専用プロキシとはしない。

- クライアントから `EVENT`・`REQ`・`CLOSE` を受け付ける。
- 規則に従い `OK`・`EVENT`・`EOSE`・`CLOSED` 等で応答する。
- event ID と BIP-340 署名を検証し、元の署名対象フィールドを維持する。
- 本プロトコルのイベントを保持し、保存データの取得と新着の購読を提供する。
- 合意済みの NIP-09 削除要求の処理と整合させる。

「Nostr リレーとして機能する」は全 NIP を実装する意味ではない。能力・制限の公開には NIP-11 と本プロトコル向け追加情報を用いる。それ以外の追加 NIP の必須範囲は未決定。一般用途の全 kind の無制限な受け入れも保証しない。

## 3. 本プロトコル向けの受け入れ方針

本プロトコルで扱うイベントについて、独自タグがあることや、オフライン配送で `created_at` が古くなったことだけを理由に拒否しない方針とする。未知の著者署名付き拡張は既存の保持・中継原則に従う。

これは不正署名・不正形式・サイズ超過・資源枯渇・削除済みイベント等まで無条件に受け入れる意味ではない。具体的な上限、保持期間、追放、未来時刻や時計ずれへの対応は今後定義する。独自タグを保持することと、任意の複数文字タグ名で検索できることは区別し、検索用タグと索引要件は別途定める。

メッシュ配送期限と、リレーでの保存・取得可能期間は別である。メッシュ配送期限の満了だけで、リポジトリ復元に必要な情報まで一律に破棄する規則は採用していない。具体的な保存方針は未決定であり、永久保存は保証しない。

古い Nostr イベントの受理と、atproto の正規公開先としての検証・状態更新は別段階とする。受理したイベントから古い commit を得ても、現在の検証済みリポジトリを無条件に巻き戻さない。

## 4. PDS 復元・グループ間共有との接続

リレーの受理済みイベントを収集・復元処理へ渡す。自グループの DID は検証と運用方針の範囲で復元・公開し、他の対応グループ宛ての未共有 commit は [0006](0006-logical-pds.md) の通知＋必要時取得で正規公開先へ共有する。

共有元は自分が提供する Nostr リレーも取得先として案内でき、受信側はイベント ID 等で元の署名済みイベントを取得する。一般リレーの保持だけに依存しない。正確な取得・フィルタ形式、復元用ブロックの配送形式、保持・可用性の確認は未決定。

Nostr の `OK` による受理は、PLC 登録、完全なリポジトリ検証、論理 PDS 内の冗長保存、atproto Relay への取り込み、AppView 表示の完了を意味しない。完了状態の確認方法は別途定義する。

## 5. 発見と信頼

本プロトコル対応の物理 PDS のリレーは、NIP-11 の Relay Information Document を提供し、本プロトコル向けの能力・方針を追加情報として公開する。標準の対応 NIP・制限の項目を再利用し、追加情報には対応バージョン、対象イベントの受け入れ・保持方針、関連する論理 PDS グループ等を表す。具体的な項目名・型・必須範囲・版管理は未決定である。

NIP-11 はリレーの WebSocket URI に対応する HTTP(S) URI へ `Accept: application/nostr+json` を指定して取得する。独自情報は標準項目の意味を変更せず、未対応クライアントが無視できる追加項目として設計する。クライアントは能力・制限を確認し、対応リレーを優先利用するための情報として使える。具体的な選択手順とグループ所属の認証は引き続き未決定である。

能力の自己申告だけで、正規 PDS グループの参加権限や公的情報の変換者としての信頼を得ることはない。Nostr リレーの受け入れ方針と、公的情報の信頼リストを区別する。

### 5.1 複数経路のリレー発見

初期候補をアプリに同梱し、取得済み候補をキャッシュする。既知 AppView のレコードからの一覧取得・更新と、Nostr 経由での候補発見も組み合わせる。AppView に到達できないことだけで初回接続や接続回復後の投稿を止めない構成とする。Nostr 経由の具体的な発見方式は未決定であり、世界共通の単一ブートストラップ手順の存在を前提としない。

同梱候補には、本プロトコル対応の物理 PDS のリレーに加え、独自拡張を持たない既存の著名な一般 Nostr リレーも含めてよい。世界共通の固定リストは規定せず、アプリ・運用者が設定する。具体的な採用先、稼働・利用条件の確認、一覧の更新・失効方式は未決定である。

候補の到達性と NIP-11 の能力・制限を確認して利用する。ただし、本プロトコル用追加情報がないことだけで一般リレーを利用対象外にはしない。一般リレーへの投稿・取得も標準 Nostr として試みられるが、独自タグ・古いイベントの受け入れや保持を保証しない。能力情報の未取得と、対象イベントを明示的に扱わないリレーを区別する具体規則は今後定義する。

対応物理 PDS のリレーを優先しつつ、一般リレーを併用できる。候補一覧への掲載や能力の自己申告だけで、グループ所属や情報源の信頼を認定しない。接続数、送信量、再試行、古いキャッシュの扱い、候補情報の発行者の信頼規則は未決定である。
