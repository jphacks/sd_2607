# 0001: リポジトリ正本モデル

状態: 設計中（部分合意）

## 1. 合意事項

端末が生成・署名した atproto リポジトリを正本とする。Nostr と BPv7 はその配送を担う。収集サーバーは端末の署名済み状態を検証・復元・複製するものであり、独自に組み直した状態を端末署名済みの状態として扱わない。

### 1.1 発信者 ID の境界

発信者 ID・秘密鍵・リポジトリは、アプリのインストール単位で独立させる。同じ物理端末にある異なるアプリでも共有しない。秘密鍵は当該インストール内で永続化し、別端末へ引き継がない。

異なるアプリ間の相互運用は、共通プロトコルによる投稿の受信・検証・中継で実現する。同じ発信者 ID の共有は前提にしない。他アプリの投稿を中継できることは、その著者として投稿・削除できることを意味しない。

再インストール、OS バックアップ復元、状態の巻き戻りの扱いは別途定義する。

### 1.2 投稿の単独検証と表示

過去の投稿やリポジトリ状態を取得していなくても、投稿内容を含む Nostr イベントの著者署名を検証して表示できることを必須とする。投稿内容は Nostr の署名対象に含める。

Nostr 署名の検証済み状態と、atproto の署名済みリポジトリ状態への包含の検証済み状態を区別する。前者だけで後者が成立したと扱ってはならない。Nostr 公開鍵と DID の対応の検証方式は未決定であり、Nostr 署名だけで DID の著者として認証されたとは扱わない。

単独検証のために MST 包含証明を必須とする必要はない。PDS による状態復元・検証に必要なデータの配送形式は引き続き未決定である。

著者署名は内容の真実性、GPS 位置の正確性、現在まで撤回されていないことを保証しない。削除要求を受信した場合の処理は次節による。

### 1.3 本文と構造化データ

Nostr イベントの `content` は人がそのまま読める本文とし、CAR や CBOR の Base64 表現等を本文の代わりに格納しない。独自拡張を解釈しないクライアントにも本文を提供する。

対応クライアントは構造化データを読み、地図表示などのリッチな表現を提供する。本文と構造化データはいずれも著者署名で保護する。構造化データの具体的な配置・スキーマ、atproto レコードとの対応、重複削減の符号化方式は未決定である。

### 1.4 発信地点と影響範囲

発信地点は任意の構造化データ単位（論理的な「発信地点ブロック」）とする。存在し、解釈できるクライアントは表示に利用できる。存在しないことや未対応であることを理由に本文の受信・検証・表示を拒否しない。具体的な表示方法はクライアントが定める。

この「ブロック」は論理的な拡張単位を意味し、BPv7 extension block への配置を確定するものではない。発信地点を配送層だけの可変データにはせず、公開する発信地点は著者署名の対象に含める。具体的な符号化と各層への対応は未決定である。

発信地点と、投稿内容が関係する影響範囲は独立した概念とする。発信地点は省略でき、公開時は精度を落とせる。配送範囲の絞り込みには原則として影響範囲を用いる。署名された座標は著者による申告であり、実際の現地滞在や GPS の真正性を証明しない。

### 1.5 地理情報と配送

影響範囲は表示の絞り込みと配送の優先・抑制に使うヒントであり、範囲外への転送を一律に禁止する境界ではない。地域外のゲートウェイへ到達するための中継を許容する。地理情報による秘匿やアクセス制限は提供しない。

寿命・hop 上限・保存量・帯域上限等の配送制約は影響範囲とは別に定める。位置情報を持たないノードも、ローカルな資源上限の範囲で配送に参加できる。具体的な地域内優先・範囲外抑制・ゲートウェイ搬出のアルゴリズムは未決定である。

影響範囲も任意の論理的な拡張単位（「影響範囲ブロック」）とする。省略時、または受信ノードがその拡張を解釈できない場合は地域不明として扱い、本文の受信・検証・表示を拒否しない。地域不明は全世界対象や高優先度を意味せず、地域内優先の加点を与えない。通常の配送上限内で中継できる。発信地点を影響範囲として自動的に代用しない。

初期仕様の影響範囲は円と地域コードを対象とし、多角形は対象に含めない。地域コードには行政区域コードではなく全球グリッド方式を採用する。独自の地理区分や特定の国だけに依存する方式は避け、既存の公開された方式を再利用する。既存アプリへの組み込み負担を小さくするため、行政境界データの事前搭載や外部サーバーへの照会なしでセルの範囲と位置の包含を計算できる方式を選ぶ。符号化・領域判定の実装コードまで不要になることは意味しない。具体的なグリッド方式、精度・セル数の上限、円の座標系・半径単位・符号化は未決定である。

### 1.6 atproto のレコード形式と BSAF

本プロトコルの atproto 表現は独自 Lexicon を本体とする。本文と任意の構造化拡張を定義し、`app.bsky.feed.post` のタグに全情報を詰め込む方式は採用しない。具体的な NSID・スキーマ・上限は未決定である。

AppView は本プロトコルのレコードに加え、既存の BSAF 投稿も別の入力として収集し、一覧・地図等で統合して扱う。BSAF を本プロトコルへ適合させるために元レコードを書き換えたり、元著者の署名を捏造したりしてはならない。元の著者・出典・識別子を保持する。BSAF 入力を Nostr・メッシュへ再配信するか、その場合の変換者の署名と帰属は未決定である。

既存の Bluesky クライアントが独自 Lexicon の投稿を表示することは保証しない。Nostr の人が読める本文と、対応 AppView による表示を提供する。BSAF の対象地域コードから地理境界を解決できない場合、正確な領域を推測して生成しない。

比較上、既存投稿のタグ方式は通常の Bluesky 投稿としての表示に優れる。一方、独自 Lexicon は地理形状・任意項目・将来拡張を明示的に定義でき、既存投稿の本文・タグ制限に本プロトコル全体を合わせずに済む。本設計では後者を優先する。

### 1.7 未知の拡張と部分実装

未知の著者署名付き拡張は、解釈せずとも署名検証に必要な表現を保持して中継することを基本とする。署名対象の情報を削除・並べ替え・書き換えしてはならない。保持できない場合は改変して中継せず、中継を見送る。未知の拡張があることだけを理由に、既知の本文の表示を拒否しない。

この原則は任意の拡張に適用し、未知のプロトコル版や署名方式まで検証済みとするものではない。サイズ上限超過や不正形式は資源保護のため拒否できる。具体的な上限と拡張の識別・符号化方式は未決定である。

中継者が付ける配送用メタデータは、著者署名付き拡張と区別し、各層の規則に従って更新・省略できる。BPv7 の未知の拡張ブロックは BPv7 の処理フラグと規則に従う。

### 1.8 訂正と更新

初期仕様は、新規投稿、元投稿を参照する訂正の新規投稿、および削除を扱う。既存投稿レコードの内容を上書きする更新操作は設けない。訂正は新しい repository path に作成し、元投稿への参照を構造化データに含める。参照形式は未決定である。

訂正投稿は単独でも意味の分かる本文を持つ。対応クライアントは元投稿に訂正の存在を表示できる。元著者による訂正と、別の著者による訂正の主張を区別する。訂正が存在しても元投稿の削除を意味しない。訂正対象より先に訂正が届くこと、訂正が未到着の端末に元投稿が残ることを許容する。

### 1.9 可逆変換と配送状態の境界

決定的な相互変換の保証対象は、本プロトコルの交換データが保持する著者署名付きデータとする。本文・構造化拡張・署名済み commit・必要なレコード情報・各署名について、規定の往復変換後も元の署名対象バイト列を復元できる形式を定義する。Nostr のイベント ID と署名、atproto の commit CID・record CID と署名を維持する。

素の atproto commit 単体には Nostr の署名やタグ等を保持する標準フィールドがない。したがって、相互変換の単位は commit 単体ではなく、必要な情報を併せ持つ本プロトコルの交換データとする。具体的な配置と符号化は未決定である。

BPv7 の hop count・経過時間・直前ノード等の可変な配送状態は著者署名付きデータから分離する。経路ごとに異なる Bundle 全体のバイト単位の復元は保証しない。Nostr からの再バンドル時に配送状態をどのように初期化できるか、寿命や hop 制限のリセットによる再拡散をどう抑止するかは別途定義する。

### 1.10 インターネットからメッシュへの投入

条件付きのインターネットからメッシュへの配送を初期仕様に含める。取得した全投稿を無条件に投入する方式は採用しない。公的発表に基づく情報等、情報源を特定でき、誰が持ち込んでも同じ元情報として扱える仕組みを求める。

投入者によらない同値性は元情報の同値性として実現し、投入者ごとの署名付きイベントは別物として維持する。元情報が同値の複数イベントは、例外的に配送上の同一パケットとして扱い、冗長な配送を抑制する。これは BPv7 の Bundle ID、Nostr event ID、atproto の commit CID が同一になることを意味しない。

元情報の同値性に基づく配送用の重複排除と、署名付きイベント自身の識別を分離する。署名付きイベントを合成・改変しない。具体的な配送同値キー、正規化、代表イベントの選択、他イベントの保持方針は未決定である。内容が異なるイベントや、原情報の訂正・取消を同一の配送対象として潰さない。

情報源の記載と情報源による真正性の保証は区別する。例外的な配送重複排除は、受信ノードが信頼する情報源・変換者に基づき、受信データの検証後に適用する。自己申告の同値キーや未検証の inventory 広告だけで配送済みとは扱わない。未信頼の投稿は通常のイベント ID 単位で扱い、別途レート制限する。

初期運用では、受信者が既定の複数の取り込みサーバーを信頼する方式を採用する。既定では、信頼する取り込みサーバーのうち1者の有効な署名で受理できる。複数者の一致は追加の確認として扱い、必須にしない。受信者の方針として複数者の一致を要求できる余地を残す。信頼する1者の侵害で誤情報を受理し得るリスクを許容する設計である。信頼対象はアプリ・運用者が選択できる。信頼する取り込みサーバーが生成した署名付きイベントは、任意の中継者が運べる。中継者自身を情報の変換者として信頼する必要はない。

将来的には気象庁等の発表機関自身が署名して直接発信する形を目指す。発表機関の鍵の認証・管理、既定の信頼リストの配布・更新・失効、原情報の識別子と版の対応規則は未決定である。

再取得・再バンドルを無制限な再拡散の理由としてはならない。投入対象の選択、重複排除、期限、配送上限と、削除・訂正の伝播に関する具体的な規則は未決定である。

### 1.11 削除

追加専用モデルには制限しない。削除時は著者端末が、対象 Nostr イベントへの NIP-09 削除要求と、対象レコードを MST から除いた状態の atproto commit をそれぞれ署名・発行する。両者の対応を配送データで表現する。具体的な形式と対応関係の検証規則は未決定である。

収集サーバーは NIP-09 だけを根拠に著者の新しい atproto commit を生成してはならない。削除要求のみ到着した場合と、署名済みリポジトリの削除が検証できた場合を区別する。

削除は協調するノードへの要求であり、全コピーの消去を保証しない。削除要求が対象より先に到着する場合に備え、再表示・再配送を抑制する削除要求の記録を配送管理側で保持する。保持期間・対象・検証規則は未決定である。古い署名済み状態が有効だったことと、それを現在の表示・配送対象とすることを区別する。

## 2. 標準仕様に由来する制約

atproto repository v3 の commit の `data` は現在の MST ルート CID である。`prev` は過去の commit の CID を指す nullable フィールドであり、過去の MST ルート CID ではない。標準では通常 `null` である。

commit はレコード本文や変更操作の一覧を含まない。したがって、commit オブジェクトだけを集めてもレコード集合は復元できない。

同一の repository path → record CID の写像からは、標準の MST 構築規則に従って同一のルート CID を再現できる。必要なレコードと正確な path が別途取得できれば、MST ノードそのものを全て配送せず、受信側で再構築して署名済み commit の `data` と照合する設計は可能である。

commit の署名検証と、レコードがその commit の状態に含まれることの検証は別である。後者には再構築した木または包含証明等が必要となる。署名鍵と DID の対応の検証方式は未決定である。

## 3. 未決事項

- 削除の配送形式、順序逆転時の処理、削除要求記録の保持方針。
- 訂正対象の参照形式と、訂正の連鎖・複数訂正の表示。
- 配送形式に CAR slice を使うか、commit と path・レコードから再構築する独自形式を使うか。
- 欠落時の取得、再構築上限、状態の検証段階。
- 単一 writer の範囲、競合・端末状態の巻き戻りへの対応。
- DID と鍵、標準 atproto ネットワークへの公開と PDS 冗長化。
