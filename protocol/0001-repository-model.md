# 0001: リポジトリ正本モデル

状態: 設計中（部分合意）

本書は合意の記録である。体系化した基本モデルと型案は [0010](0010-core.md)・[0011](0011-extensions.md)、データ配置案は [0012](0012-bindings.md)、公的情報・BSAF は [0013](0013-public-information.md) を参照する。

## 1. 合意事項

端末が生成・署名した atproto リポジトリを正本とする。Nostr と BPv7 はその配送を担う。収集サーバーは端末の署名済み状態を検証・復元・複製するものであり、独自に組み直した状態を端末署名済みの状態として扱わない。

### 1.1 発信者 ID の境界

発信者 ID・秘密鍵・リポジトリは、アプリのインストール単位で独立させる。同じ物理端末にある異なるアプリでも共有しない。秘密鍵は当該インストール内で永続化し、別端末へ引き継がない。基本経路では、インストール後の初回起動等、平時に実行可能なアプリ初期化で鍵・DID・リポジトリを自動的に準備し、オンラインでアカウント登録を進める。災害時機能の起動まで準備を待つ設計にはしない。

異なるアプリ間の相互運用は、共通プロトコルによる投稿の受信・検証・中継で実現する。同じ発信者 ID の共有は前提にしない。他アプリの投稿を中継できることは、その著者として投稿・削除できることを意味しない。

atproto 用と Nostr 用の署名鍵は用途別に分け、同じ秘密鍵を共用しない。1インストール＝1発信者という境界は維持し、その内部で鍵セットとして生成・永続化する。二つの公開鍵の対応は、両方の鍵で署名する鍵対応宣言で示す。初回に生成する独立した小さなデータとし、必要に応じて投稿と一緒に配送できるようにする。宣言には用途を区別する識別子・仕様バージョン、発信者 DID、atproto 用公開鍵、Nostr 用公開鍵と、その DID の発信に当該鍵の組を用いることへの同意を含め、両鍵で署名する。初回は3用途の鍵を生成し、PLC 初期操作を署名して DID を決定した後、DID を含む鍵対応宣言を生成・署名する。鍵対応宣言を PLC 初期操作へ含めることは要求しない。

鍵対応宣言は両秘密鍵の保持者による対応付けへの同意を検証するものであり、実在する人物・機関の本人確認、特定 DID に対する鍵の正当性、現在までの未失効をそれだけで証明するものではない。標準の DID Document や DID の認証と区別する。PDS による正規の atproto リポジトリとしての検証・公開や、DID の認証済み表示では、宣言内の atproto 公開鍵が、検証に用いる PLC の状態において宣言内の DID のリポジトリ署名鍵として認められていることを別途確認する。通常のメッシュ受信・中継・本文表示には、この DID 認証を要求しない。どの PLC の状態を用いたか、現在の鍵・失効まで確認できたかを区別する。署名対象の符号化、配送形式、鍵更新・失効時の規則は未決定である。

atproto は ECDSA、Nostr は BIP-340 Schnorr を用いる。PLC 管理鍵も投稿署名鍵から分離し、Nostr 署名鍵・atproto リポジトリ署名鍵・PLC 管理鍵の3用途の鍵を端末で保持する。PLC 初期操作と、その後の鍵・PDS 設定等の変更操作は PLC 管理鍵で署名する。PLC 管理鍵は発信端末だけが保持し、PDS や代理登録ノードへ渡さない。複数の PLC 管理鍵による回復構成を必須とはしておらず、具体的な回復方針は未決定である。

初期仕様で端末が生成する Nostr 署名鍵・atproto リポジトリ署名鍵・PLC 管理鍵の曲線は、全て `secp256k1` に統一する。Nostr は BIP-340 Schnorr、atproto と PLC は ECDSA を用い、曲線の統一は署名方式の統一や秘密鍵の共用を意味しない。初期の端末鍵生成では `P-256` を選択肢とせず、ハードウェア保護等の必要に応じた将来の対応は別途検討する。この決定は機関の身元証明用ルート鍵・中間鍵やサービスの Label 署名鍵の曲線を指定するものではない。

鍵生成・保管、独立生成と用途別導出の選択、更新・失効は今後定義する。鍵の分離だけで、同じアプリ全体の侵害から保護されるとは扱わない。

再インストールの扱いは別途定義する。OS バックアップ復元等による端末状態の巻き戻りへの対応は [延期課題 §9.5](0003-open-questions.md#95-端末状態の巻き戻りへの対応) とし、今回は検出・発信再開・回復・分岐解消を設計しない。復元時の新規 DID 発行も採用済みとはしない。

### 1.1.1 平時の自動登録と例外的な代理登録

DID method は `did:plc` を採用する。基本経路は、平時のアプリ初期化で発信アプリが初期操作を生成・署名し、そのハッシュから DID を決定して、オンラインで PLC Directory への登録と既定の論理 PDS での受け入れを自動的に進めるものとする。利用者による手動のアカウント作成を前提にしない。PLC 登録と PDS の受け入れ・公開完了は区別する。

初回起動がオフライン等で登録が完了していない場合に限る例外経路として、署名済み初期操作をメッシュ等で独立した制御データとして配送し、受け取ったオンラインノードが PLC Directory への代理登録を試みる。発信端末自身も接続回復後に同じ初期操作を送信できる。通常投稿ごとの初期操作の同梱や、代理登録を全発信者の必須経路にはしない。

代理登録は署名済み初期操作をそのまま送信する行為であり、中継者へ秘密鍵や DID の管理権限を渡すものではない。PLC 仕様は認証不要の HTTP リクエストで署名済み操作の提出を受け付け、操作の署名等を検証する。

全ノードがオフラインの場合に登録完了は保証できない。初期操作のローカル検証と、公開ディレクトリでの登録・解決確認を区別する。既存登録がある場合は初期操作の一致と現在の状態を確認し、重複送信の応答だけで失敗や最新状態を判断しない。具体的な再試行・重複抑止・負荷制限の規則は未決定である。

初期操作は DID Document そのものではなく、その導出元である。`rotationKeys` には端末の PLC 管理用公開鍵を用いる。初期操作の配送形式、管理鍵の回復構成、PDS endpoint、鍵更新・失効と登録確認の伝達方式は未決定である。公開ディレクトリへの依存と、オフライン時に更新・失効を確認できない限界は残る。

### 1.2 投稿の単独検証と表示

過去の投稿やリポジトリ状態を取得していなくても、投稿内容を含む Nostr イベントの著者署名を検証して表示できることを必須とする。投稿内容は Nostr の署名対象に含める。通常のメッシュ受信では、イベント内の Nostr 公開鍵に対してイベント ID・署名を検証し、DID の認証を受信・中継・本文表示の前提にしない。PLC 初期操作・更新履歴・鍵対応宣言を通常投稿ごとに同梱する要件は設けず、それらの取得・検証を待つ必要もない。これは当該鍵による署名と署名対象の非改変を確認するものであり、申告された DID や実在の人物・機関への帰属を保証しない。

Nostr 署名の検証済み状態と、atproto の署名済みリポジトリ状態への包含の検証済み状態を区別する。前者だけで後者が成立したと扱ってはならない。Nostr 公開鍵と DID の対応の検証方式は未決定であり、Nostr 署名だけで DID の著者として認証されたとは扱わない。

本プロトコルの投稿配送には MST ノードや包含証明を同梱する仕組みを定義しない。PDS がレコードと変更操作から MST を再構築する。必要な交換データの具体的なフィールド・符号化は引き続き未決定である。

著者署名は内容の真実性、GPS 位置の正確性、現在まで撤回されていないことを保証しない。削除要求を受信した場合の処理は次節による。

### 1.3 本文と構造化データ

Nostr イベントの `content` は人がそのまま読める本文とし、CAR や CBOR の Base64 表現等を本文の代わりに格納しない。独自拡張を解釈しないクライアントにも本文を提供する。

新規投稿と訂正文の Nostr 表現は `kind: 1` とする。削除要求は NIP-09 の `kind: 5` を用い、PLC 初期操作・鍵対応宣言等の制御データは本文投稿とは別イベントとして定義する。制御イベントの kind と形式は未決定である。

対応クライアントは構造化データを読み、地図表示などのリッチな表現を提供する。本文と構造化データはいずれも著者署名で保護する。Nostr では基本項目・拡張ごとに複数のタグへ分ける方式を採用し、拡張プロトコル間の独立性と検索への活用を優先する。本文以外の全体を一括 CBOR として一つのタグへまとめる方式は採用しない。既定では1拡張オブジェクトを1自己完結タグとし、タグ名の共通接頭辞と完全修飾 `$type`、値の全残存フィールドの CBOR／Base64 という共通方式で運ぶ。拡張タグの出現順から配列を構成し、位置番号は要求しない。未知型でも保持・再構成に専用コードを要求せず、意味を利用する実装だけがその拡張に対応する。標準タグは定義元 NIP の対象 kind・文脈・意味が正確に一致するものだけを使い、それ以外は衝突しにくい名前空間付きの独自タグを用いる。独自タグの一般リレーでの検索は要求せず、検索のためだけに標準の意味を流用したり別名タグ・重複索引を追加したりしない。公式タグ名は [0014](0014-namespaces.md) に割り当て、共通拡張タグは `mosimo.oriom.dev:ext:` と完全修飾 `$type` の連結とする。個別スキーマ・基本項目の値の配置・版の具体表記には未決定事項が残る。

### 1.4 発信地点と影響範囲

発信地点は任意の構造化データ単位（論理的な「発信地点ブロック」）とする。存在し、解釈できるクライアントは表示に利用できる。存在しないことや未対応であることを理由に本文の受信・検証・表示を拒否しない。具体的な表示方法はクライアントが定める。

この「ブロック」は論理的な拡張単位を意味し、BPv7 extension block への配置を確定するものではない。発信地点を配送層だけの可変データにはせず、公開する発信地点は著者署名の対象に含める。具体的な符号化と各層への対応は未決定である。

発信地点と、投稿内容が関係する影響範囲は独立した概念とする。発信地点は省略でき、公開時は精度を落とせる。配送範囲の絞り込みには原則として影響範囲を用いる。署名された座標は著者による申告であり、実際の現地滞在や GPS の真正性を証明しない。

### 1.5 地理情報と配送

影響範囲は表示の絞り込みと配送の優先・抑制に使うヒントであり、範囲外への転送を一律に禁止する境界ではない。地域外のゲートウェイへ到達するための中継を許容する。地理情報による秘匿やアクセス制限は提供しない。

寿命・hop 上限・保存量・帯域上限等の配送制約は影響範囲とは別に定める。位置情報を持たないノードも、ローカルな資源上限の範囲で配送に参加できる。具体的な地域内優先・範囲外抑制・ゲートウェイ搬出のアルゴリズムは未決定である。

影響範囲も任意の論理的な拡張単位（「影響範囲ブロック」）とする。省略時、または受信ノードがその拡張を解釈できない場合は地域不明として扱い、本文の受信・検証・表示を拒否しない。地域不明は全世界対象や高優先度を意味せず、地域内優先の加点を与えない。通常の配送上限内で中継できる。発信地点を影響範囲として自動的に代用しない。

初期仕様の影響範囲は円と地域コードを対象とし、多角形は対象に含めない。地域コードには行政区域コードではなく全球グリッド方式を採用する。独自の地理区分や特定の国だけに依存する方式は避け、既存の公開された方式を再利用する。既存アプリへの組み込み負担を小さくするため、行政境界データの事前搭載や外部サーバーへの照会なしでセルの範囲と位置の包含を計算できる方式を選ぶ。符号化・領域判定の実装コードまで不要になることは意味しない。具体的なグリッド方式は Geohash を採用する。正式な ISO・OGC 規格であることより、小さな組み込み実装と既存利用・Nostr との親和性を優先する。発信地点と円の中心は WGS 84 の緯度・経度を用いる。保存形式はサイズ削減を優先して固定単位の整数とし、緯度・経度は100万分の1度、円の半径・測位精度はミリメートルを1とする。自己完結した Nostr 拡張タグでは内部 CBOR に整数型を保持する。数値を直接タグの値へ出す場合は整数の十進文字列を使い、レコードでは整数型に戻す。表示は度・メートルへ換算できる。原値の丸め・誤差の扱いは未決定である。範囲判定は地表上の二次元領域を対象とし、高度を使わない。異なる座標系・単位の原情報は取り込み側で変換する。精度・セル数の上限、符号化、距離計算法は未決定である。複数の円・Geohash セルを指定でき、その和集合を影響範囲とする。除外領域・差集合・任意の論理式は初期仕様に設けない。解釈できる要素に含まれれば範囲内、それ以外で未対応要素があれば判定不明とし、無視して範囲外と断定しない。要素数・総バイト数に上限を設けるが、具体値は未決定である。詳細は [地理情報](0004-geography.md) を参照する。

### 1.6 atproto のレコード形式と BSAF

本プロトコルの atproto 表現は独自 Lexicon を本体とする。本文と任意の構造化拡張を定義し、`app.bsky.feed.post` のタグに全情報を詰め込む方式は採用しない。レコードの NSID は `dev.oriom.mosimo.post`、公式拡張は `dev.oriom.mosimo.defs#定義名` とする。名前の割り当ては [0014](0014-namespaces.md) に従い、スキーマ・上限には未決定事項が残る。

AppView は本プロトコルのレコードに加え、既存の BSAF 投稿も別の入力として収集し、一覧・地図等で統合して扱う。BSAF を本プロトコルへ適合させるために元レコードを書き換えたり、元著者の署名を捏造したりしてはならない。元の著者・出典・識別子を保持する。BSAF 入力を Nostr・メッシュへ再配信するか、その場合の変換者の署名と帰属は未決定である。

既存の Bluesky クライアントが独自 Lexicon の投稿を表示することは保証しない。Nostr の人が読める本文と、対応 AppView による表示を提供する。BSAF の対象地域コードから地理境界を解決できない場合、正確な領域を推測して生成しない。

比較上、既存投稿のタグ方式は通常の Bluesky 投稿としての表示に優れる。一方、独自 Lexicon は地理形状・任意項目・将来拡張を明示的に定義でき、既存投稿の本文・タグ制限に本プロトコル全体を合わせずに済む。本設計では後者を優先する。

### 1.7 未知の拡張と部分実装

atproto レコードの拡張一覧は、Lexicon の open union を要素とする配列とする。各要素は `$type` と拡張固有フィールドを持つ構造化オブジェクトであり、投稿内に格納する。atproto レコード内で拡張本体を一律に bytes に包む方式と、旧案の共通 `type`・`version`・`value` の包みは採用しない。Nostr で運ぶ際の共通符号化とは区別する。公式名前空間は、使用を承認された `mosimo.oriom.dev` を基点とし、今後必要となる公式のドメイン由来の識別子もこの管理範囲で割り当てる。具体的な割り当ては [0014](0014-namespaces.md) に従う。第三者の型を公式名前空間へ限定しない。基本プロトコル・拡張型・メッシュ符号化形式は独立して版管理する。基本版は `mosimo.oriom.dev:version` タグ、メッシュ符号化版は payload、拡張の非互換変更は新しい `$type` で識別する。未知拡張の追加だけでは基本版・符号化版を変えず、共通の拡張版フィールドは置かない。初期基本版はタグ値の文字列 `"1"`、メッシュ符号化版は固定7要素配列の先頭の整数 `1` とする。個別スキーマ等は未決定。詳細は [0011](0011-extensions.md) を参照する。

拡張は任意とし、誰でも自身の衝突しない Lexicon 名前空間で、共通管理者の承認なしに定義できる。全アプリ・PDS への型一覧や専用コードの追加、受信時のオンラインスキーマ取得を条件にしない。未知の著者署名付き拡張は、解釈せずとも署名検証に必要な表現を保持して中継することを基本とする。署名対象の情報を削除・並べ替え・書き換えしてはならない。保持できない場合は改変して中継せず、中継を見送る。未知の拡張があることだけを理由に、既知の本文の表示を拒否しない。

この原則は任意の拡張に適用し、未知のプロトコル版や署名方式まで検証済みとするものではない。サイズ上限超過や不正形式は資源保護のため拒否できる。拡張の識別・符号化方式は [0011](0011-extensions.md)・[0012](0012-bindings.md) に従う。具体的な資源上限は未決定である。

中継者が付ける配送用メタデータは、著者署名付き拡張と区別し、各層の規則に従って更新・省略できる。BPv7 の未知の拡張ブロックは BPv7 の処理フラグと規則に従う。

### 1.8 投稿単位、訂正・補足・追認

通常投稿と、対象投稿に対する訂正・補足・追認は、1件につき発信者自身のリポジトリに1レコードを追加し、1 commit と1 Nostr 投稿イベントを生成する。一投稿の本文・レコード・repository path・署名済み commit・適用元 commit CID は、その同じ Nostr 投稿イベントに含め、別の投稿イベントに分離しない。これらの複数投稿をまとめるバッチ commit は初期仕様に設けない。削除や ID 宣言等の制御処理は、この追加投稿の単位とは区別する。

投稿 collection `dev.oriom.mosimo.post` のレコードキーは端末生成の atproto TID とする。生成状態を永続化し、同時刻の連続作成や通常動作中の時計の後退でも同じ collection 内でキーを再利用せず単調増加させる。キー内の時刻は表示・期限判定の根拠にせず、DID・collection・キーの組でレコードの場所を識別する。キー単体の世界的な一意性は要求しない。具体的な扱いは [0012 §2.1.1](0012-bindings.md#211-レコードキーの生成合意済み) に従う。端末状態の巻き戻りへの対応は引き続き延期する。

訂正・補足・追認は対象投稿の著者に限らず誰でも発信できる。対象のリポジトリを書き換えるのではなく、発信者自身の新しい repository path に作成し、対象投稿への参照を構造化データに含める。既存投稿レコードの内容を上書きする更新操作は設けない。参照形式は未決定である。

これらの注釈を atproto 上では Label として対象投稿に提示する方針とする。ただし標準 Label は本文レコードとは独立した署名付きオブジェクトであり、レコードの追加だけで自動的に Label になるわけではない。本人署名付きの注釈レコードを正本とし、グループ等の Labeler が独立に検証・集約して自身のサービス DID・鍵で標準 Label を発行する。元の著者は注釈レコードで維持し、本人発行の Label と偽らない。閲覧者が発信者全員を個別の Labeler として購読する構成を必須にしない。利用者の3用途の鍵とサービスの Label 署名鍵は別であり、著者の秘密鍵をサービスへ渡さない。具体的な Label 値・採用基準・本文レコードとの対応・配信・撤回は未決定。詳細は [投稿と注釈・Label](0008-posts-and-labels.md) を参照する。

初期仕様の基本 Label は注釈の存在を示し、件数や存在だけで真偽を自動確定しない。ただし元の注釈発信者・署名・根拠レコードを確認できるようにし、自治体等の確認済み発信者による誤情報指摘を強い判断材料として扱える。集約 Label の `src` と元著者を区別し、自己申告の名称やサービスの署名だけで自治体の公式見解と認定しない。元発信者の身元確認には §1.19 のルート公開鍵と署名チェーンを用いる。証明の具体形式、信頼の重み付け・相反する指摘の扱いは未決定である。

訂正投稿は単独でも意味の分かる本文を持つ。対応クライアントは元投稿に訂正の存在を表示できる。元著者による訂正と、別の著者による訂正の主張を区別する。訂正が存在しても元投稿の削除を意味しない。訂正対象より先に訂正が届くこと、訂正が未到着の端末に元投稿が残ることを許容する。

### 1.9 変換方向と配送状態の境界

初期仕様は Nostr から atproto への復元・公開を対象とし、atproto データだけから Nostr 投稿を生成・復元する逆変換は対象外とする。この判断は、以前の三形態間の全面的な往復変換の目標を限定する。atproto レコードやリポジトリに Nostr 用の署名・イベント復元情報を保持する要件を設けない。

端末が生成・署名した atproto commit と、必要なレコード・path・適用元 commit CID・変更操作を同じ投稿の Nostr 配送データから取得し、元の commit CID・record CID・署名を維持して復元する。対象はこれらの情報を備えた本プロトコルのイベントであり、一般の Nostr 投稿から PDS が著者の atproto commit を新規署名するものではない。通常投稿の初期基本版1のタグ配置は [0012 §3.2.4](0012-bindings.md#324-通常投稿の基本タグ合意済み) に従う。基本タグは各1個、初回の適用元なしは空文字列とする。レコード型は path の collection と同じ `dev.oriom.mosimo.post`、操作は新規追加とし、`record-type`・`action` タグは要求しない。DID・`rev`・root・署名は commit から、各 CID は元データから得る。基本版1のレコードのトップレベルは `$type`・`text`・`createdAt`・`deliveryExpiresAt`・`extensions` の5項目に固定し、任意の追加情報は `extensions` へ集約する。未知のトップレベル項目がある既存レコードは版1の発信・変換対象にせず、項目を削って同じレコードとして扱わない。基本項目の追加は基本プロトコルの版変更として扱う。制御形式・資源上限等は未決定である。

Nostr とメッシュ交換データ間では、保持する元の Nostr イベント ID・署名・署名対象フィールドを復元できることを求める。本プロトコルの独自タグに新たに定義する bytes 項目は、RFC 4648 の通常の Base64（`+`・`/`）で、末尾の `=` padding・改行なしの表現とする。Nostr 標準の `id`・`pubkey`・`sig` と CID の表現は変更しない。メッシュ用 CBOR は既知タグごとの可逆な型変換を採用し、整数文字列・バイト列の既知の符号化文字列を整数・bytes にできる。元の文字列へ完全に戻る場合に限り、タグと値の順序・要素数を維持する。未知タグ・変換条件に合わない値・日時文字列は元のまま保持する。メッシュ符号化形式 v1 は、先頭の整数 `1` と公開鍵・Nostr 作成時刻・kind・タグ一覧・本文・署名の固定7要素配列とする。型変換するタグ名・値の位置と復元規則は [0012 §4](0012-bindings.md#4-メッシュ用-cbor合意済み) の v1 対応表に限定する。共通形式による未知拡張の追加は版変更を要しない。元の Nostr イベントを既に保持している PDS がそれを再配信することは、atproto からの逆変換とは区別し、禁止しない。標準 atproto データだけから元の Nostr イベントを復元できるとは保証しない。

メッシュ符号化形式 v1 の1イベントは、符号化済み CBOR payload 全体で32 KiB（32,768バイト）以下とする。BPv7 のヘッダー・CRC・拡張ブロック等は含めず、断片化前のイベント全体に適用する。各端末はさらに小さい受信・転送上限を設定できる。中継者は署名済みイベントから本文や拡張を削って上限内へ収めず、配送を見送る。Nostr JSON 等の他の表現のサイズ上限とは区別する。詳細は [0012 §4.4](0012-bindings.md#44-payload-のサイズ上限合意済み) に従い、デコード負荷・保存総量・転送総量等の具体上限は引き続き未決定とする。

Nostr を先に署名してその署名を atproto レコードへ格納する案と、Nostr の署名対象外トップレベルフィールドに commit 等を置く案は検討案にとどまり、採用していない。逆変換を成立させるためだけの署名格納や専用イベントは要求しない。

BPv7 の hop count・経過時間・直前ノード等の可変な配送状態は著者署名付きデータから分離する。経路ごとに異なる Bundle 全体のバイト単位の復元は保証しない。Nostr からの再バンドル時に配送状態をどのように初期化できるか、寿命や hop 制限のリセットによる再拡散をどう抑止するかは別途定義する。

メッシュの共通基本経路は BLE GATT とする。スマホ・マイコンを含む参加機器は、BLE 広告・スキャンで発見して GATT で交換できる構成とし、接続済み Wi-Fi LAN に到達できる場合は LAN 上の探索・IP 転送も使える。LAN 経路自体には AP なしの直接 Wi-Fi 接続の構築を含めない。BLE 接続後に双方の能力を交換し、双方が対応する場合は Nearby Connections による別接続を試み、同じ相手との対応を確認して転送経路を切り替えられる。Nearby 非対応・失敗時も GATT で配送を完結でき、Nearby を機器の参加条件にしない。経路切替は高速化や無線方式を保証せず、著者署名付きイベントと保持済みデータを維持する。複数経路の重複は既存のイベント ID で排除し、配送期限・hop 等の制限を解除しない。詳細と未確定の wire 形式は [MNDT §3](mndt.md#3-接触時の処理の流れ) に従う。

BLE の基本実装は central・peripheral の両役に対応し、機器種別で役割を固定しない。本プロファイルでは central＝GATT client、peripheral＝GATT server とし、どちらからも投稿を送受信できる。制約の強い機器の片役だけの部分実装は許容するが、対応役割を明示し、同じ片役だけの2台は直接接続できない。両役対応でも広告・探索の常時同時実行や多数の同時接続は要求しない。詳細は [MNDT §3.2.1](mndt.md#321-ble-の役割と部分実装合意済み) に従う。

GATT は共通の1サービスと方向別2 characteristic を採用する。server から見た RX は client の書込み、TX は server の通知に用いる。能力交換・所持一覧・取得要求・Bundle 等は同じ経路の上位メッセージ種別で区別し、個別の機能・著者拡張ごとに characteristic を増やさない。RX は Write Without Response、TX は Notification とし、相手・OS の能力に応じた分割と、受信側の許容量に従う連続転送を採用する。Bundle 全体の検査・配送用保存後に受理応答を返し、断片受信や GATT 操作成功とは区別する。初版では切断をまたぐ途中再開を行わず、未完了 Bundle は次回接触で先頭から再送する。受理を確認済みの Bundle は接続変更だけを理由に再送せず、応答が不明な場合の再送は既存の重複排除で扱う。受理応答は最終配送・永久保持を保証せず、唯一のコピーの削除を指示するものではない。UUID、フレーム配置、許容量の単位・制御形式等は別途定める。詳細は [MNDT §3.2.2](mndt.md#322-gatt-サービスと共通送受信経路合意済み)・[§3.2.3](mndt.md#323-分割流量制御受理応答合意済み) に従う。

初版の接触時交換では接続の各方向につき進行中の Bundle を1件に制限し、受理・拒否・中止後に次の転送を開始する。双方向は独立し、同じ方向で複数 Bundle の断片を混在させない。許容量の追加や終了応答等の制御は転送中も送信でき、データの許容量が尽きても制御を送れる小さな資源枠を確保する。制御にも別途資源上限を設け、任意の大量データをこの枠へ逃がさない。優先順位は次の Bundle の選択へ適用する。詳細は [MNDT §3.2.4](mndt.md#324-接続内の転送数と制御メッセージ合意済み) に従う。

共通交換メッセージは、数値の種別を先頭に持つ CBOR 配列とし、後続項目を種別ごとの位置で表す。イベント ID・Bundle 断片は生バイト列で運び、GATT・LAN・Nearby で同じメッセージ定義を使う。これは著者署名付きイベント payload とは別の外側の交換形式である。基本種別は `HELLO`・`INVENTORY`・`WANT`・`BEGIN`・`DATA`・`CREDIT`・`RESULT`・`CANCEL` の8種、任意の経路切替用は `ROUTE_OFFER`・`BIND` の2種とする。`RESULT` で保存受理・所持済み・拒否・提供不能・中止確認を区別する。`BEGIN` の全長で受信終了を判断し、独立の `END` は設けない。種別番号・フィールド配置とリンク別の境界・分割は未確定。詳細は [MNDT §3.2.5](mndt.md#325-共通交換メッセージの符号化合意済み)・[§3.2.6](mndt.md#326-共通交換メッセージの種別合意済み) に従う。

### 1.10 インターネットからメッシュへの投入

条件付きのインターネットからメッシュへの配送を初期仕様に含める。取得した全投稿を無条件に投入する方式は採用しない。公的発表に基づく情報等、情報源を特定でき、誰が持ち込んでも同じ元情報として扱える仕組みを求める。

投入者によらない同値性は元情報の同値性として実現し、投入者ごとの署名付きイベントは別物として維持する。元情報が同値の複数イベントは、例外的に配送上の同一パケットとして扱い、冗長な配送を抑制する。これは BPv7 の Bundle ID、Nostr event ID、atproto の commit CID が同一になることを意味しない。

元情報の同値性に基づく配送用の重複排除と、署名付きイベント自身の識別を分離する。署名付きイベントを合成・改変しない。具体的な配送同値キー、正規化、代表イベントの選択、他イベントの保持方針は未決定である。内容が異なるイベントや、原情報の訂正・取消を同一の配送対象として潰さない。

情報源の記載と情報源による真正性の保証は区別する。例外的な配送重複排除は、受信ノードが信頼する情報源・変換者に基づき、受信データの検証後に適用する。自己申告の同値キーや未検証の inventory 広告だけで配送済みとは扱わない。未信頼の投稿は通常のイベント ID 単位で扱い、別途レート制限する。

初期運用では、受信者が既定の複数の取り込みサーバーを信頼する方式を採用する。既定では、信頼する取り込みサーバーのうち1者の有効な署名で受理できる。複数者の一致は追加の確認として扱い、必須にしない。受信者の方針として複数者の一致を要求できる余地を残す。信頼する1者の侵害で誤情報を受理し得るリスクを許容する設計である。信頼対象はアプリ・運用者が選択できる。信頼する取り込みサーバーが生成した署名付きイベントは、任意の中継者が運べる。中継者自身を情報の変換者として信頼する必要はない。

将来的には気象庁等の発表機関自身が署名して直接発信する形を目指す。発表機関の鍵の認証・管理、既定の信頼リストの配布・更新・失効、原情報の識別子と版の対応規則は未決定である。

再取得・再バンドルを無制限な再拡散の理由としてはならない。投入対象の選択、重複排除、期限、配送上限と、削除・訂正の伝播に関する具体的な規則は未決定である。

### 1.11 削除

追加専用モデルには制限しない。削除時は著者端末が、対象 Nostr イベントへの NIP-09 削除要求と、対象レコードを MST から除いた状態の atproto commit をそれぞれ署名・発行する。両者の対応を配送データで表現する。具体的な形式と対応関係の検証規則は未決定である。

MST は repository path → record CID の写像であり、削除するのは対象レコードのエントリであって過去の commit ではない。削除後の状態には新しい署名済み commit を生成する。追加レコードが0件でも commit は生成されるため、投稿レコード追加と同じ単位とは扱わない。過去の commit や第三者の保存コピーの消去を保証しない。

収集サーバーは NIP-09 だけを根拠に著者の新しい atproto commit を生成してはならない。削除要求のみ到着した場合と、署名済みリポジトリの削除が検証できた場合を区別する。

削除は協調するノードへの要求であり、全コピーの消去を保証しない。削除要求が対象より先に到着する場合に備え、再表示・再配送を抑制する削除要求の記録を配送管理側で保持する。保持期間・対象・検証規則は未決定である。古い署名済み状態が有効だったことと、それを現在の表示・配送対象とすることを区別する。

### 1.12 情報の有効期間と配送期限

情報の有効期間とメッシュの配送期限は、別の概念・項目として設ける。有効期間は内容がいつの状況・指示として有効かを表し、配送期限はいつまで新たなメッシュ配送の対象にするかを表す。

投稿・拡張の共通時刻型は、atproto `datetime` に適合する UTC・末尾 `Z` の日時文字列とする。秒未満は任意で固定桁数を要求せず、受信済みの文字列を再整形しない。Nostr の標準 `created_at` は作成時刻の秒未満を切り捨てた Unix 秒整数とし、元の作成時刻は独自タグへ同じ文字列で保持する。外部原情報の時刻は変換投稿作成時に UTC へ変換し、必要なら原表記を残す。不明な任意時刻を現在時刻やゼロで補わない。詳細は [0010 §3.1](0010-core.md#31-共通時刻型合意済み) を参照する。

情報の有効期間は任意とする。省略時は有効期間不明であり、無期限に有効とは扱わない。公的な原情報等に有効期間が明記されている場合は構造化情報として保持できる。有効期間の終了は投稿の削除を意味しない。

配送期限の満了だけで投稿の削除・撤回や内容の無効化とは扱わない。情報の有効期間が不明な場合、配送期限から推測する等により勝手に補わない。再バンドルで著者署名付きの配送期限を延長してはならない。

BPv7 の Lifetime は配送層の制約とし、署名付き配送期限とローカル上限と併せて適用する。通常投稿は著者署名付きの配送期限を必須とする。利用者による毎回の入力は要求せず、アプリ・運用者が設定する既定期間から、投稿作成時に絶対期限を確定して署名する。共通仕様で一つの既定期間を必須にはしない。中継者は発信アプリの既定値を知る必要はなく、署名された期限を用いる。これは著者が許可する配送の上限であり、各ノードはローカルな資源事情により配送を早く打ち切ることができる。長い期限の指定によって、受信側の保持時間・保存量・送信量の上限を解除しない。期限の満了によって著者署名そのものが無効になるわけではない。

配送期限の実施はクライアントの実装・時計・資源状態に依存するベストエフォートとし、全参加者が厳密に遵守することは保証しない。通常投稿に署名付き配送期限を含める要件と、各ノードがそれを実施できるかは区別する。期限を判定できないことだけを理由に中継を禁止せず、期限内と確認済みにはせずに、ローカルな保持時間・配送量の上限内で保持・中継できる。

時刻を信頼できる場合は、期限内と期限切れを区別し、期限切れの新たなメッシュ配送を停止することを推奨する。BPv7 の経過時間、受信後の単調時計等は資源制限に利用できるが、受信前の情報の古さを完全に証明しない。再投入や不正な時計により、期限切れ情報が届く可能性を許容する。受信したことだけで、期限内・最新の情報と保証された扱いにしてはならない。

削除要求・ID 情報・欠落ブロック取得等の制御データの保持・配送規則は、通常投稿と分けて検討する。有効期間の開始・終了の指定方法、時計ずれ・時計不明時の必須時刻の作成方針、満了後の保存・表示、Nostr・atproto の保持方針との関係は未決定である。

### 1.13 配送優先度

著者による署名付き優先度の指定は配送上の希望・ヒントとする。実効優先度は受信ノードが情報源への信頼、地域との関連、資源状況等のローカルな運用方針から決定する。

著者署名付きの指定は書き換えず、実効優先度は受信側の配送判断として扱う。未信頼の著者が高優先度を指定しても、そのまま優遇する必要はない。公的な情報も無条件に最高優先度とはしない。優先度を上げても保存量・送信量等のローカル上限を解除しない。段階数・既定値・具体的なスケジューリング方式は未決定である。

### 1.14 分散復元と論理 PDS

収集・復元サーバーを分散しつつ、既存 Relay 向けには DID ごとに一つの論理 PDS を公開する構成（[PDS・Relay 調査](../docs/research/0005-pds-relay-research.md) の案 A）を採用する。論理 PDS の公開 HTTPS endpoint と、その背後の複数の収集・復元・公開サーバーを区別する。

著者の署名済み commit・レコード・状態を復元・複製し、サーバー側で再署名や `rev` の付け直しをしない。別ホストの同一 DID の更新を、標準 Relay の重複排除だけに依存して同時に正規公開元として取り込ませる方式は採用しない。独立ホストのミラーは保管・復旧等の内部経路に利用できる。

同一公開ホストの背後では、firehose の順序・`seq`・再送履歴、同期 API と account 状態の整合性・継続性が必要となる。無調整な独立 stream の負荷分散だけではフェイルオーバーが成立したとは扱わない。

公開名、DNS・TLS・管理権限の障害耐性、stream の複製・切替機構と相互運用試験は未決定・未検証である。全世界で単一の論理 PDS を必須とはせず、複数の運用グループがそれぞれ論理 PDS を提供できる。DID はそのうち一つのグループの公開 HTTPS endpoint を正規 PDS として指定する。アプリ・運用者が既定の論理 PDS グループを事前設定し、平時の自動登録から、その公開 HTTPS endpoint を PLC 初期操作に含める方式を採用する。未登録のままオフラインで初回利用する例外経路でも同じ設定を用いる。プロトコル全体で一つの既定グループを強制しない。代理登録ノードは指定先を書き換えず、端末の署名済み初期操作を送信する。

DID に endpoint が記載されたことは、当該グループが発信者を受け入れたことや、リポジトリが公開済みであることの保証ではない。発信者の事前登録は不要とし、署名と DID の対応、自グループが正規公開先であること等を検証して、資源上限・濫用対策・運用方針の範囲で受け入れる。無制限の保存は保証せず、拒否・保留・公開完了の確認方法と既定グループ停止時の対応は未決定である。公開先の変更操作は端末の PLC 管理鍵で署名する。

物理 PDS は複数の論理 PDS グループに同時に所属できる。論理 PDS と物理 PDS の関係は多対多であり、物理 PDS の所在と DID が指す正規公開先を同一視しない。署名済みブロックの共用保存等は可能だが、各論理 endpoint の stream・`seq`・再送履歴・公開対象・account 状態の整合性はグループごとに管理する。異なる論理 endpoint の `seq` を共通カーソルとして扱わない。

別グループの物理 PDS が同じ署名済みデータを保持しても、DID の正規公開先が自動的に複数へ増えるわけではない。情報の収集・検証・ミラーは誰でも独立して実施できる。一方、グループの正規公開系への参加には、そのグループによる承認・認証を必要とする。公開 endpoint での応答や共通 stream の採番・切替等の権限を、データを保有していることだけで取得できるとは扱わない。各グループが独立に参加方針を定め、同一の物理 PDS をそれぞれ承認できる。承認されても著者の署名鍵や PLC 管理鍵は取得しない。

他の同一プロトコル対応グループが DID の正規公開先であり、そこがまだ知らない commit を収集した場合は、正規公開先へ commit や取得元 Nostr リレー情報を共有する。共有で著者署名を変更せず、受信先は独立に検証する。小さな通知と受信側による必要時取得を基本方式とし、既知の commit の取得を省略できる。停止中の正規公開先へは制限付きで再試行し、通知だけを別グループへ転送し続けない。通知の必須項目、必要なレコード・ブロックの取得、既知状態の確認、発見・認証・保持・再試行上限等の具体方式は未決定である。

グループ内部の DB・複製・合意・リーダー選出の方式は固定せず、外部から見た整合性と復旧の要件を規定する。同一論理 endpoint の `seq` の意味の維持、保持範囲の再送、欠落を隠さない再同期、リポジトリと更新情報の整合性、遅れた複製先への無条件な切替の防止を求める。任意の異なる実装が同じグループ内で自動的に協調できることは保証せず、内部通信用の共通仕様の要否は別途検討する。

グループの承認・認証の具体方式、参加・離脱・権限失効、公開名の管理、DID の公開先グループ変更の具体手順は未決定である。詳細は [論理 PDS と分散公開](0006-logical-pds.md) を参照する。

### 1.15 物理 PDS の Nostr リレー機能

物理 PDS 自身が標準 Nostr リレーとして投稿・保存・取得・購読を提供する。クライアントは接続可能な対応物理 PDS へ直接送信でき、これらを優先的なリレーとして利用する。本プロトコルの独自タグやオフライン配送による古い投稿時刻だけを理由に拒否しない。資源上限・保持方針・不正データ対策は引き続き適用する。

グループ間共有の取得元として共有元 PDS の Nostr リレーも利用する。全 NIP 対応や全イベントの無制限な受け入れ・永久保存を意味しない。能力・制限は NIP-11 の標準項目と本プロトコル向けの追加情報で公開する。対応バージョン・受け入れ／保持方針・関連グループ等を表し、標準項目の意味を変更しない。リレー発見はアプリ同梱候補・保存済みキャッシュ・AppView の一覧・Nostr 経由の候補を組み合わせる。同梱候補には独自拡張のない著名な一般リレーも含められ、プロトコル共通の固定リストは設けない。対応リレーを優先し一般リレーも併用するが、一般リレーの受け入れ・保持は保証しない。候補一覧の自動更新はアプリ・運用者が信頼する複数の発行者を基本とし、未知の候補は区別して制限付きで探索する。一覧発行者への信頼から、投稿内容や公的情報の変換者への信頼を導かない。具体的なスキーマ・発行者認証・候補更新／失効・選択・検索・保持の規則は未決定である。能力の自己申告だけでグループ所属や公的情報源としての信頼を認めない。詳細は [Nostr リレープロファイル](0007-nostr-relay-profile.md) を参照する。

検索用のプロトコル識別には単一文字の `t` タグを用い、標準の `#t` フィルタで発見する。識別値は `mosimo.oriom.dev` とする。タグは著者が署名時点で含め、検索結果を署名・形式の検証済みや信頼済みとは扱わない。

### 1.16 PDS による MST 再構築と延期事項

本プロトコルのメッシュ・Nostr 配送では、端末署名済み commit、新規レコードと正確な repository path、削除対象等の変更操作を用いて PDS が MST を再構築する方式だけを対象とする。MST ノードや包含証明を同梱する配送形式は定義しない。再構築した root CID と commit の `data` を照合し、元の commit と署名を維持する。

各更新の配送データに、変更の適用元となる commit の CID を含め、Nostr イベントの署名対象とする。初回更新では適用元なしを明示し、以後は端末が直前に確定した commit の CID を指定する。これは本プロトコルの配送情報であり、標準 atproto commit の形式や `prev` の意味を変更しない。具体的なフィールド名・符号化は未決定である。

PDS は適用元の状態が検証済みの場合に変更を適用し、再構築した root と新しい署名済み commit の `data` を照合する。適用元参照は再構築の手掛かりであり、それだけで状態の正しさや履歴の非分岐を証明しない。

適用元の状態、または状態の再現に必要なレコード・変更が欠けている場合はリポジトリ状態の検証を保留し、推測した木を検証済みとして公開しない。Nostr 著者署名による単独投稿の検証・表示とは区別する。

PDS が欠落コミットを探索・取得するためのプロトコルは将来課題として記録し、今回は設計を進めない。これまで合意した発見済み commit のグループ間通知＋必要時取得とは区別する。

Nostr／atproto の双方向変換で両方の署名を維持する問題も将来課題へ送る。鍵対応宣言を両鍵で相互署名する採用済みの方針を取り消すものではない。

PDS が再構築した MST から、標準 atproto 同期 API や firehose の CAR 出力を作ることは、本プロトコルの入力に MST ノードを同梱することとは別である。標準 Relay 向け出力では既存の同期仕様に従う。

### 1.17 公開情報への限定

初期仕様は公開情報の共有に限定する。本文や公開した構造化位置情報は第三者が取得・保存し得る。影響範囲は閲覧者のアクセス制限ではなく、削除要求でも全コピーの回収は保証しない。

個別通信・限定公開・投稿の暗号化は [延期した課題](0003-open-questions.md#9-延期した課題今回の設計対象外) に記録し、今回は形式や鍵配布方式を定義しない。TLS 等の通信路保護と投稿自体の秘匿は別であり、通信路保護を不要とするものではない。要救助者の氏名・連絡先・詳細な所在等を安全に扱える仕組みを本仕様が提供すると誤認させない。

### 1.18 メディア配送の延期

初期仕様はテキスト・構造化情報と、その検証・復元に必要な署名済みデータを対象とする。画像・動画・音声等のメディア本体の配送は [延期課題](0003-open-questions.md#9-延期した課題今回の設計対象外) とし、今回は形式・分割・再送・保存管理を定義しない。

本文への URL 記載は可能だが、リンク先のオフライン取得や配送を保証せず、自動取得を要求しない。commit・レコード等のバイト列表現を運ぶことはメディア配送とは区別する。CAP・EDXL・気象庁 XML 等からの本文・構造化情報への変換は引き続き対象である。

### 1.19 ルート公開鍵と身元証明チェーン

自治体等の名称と公開鍵の対応は、信頼するルート公開鍵からの署名チェーンで証明する。アプリが既定のルート公開鍵を同梱でき、利用者自身も信頼するルートを選択できる。中間の証明者を介した多段チェーンに対応する。ルート秘密鍵を検証側へ配布するものではない。

署名チェーンは論理的な拡張ブロックとして含める。BPv7 の拡張ブロックだけへの配置を確定するものではない。受信チェーンに含まれる鍵を自動で信頼の起点へ追加せず、設定済みのルートから検証する。末端の発信端末への証明は組織名・発信者 DID・atproto リポジトリ署名公開鍵を結び付け、DID の鍵情報との対応も確認する。Nostr 用公開鍵は相互署名付き鍵対応宣言で結び付け、その宣言内の atproto 鍵と証明対象鍵の一致と各署名を検証する。atproto 署名鍵の変更時には証明の再発行等が必要となるが、具体手順は未決定である。

投稿用の身元証明、他者の身元を証明する権限、その再委任権限を区別する。証明・再委任できる名称・組織・用途等の範囲を制限し、下位への委任で上位の権限を拡大しない。証明経路は署名だけでなく各段の権限・範囲も検証する。

発行する身元証明に有効期間を設け、期限切れを現在有効な身元証明とは扱わない。チェーンの署名・権限の検証、期間確認、失効情報の確認と取得時点、時計・情報不足による判定不能を区別する。配送期限がベストエフォートであることを、身元確認済みとの誤表示の理由にはしない。証明の期限切れや確認不能は、投稿署名そのものの無効化・削除とは区別する。

証明書形式、委任範囲・権限の符号化と照合、経路長・サイズ、有効期間の長さと時刻表現、失効情報・時計ずれ、鍵更新・過去投稿の評価、具体的な配置と符号化は未決定である。署名チェーンによる身元確認と内容の真偽を区別する。詳細は [署名チェーンによる身元証明](0009-identity-attestations.md) を参照する。

## 2. 標準仕様に由来する制約

atproto repository v3 の commit の `data` は現在の MST ルート CID である。`prev` は過去の commit の CID を指す nullable フィールドであり、過去の MST ルート CID ではない。標準では通常 `null` である。

commit はレコード本文や変更操作の一覧を含まない。したがって、commit オブジェクトだけを集めてもレコード集合は復元できない。

同一の repository path → record CID の写像からは、標準の MST 構築規則に従って同一のルート CID を再現できる。必要なレコードと正確な path が別途取得できれば、MST ノードそのものを全て配送せず、受信側で再構築して署名済み commit の `data` と照合する設計は可能である。

commit の署名検証と、レコードがその commit の状態に含まれることの検証は別である。標準では後者に木や包含証明等を利用できるが、本プロトコルの入力は PDS による木の再構築で検証し、包含証明の同梱形式は定義しない。署名鍵と DID の対応の検証方式は未決定である。
