# MeshBundle host validation

Production files: `../include/MeshBundle.h`, `../src/MeshBundle.cpp`.
No ArduinoJson or new crypto dependency is required. The NIP-01 JSON preimage
is streamed directly into SHA-256 with the exact escaping used by Android's
`SignedPost.kt`. Typed commit/extension bytes become **unpadded standard Base64**
(`+` and `/`, never `=`), exactly like Android `B64.encode` in `AtRepository.kt`;
typed version `1` becomes the string `"1"`. Unknown signed strings and tag order
are preserved. The event ID is computed, not supplied by the sender.

## Actual server importer → ESP32 interop (two successive real MSTs)

`wire-v1-server-fixture.json` is generated by **the actual** `pds/public-information.mjs` exports (`createRoot`, `createImporter`, `issueCertificate`, `createSnapshot`, `createImporterEvent`). It is not a hand-built commit pointing at an empty/fake MST. `pds/repository.mjs:reconstruct` verifies both roots: one record for event 1, then both records for event 2. The second event has a nonempty canonical `base` pointing to event 1's signed commit CID; both commits have `prev:null`, matching the actual importer. Text and extension arguments match the shape of `appview/bsaf/publisher.mts:stageNext`, including Japanese attribution and `[bsafV1, identity, priority]` order. The SQLite publisher/main/network loop is not run.

The generator is a **standalone TEST ONLY process**. It installs a deterministic public test entropy stream in that process's WebCrypto providers before dynamically importing the actual APIs; it never changes dependency files or server code. Certificate serial/time/URLs are fixed test inputs. Generated private keys stay in process memory and are explicitly excluded from output. No operational key/config/database is read, and there are no network requests, PLC submissions or relay posts. A temporary file-backed trust store under ignored `.pio/` is removed on exit. `.invalid` endpoints and synthetic source Bot identity must never become production trust.

From `apps/esp32`, using the installed native Windows Node (validated with **v24.13.1**):

```sh
node test_bundle/generate_server_fixture.mjs --write
node test_bundle/generate_server_fixture.mjs --check
```

`--write` explicitly regenerates **only** the ESP32 public fixture; `--check` recreates it using the actual exports and requires byte-equivalent public output. Both were executed together with a 45-second tool bound. Producer/repository/publisher source SHA-256 values (normalized LF) record provenance and intentionally detect source drift. Existing `pds/node_modules` dependencies are reused; nothing is installed or written there.

From repository root in Windows Git Bash/sh, this is the exact bounded host command (Ubuntu WSL, existing cached mbedTLS 2.x/cbor2; no native Windows mbedTLS installation required):

```sh
MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu -- timeout 180s env PYTHONPATH=/home/mchiba/.cache/mesh-bundle-host/deps/usr/lib/python3/dist-packages python3 apps/esp32/test_bundle/test_ingress.py --mbedtls-include /home/mchiba/.cache/mesh-bundle-host/deps/usr/include --mbedtls-library /home/mchiba/.cache/mesh-bundle-host/deps/usr/lib/x86_64-linux-gnu/libmbedcrypto.a
```

The runner compiles the real `MeshIngress.cpp`/`MeshBundle.cpp` checker with `-Wall -Wextra -Werror` and ASan/UBSan, then checks both actual events and their exact signed-event/CBOR round trip with the fixture's coherent root, scope, selected Bot/type, receive time, snapshot and **minSequence=41**. It also accepts both consecutively across persisted snapshot/issuer-serial state. Python independently recomputes record/commit/original CIDs, hashes every supplied block, traverses the MST and verifies that the second root contains exactly the first and second records. This fixture audit does **not** add on-device MST inclusion-proof verification.

Measured actual output: JSON 3,635 / 3,694 bytes, payload 2,742 / 2,802 bytes, text 339 bytes, commit 188 bytes. Both fit the unchanged ESP32 strict input/CBOR/key bounds; no limit increase, signer allowlist, skipped signature or decoder relaxation was needed. The receiver additionally mirrors the server's atproto/Nostr same-x-coordinate key-reuse rejection, with a negative test where all signatures would otherwise be valid. The older primitive fixtures remain separate and are not presented as valid repository MST fixtures.

## Build requirements

- C++11 and mbedTLS **2.x** APIs (tested against host 2.28.8 and the installed
  espressif32 6.12.0 Arduino framework's headers/toolchain).
- `MBEDTLS_ECP_C`, `MBEDTLS_BIGNUM_C`, `MBEDTLS_SHA256_C`, and
  `MBEDTLS_ECP_DP_SECP256K1_ENABLED`; link the framework's existing mbedcrypto.
- `mbedtls_ecp_muladd`, MPI modular exponentiation, and SHA-256 must be available.
  No ECDSA-as-Schnorr substitution: this implements BIP340 lift_x, tagged
  challenge, scalar/field bounds, even-Y and non-infinity checks explicitly.
- mbedTLS 3.x private struct fields/API names are not supported by this file.
- Host fixture tests: Python 3.10+ and `cbor2` (tested with **5.6.2**).

On a Linux host with mbedTLS development libraries:

```sh
python3 -m pip install cbor2==5.6.2
g++ -std=c++11 -Wall -Wextra -Werror -g -fsanitize=address,undefined \
  -I../include host.cpp -lmbedcrypto -o /tmp/mesh-bundle-host
python3 test_bundle.py --host /tmp/mesh-bundle-host
```

Run these commands **from this directory**. `host.cpp` includes the production
implementation so official BIP340 vectors can exercise the private verifier;
do not separately compile/link `MeshBundle.cpp` into that host executable.

`fixtures.json` is deterministic and includes the signing JSON, payload, event
ID, valid BPv7 envelope, and signature-tampered envelope with *correct* BP CRCs.
Regenerate with:

```sh
python3 test_bundle.py --generate fixtures.json
```

All signing uses public test secret key **3**, deterministic BIP340 nonce
construction, and zero auxiliary randomness. The slow Python signer is for
tests only. `bip340-vectors.csv` is the unmodified public fixture from
<https://github.com/bitcoin/bips/blob/master/bip-0340/test-vectors.csv>.
The first 15 official vectors have 32-byte messages (Nostr SHA-256 digests);
variable-message-length vectors are intentionally outside this verifier API.

The suite checks official valid and invalid signatures, CRC-16/X-25 and
CRC-32C check values, definite/indefinite BP arrays, exact ID/Unicode/control
escaping, typed tags, tampering with recomputed CRCs, destination, extension
policy, duplicate blocks, payload position, age/hop/residence boundaries,
signed deadline validity, 24000-byte forwarding overflow, canonical payload
encoding, invalid UTF-8, truncations, and deterministic mutations. It checks
forwarded payload bytes are unchanged and re-validates forwarded bundles.

## Android Base64 regression and actual Kotlin fixtures

The original C++ encoder **incorrectly added padding**, and the original Python
fixture encoder made the same mistake. They agreed with each other but not with
Android. This changes the Nostr signing JSON, its event ID, and signature validity
whenever a typed byte string's length is not divisible by three.

The regression was added **before changing C++**, then run against the old host
binary. Both the independently signed Python case and a bundle produced by the
actual Kotlin implementations failed with:

```text
('mosimo.oriom.dev:commit', 1, 1, 'invalid event signature')
(('actual Kotlin', 'mosimo.oriom.dev:commit', 1), 1, 'invalid event signature')
```

`test_base64.py` now covers one-, two-, three-, and four-byte values for both
commit and extension tags. Fixed spellings include `+w`, `//8`, `AAH+`, `AAH+/w`.
It checks computed IDs, forwarded IDs, and byte-for-byte payload preservation.
`test_bundle.py` runs this regression automatically after the main suite. Padded
or noncanonical **text** tag values remain text and retain their exact signature;
they are not incorrectly converted to CBOR bytes by the Python oracle.

`android-base64-fixtures.json` is a separate fixture generated by
`GenerateAndroidFixture.kt`, compiled **alongside the real Android bundle-core
sources**. It calls the real `B64.encode`, Schnorr signer, `EventCodec.encode` /
`decode`, and `MeshEngine.originate`, not Python reimplementations. It contains
8 signed bundles plus source SHA-256 provenance for `SignedPost.kt`,
`AtRepository.kt`, `MeshEngine.kt`, and `CanonicalCbor.kt`. Python never
regenerates this file. The three-byte control cases also prove the failure is
specifically padding, rather than a blanket Schnorr implementation mismatch.
The measured differential was: old codec rejects all 6 non-multiple-of-three
Kotlin cases but accepts both three-byte controls; fixed codec accepts all 8.

Regenerate with JDK 21 and the existing Gradle dependency cache (no downloads or
Android/Gradle source/build modifications; requires an existing BPv7 jar):

```powershell
python apps/esp32/test_bundle/generate_android_fixture.py --java "C:/Program Files/Microsoft/jdk-21.0.6.7-hotspot/bin/java.exe"
```

Run from the repository root. The helper uses Kotlin 2.3.20, the versions already
pinned by bundle-core, and the appropriate cached desktop secp256k1 JNI artifact.
On this Windows machine compiler argfiles and `producer.jar` are retained at
`C:\Users\chiba\.cache\mesh-bundle-kotlin`. `--gradle-cache`, `--java`,
`--bpv7-jar`, `--build-dir`, and `--output` can override local locations.

## Integration contract and deliberate limits

- The suggested `mesh::BundleInfo`, `validateBundle`, and `forwardBundle` API is
  unchanged. Success is sufficient for codec-level ACK eligibility; dedup,
  storage success, flooding/rate policy and BLE framing remain caller duties.
- **No trusted clock:** a unique, valid signed UTC deadline is mandatory, but
  wall-clock expiry and creation-timestamp expiry are UNKNOWN, matching
  Android `ClockConfidence.UNKNOWN`. Past deadlines are not guessed from an
  ESP32 wall clock. The age and lifetime policies still apply.
- Frames are 1..24000 bytes; lifetime is 1..86400000 ms; age must be strictly
  below lifetime. A hop count at `min(limit, 8)` may be accepted but is not
  forwarded; limits must be 1..255. Residence uses overflow-safe subtraction.
- Pass **total monotonic residence since these stored input bytes arrived**
  to forwarding. Each retry starts from those same bytes. Forwarding verifies
  the entire original again and returns a new hop/age/CRC view. Never reset
  residence to extend lifetime. After a reboot, discard entries if their
  monotonic residence cannot be recovered safely. No persistent checkpoint API
  is provided; ordinary 24000-byte wire bounds apply to both APIs.
- No input/output aliasing for `forwardBundle`; `out` is cleared at entry.
  Outputs are cleared on rejection and errors are cleared on success.
- Fragmentation, admin records, BPSec and unsupported EID schemes are rejected.
  Payload number must be 1 and payload must be last. Primary CRC is mandatory;
  canonical CRC type 0 is allowed like Android, and every present CRC is
  checked against the *original received encoding*, including break bytes.
- Previous Node blocks are checked and dropped when forwarding. Unknown blocks
  with delete-bundle flag `0x04` reject; discard-block `0x10` drops on forwarding;
  others are preserved byte-for-byte. Unchanged primary and signed payload
  bytes are preserved too. Only age/hop blocks are re-encoded with new CRCs.
- Maximum 64 canonical blocks (a deliberate local tightening of Android's
  general CBOR limits), 8192 parser items, 256 tags, 32 strings per tag,
  16384 content bytes, and 262144 reconstructed JSON bytes. Payload CBOR must
  be minimal/definite. Fixed-shape readers are nonrecursive and never allocate
  from a claimed CBOR string/container length. Integers are bounded to signed
  64-bit compatibility with Android. Typical Android bundles have three blocks.
- No full event JSON/tree is allocated. Heap is bounded by actual 24KB input,
  a 64-entry block table, extracted content/ID, at most one Base64 tag string,
  and forwarding output, plus mbedTLS's bounded secp256k1 workspace. Allocation
  failure follows the framework's stdlib policy, not a recoverable bool error.
- Run on a serialized worker with adequate task stack, **not a BLE callback**.
  This is synchronous software Schnorr verification and may take significant
  ESP32 CPU time. Parent integration must measure device latency/heap/stack.

Validation: 15 official BIP340 vectors; 228 bundle / forwarding / malformed-input
checks; 16 unpadded typed-byte cases (including 8 actual Kotlin-generated bundles),
with forwarded IDs and payload preservation. Full firmware and BLE device results
are recorded separately in [../VERIFICATION.md](../VERIFICATION.md).

## Relay and BLE transport regressions

From the repository root on Linux with GCC, mbedTLS 2.x development libraries,
Python cbor2 and PlatformIO dependencies installed:

```sh
python3 apps/esp32/test_bundle/test_relay.py
python3 apps/esp32/test_bundle/test_ble.py --sanitize
```

Relay compiles the production codec/exchange with ArduinoJson 7.4.2, mocking only
LittleFS and monotonic time. Its 3,621 assertions cover verification before writes,
ACK after readback, the provisioned 32-character filename limit, numeric slots,
cold restoration, bounded cache replacement, duplicate age preservation, queue
backpressure, protocol limits, and failed I/O without false ACKs. Accepted-message
callbacks fire only for verified, successfully saved new events, not duplicates,
failed saves or reboot-restored entries. Same-session 17th receipt and bounded
128-ID completion history have dedicated regressions. Verified kind metadata is
preserved for ordinary posts and PLC control events; controls still save, ACK and
forward without changing their event ID/content.

BLE compiles production `MeshBle.cpp` with mocked NimBLE/FreeRTOS/Relay. Its 316
assertions cover nonzero handles, notification queue acceptance versus application
ACK, split length headers, frame bounds, pacing, retry, overflow during a blocked
receiver, physical disconnect, radio disable/re-enable, bounded busy-peer polling,
and clean reconnection. Neither host mock proves
radio delivery or actual power-loss durability.

With the WSL environment above, Relay accepts
`--mbedtls-include /home/mchiba/.cache/mesh-bundle-host/deps/usr/include` and
`--mbedtls-library /home/mchiba/.cache/mesh-bundle-host/deps/usr/lib/x86_64-linux-gnu/libmbedcrypto.a`.
Use the same `PYTHONPATH` environment as for the codec suite. `test_ble.py` needs
no external libraries. Both harnesses build in temporary directories and run
ASan/UBSan by default (BLE requires `--sanitize` to enable them).

## Standalone evaluation speech

From the repository root on Linux with GCC:

```sh
python3 apps/esp32/test_bundle/test_speech.py --sanitize
python3 -m unittest discover -s apps/esp32/test_bundle -p test_tts_setup.py
```

`test_speech.py` compiles the actual `MeshSpeech.cpp` and text/queue helpers with
mocks only at SDK, M5, partition/hash, and task boundaries. It checks UTF-8
sanitization/chunking, bounded latest-priority jobs, deduplication, mute/cancel,
dictionary bounds and mapping failures, three-buffer output ownership, SDK/frame
errors, backpressure, timeout and non-silent sample accounting. It does not execute
the proprietary synthesizer; the separate device smoke test does.

The 13 setup tests use runtime-generated fake ZIP contents, not vendor assets.
They check idempotent local extraction, no overwrites of differing files, entry
size limits, ignored extra/traversal paths, generated size/hash config, and
refusal of unexpected partition layouts before any flashing. They guard against
subprocess/device access.

Physical audio quality, DMA drain latency, and an SDK call that never returns
are not covered. Timeout/cancel checks are cooperative between SDK calls, not an
independent watchdog. No SDK source, library, dictionary, keys, or linked firmware
is included in these tests or the repository.
