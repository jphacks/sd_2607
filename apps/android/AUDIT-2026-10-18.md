## Decision for today's integration

**Use the existing MNDT §9 experimental wire on both ends for today's demo, not a claim of latest MNDT §3 conformance.** Android and the inspected ESP32 implementation currently agree on §9. Moving only one side to §3 breaks the link. Full migration is a coordinated change, not a safe deadline patch; INVENTORY layout, CANCEL, some ID/resource limits and timeout policy still need specification decisions.

The post/event binding is substantially current. The major standards gap is the *outer contact protocol*, not the signed event payload.

## Changes

1. `mesh-android/src/main/kotlin/org/mndt/mesh/Exchange.kt`: invoke the durable-save callback before ACK, success diagnostic and inventory broadcast; document its failure contract.
2. `mesh-android/src/main/kotlin/org/mndt/mesh/MeshCoordinator.kt`: received bundles are persisted synchronously before relay drain; own provisional PLC genesis is persisted before announcement. Existing persistence failure handling marks fatal, closes links and hides/stops unsaved forwarding; no new storage format or dependencies.
3. `mesh-android/src/test/kotlin/org/mndt/mesh/ExchangeTest.kt`: assert no ACK/inventory can precede save; simulate disk failure and assert neither leaves the receiver.

Tradeoff: each new received bundle now writes the bounded encrypted snapshot instead of waiting for the one-second batch tick. This intentionally favors durable custody over batching; no throughput guarantee is made. Duplicate receipt handling and relay-acceptance batching are unchanged. JVM tests exercise the callback boundary, not Android Keystore or injected real filesystem failures; genesis ordering is source-reviewed and compiled, not separately instrumented.

## Exact integration expectations / deadline blockers

### Android ↔ ESP32 (today's experimental path)

- Both sides stay on **MNDT §9**, never mix §3 frames into this connection.
- Service `b5e89a01-f9da-45c2-9111-2de7a7441d24`; RX `483c3867-c832-4c60-9a96-7018059eaf74` (Android writes with response), TX `49d60590-c23f-4a0a-a58e-f2f2f606f94d` (notify; CCCD enabled).
- Advertise service UUID; scan response service data = 8-byte node + flags, bit0 peripheral-only for ESP32. Android and ESP32 source match these values at inspection time.
- Each frame = uint32 big-endian length then JSON control or BPv7 bytes beginning `0x9f`. hello = `{"v":1,"type":"hello","node":"<16 lowercase hex>","max":24000}`. Other controls have `v`, `type`, `ids`; ack has one 64-lowercase-hex ID. Inventory/want lists are at most 128. Only send requested Bundle IDs to ESP32.
- Android receives/forwards at most **24,000 Bundle bytes**, accepts 128 stored entries; ESP32 documents 16 cached Bundles. These are smaller permitted local limits, not contradictions of the agreed payload 32 KiB / Bundle 64 KiB ceilings. GATT chunks are `min(MTU-3,512)`.
- Do not reboot/reset ESP32 between store and forward: restored entries are deliberately cold and not forwarded. Its one BLE connection must be released by the source before destination connects. Radio visibility, permissions and foreground/background behavior still need the physical run.
- Enable Bluetooth **before** pressing relay start. `GattLink.start` returns if Bluetooth is off and no adapter-state restart is implemented; if toggled, stop/start relay again. This remains a reliability limitation, not fixed by the save-order patch.

### Offline author → online gateway → PDS

- Default gateways include `wss://pds.oriom.dev`, `wss://relay.damus.io`, `wss://nos.lol`. Custom/deleted relay lists are preserved; ensure PDS is actually present. Online export must be enabled and Activity visible or relay service running.
- New offline author must also deliver its **separate provisional kind 8173 genesis** over mesh. Online Android submits signed operation unchanged to `https://plc.directory`; it does NOT send kind 8173 to the PDS relay. Every routing hop must retain this control event as well as posts. Without genesis, Nostr text may be accepted while atproto reconstruction waits for PLC.
- New installs configure canonical PDS `https://pds.oriom.dev`; old saved `.invalid` identities are not silently migrated. They require an explicit identity/PDS migration decision, not app-data deletion.
- Carry the **entire base chain**, including the first event (`base=""`), unchanged. Third-party carried posts remain evictable under existing capacity policy; a saturated gateway/16-entry ESP32 may lose required history. Keep today's test small. No missing-base recovery or guaranteed all-relay delivery is implemented.
- UI authoring limit is **2,000 UTF-8 bytes**, matching documented ESP32 speech input limit. Avoid private/disaster-like test text; public posts are persistent.

### PDS → Relay → AppView → web (other owners)

- PDS reconstructs collection `dev.oriom.mosimo.post`, text plus createdAt/deliveryExpiresAt/extensions, original record CID and signed v3 commit. It must wait on missing PLC/base, not fabricate history or re-sign.
- Acceptance checkpoints are separate: peer ACK → Nostr `OK=true` → PLC resolution + PDS `getRecord`/`getLatestCommit`/CAR → Relay matching head/firehose → AppView ingestion → web rendering. Android's OK alone cannot certify the latter steps.
- Join on **full Nostr event ID** through mesh/Nostr; derive DID from signed commit and path from `mosimo.oriom.dev:path`. Join atproto/AppView on **DID + collection + rkey / atURI + record CID**, not text equality. rkey need not equal commit rev. Independent same-text posts are not duplicates.
- AppView must ingest the custom Lexicon, not only `app.bsky.feed.post`; web must show that same record. General Bluesky client visibility is not promised. Record exact event ID, DID/path/CID and hop at each stage for the final coordinated evidence.
